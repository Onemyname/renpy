# 36. Справочник проблем

> **Статус подсистемы:** справочник, а не подсистема. Все записи ниже — по коду и по фактическим сообщениям этого репозитория (`vn` 0.1.0, игра 0.1.4, Ren'Py 8.5.3.26051504). **Но** часть проблем в разделах 9–11 (DAZ/ComfyUI/VaM/Sims 4) относится к внешнему окружению, которое проект детектирует, но не автоматизирует — там источник истины `vn pipeline doctor` и `docs/pipeline/phase-0.md`, а не наш код.
> **Отвечает на вопрос:** «У меня вот такая ошибка/симптом — что это и что нажать».

Записи сгруппированы по слоям: окружение → сборка → рантайм → ассеты → видео → локализация → сейвы → релиз/CI → внешний 3D/AI-конвейер. Формат каждой записи одинаков, чтобы её можно было прочитать по диагонали и чтобы AI-агент мог сматчить дословный текст ошибки. Короткая таблица «первых восьми симптомов сборки» уже есть в [03-getting-started.md §8](03-getting-started.md) — здесь она не дублируется, а расширяется.

## Быстрый ответ

```bash
vn doctor                    # 1. окружение (8 проверок; exit 1 = чинить здесь и дальше не идти)
vn content lint              # 2. декларации: те же error:-строки, что валят vn build, но без сборки
vn build --check             # 3. свежесть ассетов и генерата, разметка переводов, бюджеты G19
cat errors.txt               # 4. если игра не стартует — Ren'Py положил сюда ошибку скрипта
cat log.txt                  # 5. если стартует, но ведёт себя странно — [vn]-строки надстройки
cat traceback.txt            # 6. если упала в рантайме
vn test smoke --picks 0,0    # 7. воспроизвести прохождение автопилотом (скриншоты в .vncache/smoke/)
vn pipeline doctor           # 8. только для контент-продакшена: ffmpeg/GPU/CUDA/ComfyUI/DAZ/модели
```

Три файла в корне репозитория — `log.txt`, `errors.txt`, `traceback.txt` — пишет сам Ren'Py, они в `.gitignore:15-17` и перезаписываются каждым запуском. Читайте их до того, как перезапустите игру.

# 1. Окружение и установка

### `vn: command not found` / `vn не является внутренней или внешней командой`

**Симптомы:** оболочка не находит команду `vn`; `pip show vn-tools` пуст либо показывает другой интерпретатор.
**Вероятная причина:** пакет `vn-tools` не установлен, либо установлен в другой Python (venv/системный/Store-версия), чей `Scripts/` не в `PATH`. Точка входа объявлена как `vn = "vn.cli:main"` (`../../tools/vn/pyproject.toml`).
**Диагностика:**
```bash
python -c "import vn, sys; print(vn.__file__, sys.executable)"
```
**Решение:** `pip install -e "tools/vn[dev]"` тем же интерпретатором, который вы используете. Если `import vn` работает, а команды нет — вызывайте `python -m vn.cli` либо добавьте `Scripts/` в `PATH`.
**Профилактика:** один интерпретатор на проект; в CI ровно та же строка — `pip install --quiet -e "tools/vn[dev]"` (`.github/workflows/ci.yml:31,47` — ей предшествует `pip install -r tools/vn.lock`).

### `ошибка: не найден корень репозитория: нужен project.yaml + tools/schemas/ в текущем каталоге или выше`

**Симптомы:** любая команда `vn` падает с этим текстом и exit 1.
**Вероятная причина:** CWD вне репозитория. Маркер корня — **оба** объекта сразу: файл `project.yaml` и каталог `tools/schemas/`; `.git` в поиске не участвует (`../../tools/vn/src/vn/repo.py:15-23`).
**Диагностика:** `pwd` и `ls project.yaml tools/schemas`.
**Решение:** `cd C:/Users/Vadim/IdeaProjects/renpy` (или в любой её подкаталог).
**Профилактика:** запускайте `vn` из корня; в скриптах — `cd "$(git rev-parse --show-toplevel)"`.

### `vn doctor` красный: как читать вывод

**Симптомы:** одна или несколько строк с `✗`, exit 1. Строка `!` — предупреждение, на exit не влияет.
**Вероятная причина:** зависит от строки. Полный список проверок и рецептов — `../../tools/vn/src/vn/doctor.py:69-153`; расшифровка каждой — [03-getting-started.md §3](03-getting-started.md).
**Диагностика:** сам вывод: под каждой не-`✓` строкой печатается рецепт `→ …` (норма G22 — рецепт обязан быть исполнимой командой).
**Решение:** по строкам —

| Строка | Что делать |
|---|---|
| `✗ Python 3.9.x` → `нужен Python >= 3.10` | поставить Python 3.10+ (на референс-машине 3.12.10) |
| `✗ git` / `✗ git-lfs (нет)` | установить, добавить в `PATH` |
| `✗ корень репозитория` | см. запись выше |
| `✗ project.yaml (min_tools X, vn Y)` → `обновите vn: pip install -e tools/vn` | версия тулинга ниже `project.yaml:4 min_tools` |
| `✗ реестр схем tools/schemas/` | битое имя файла схемы или `properties.schema.const` не равен имени файла (`schemas.py:26,31`) |
| `✗ шрифты UI: 0/3 материализованы (указатели LFS: …)` | см. отдельную запись ниже |
| `✗ Ren'Py SDK не найден` / `✗ Ren'Py SDK X != пину Y` | см. две записи ниже |
| `! локальное переопределение .vnstorage.local.yaml активно` | это не ошибка: у вас свой путь к хранилищу сырцов |

**Профилактика:** `vn doctor` — первый шаг любого разбирательства; `vn bootstrap` сам останавливается на красном докторе (`cli.py:212-213`).

### `✗ Ren'Py SDK не найден` (и почему `vn build` при этом иногда зелёный)

**Симптомы:** `vn doctor` красный по SDK; `vn play` → `ошибка: Ren'Py SDK не найден: скачайте с renpy.org и установите RENPY_SDK (vn doctor подскажет)`; компилятор при холодном кэше → `RENPY_SDK не установлен, а в content/ есть главы: компиляция сцен требует парсер Ren'Py из пиннованного SDK (G24)`.
**Вероятная причина:** переменная `RENPY_SDK` не задана, задана в другом процессе, или указывает на каталог **без** `renpy.py`. Поиск SDK строго env-only, никакого автоскана (`doctor.py:24-30`). SDK-fail — жёсткий только если в `content/chapters/` есть `ch*` (`doctor.py:121-142`); иначе это предупреждение.
**Диагностика:**
```bash
echo "$RENPY_SDK" && ls "$RENPY_SDK/renpy.py"
```
Зелёный `vn build` при красном докторе означает тёплый кэш анализа: `.vncache/analyze-<24 hex>.json` отдаёт результат разбора без запуска движка (`tools/vn/src/vn/content/analyze.py:52-55`).
**Решение:** `setx RENPY_SDK "C:\Users\Vadim\renpy-sdk\renpy-8.5.3-sdk"` и **новый терминал**. Чтобы убедиться, что сборка честная: удалите `.vncache/analyze-*.json` и пересоберите.
**Профилактика:** не считать зелёный `vn build` доказательством настроенного окружения — доказательство это `vn doctor` с exit 0.

### `RENPY_SDK` не наследуется в bash-сессии агента

**Симптомы:** в PowerShell всё работает, в Git Bash (в т.ч. в сессии AI-агента) `vn doctor` красный по SDK, `vn build` падает на build-bridge.
**Вероятная причина:** `setx` пишет в реестр User-окружения, и переменную получают только **новые** процессы; оболочка агента могла быть запущена раньше или с урезанным окружением.
**Диагностика:** `env | grep RENPY_SDK` — пусто.
**Решение:** экспортировать в том же вызове:
```bash
export RENPY_SDK="C:/Users/Vadim/renpy-sdk/renpy-8.5.3-sdk"
vn build
```
**Профилактика:** в любых bash-сниппетах хендбука и в скриптах агента строка `export RENPY_SDK=…` идёт первой. Та же грабля у `CIVITAI_API_KEY` — см. раздел 10.

### `✗ Ren'Py SDK 8.6.x != пину 8.5.3 (project.yaml)`

**Симптомы:** доктор красный, рецепт `поставьте пиннованную версию SDK или обновите пин отдельным PR (G18)`.
**Вероятная причина:** установлен SDK другой версии. Фактическая версия читается из `<sdk>/renpy/vc_version.py`, пин — `project.yaml:5 renpy_sdk: "8.5.3"`; сравнение по префиксу (`doctor.py:33-42,133-135`).
**Диагностика:** `grep -n "^version" "$RENPY_SDK/renpy/vc_version.py"`.
**Решение:** поставить 8.5.3 либо сменить пин **отдельным PR**: `project.yaml:5` плюс вручную `RENPY_VERSION` в `.github/workflows/{ci,nightly,release}.yml` (автосверки этих значений нет). Свежий Ren'Py еженедельно прогоняет `canary.yml` — посмотрите, зелёный ли он, прежде чем двигать пин.
**Профилактика:** апгрейд SDK — всегда отдельный PR с прогоном canary (норма G18), никогда не «заодно».

### `✗ шрифты UI: 0/3 материализованы (указатели LFS: Inter-Regular.ttf, …)`

**Симптомы:** доктор красный по шрифтам; при запуске игра падает на первом же экране ошибкой шрифта; в релизном гейте `FAIL шрифты UI: … — УКАЗАТЕЛИ LFS: …; checkout без lfs:true даст падающую сборку`.
**Вероятная причина:** чекаут без git-lfs. `.gitattributes:3-5` переводит `*.ttf/*.otf/*.woff2` в LFS; без него на диск ложится текстовый указатель. Проверка контентная, по magic bytes (`doctor.py:45-66`) — работает и без установленного git-lfs.
**Диагностика:**
```bash
head -c 64 game/fonts/Inter-Regular.ttf | xxd | head -2   # ожидается 00 01 00 00 / OTTO / true / ttcf
```
**Решение:** `git lfs install && git lfs pull`.
**Профилактика:** во всех четырёх workflow чекаут идёт с `with: {lfs: true}`; тот же детектор встроен в релизный гейт (`release.py:318-327`) — артефакт не уедет с указателями.

### Не та версия Python

**Симптомы:** `✗ Python 3.9.13` → `нужен Python >= 3.10`; либо синтаксические ошибки при импорте `vn` (кодовая база использует `X | None`).
**Вероятная причина:** активен старый интерпретатор.
**Диагностика:** `python -V`, `python -c "import sys; print(sys.executable)"`.
**Решение:** Python 3.10+ (эталон проекта — 3.12; CI использует `python-version: "3.12"`), переустановить пакет: `pip install -e "tools/vn[dev]"`.
**Профилактика:** `tools/vn.lock` фиксирует 18 пакетов, и с 2026-08-08 **он читается**: во всех в 8 джобах установки тулчейна (7 строк в конфигах: GitLab-шаблон `.with-sdk` разворачивается в `build` и `test`) перед editable-установкой идёт `pip install --quiet -r tools/vn.lock` — проверить можно `grep -rn "vn.lock" .github/ .gitlab-ci.yml`. Порядок «лок раньше editable» стережёт `tools/vn/tests/test_ci_config.py`. Остаток честного ограничения: транзитивные зависимости в локе не закреплены (`pygments`), так что воспроизводимость гарантирована для 18 прямых пакетов, а не для всего дерева.

# 2. Сборка и компиляция

### `ошибка: lint: N ошибок — сборка остановлена`

**Симптомы:** перед этой строкой — блок `error: <путь>: <что не так>`; exit 1; `game/generated/` не тронут.
**Вероятная причина:** `vn build` запускает lint первым и на ошибках останавливается (`cli.py:94-100`). Инвариант проекта: «lint зелёный ⇒ build не падает».
**Диагностика:** `vn content lint` — печатает ровно те же строки без сборки (`cli.py:382-396`). Типовые классы:

| Текст ошибки | Что чинить |
|---|---|
| `<путь>: обязательный файл отсутствует` | один из 7 REQUIRED_FILES (`tools/vn/src/vn/content/lint.py:35-43`) |
| `<путь>: <место>: <сообщение jsonschema>` | документ не проходит свою схему (`schemas.py:48-50`) |
| `<путь>: отсутствует обязательное поле schema (правило G16)` | в YAML/JSON нет `schema: <name>@<N>` |
| `<путь>: неизвестная схема 'x@1'; зарегистрированы: …` | опечатка в id схемы либо схема не заведена в `tools/schemas/` |
| `…: имя папки главы вне конвенции ch<NN>_<slug> (1.4)` | переименовать каталог |
| `…: нет парного .scene.rpy` / `.scene.yaml` | сцена — **пара** файлов (G3) |
| `…: id (X) != имени папки/номеру файла (Y)` | привести `id` к пути |
| `layout: обязательный каталог отсутствует: …/` | один из 10 REQUIRED_DIRS |
| `layout: запрещённый путь существует: game/content` или `game/images` | удалить: `content/` строго вне `game/`, автоопределение образов не используется |
| `assets_src: бинарей на N МБ > порога ADR-0004 (50 МБ)` | заливать сырцы в хранилище (`vn assets lock` + `vn assets push`) |

**Решение:** править источник в `content/` или `packs/`, а не генерат.
**Профилактика:** `vn content lint` перед коммитом; в CI это отдельная джоба-предохранитель (`ci.yml:32`). Помните про G15: у главы со `status: draft` граф-проверки (порядок сцен, entry, exits, достижимость) — **предупреждения**, а не ошибки (`tools/vn/src/vn/content/lint.py:209,231,270`), поэтому «зелёный lint» на драфте не значит «граф корректен».

### `устарело: <файл>` + `ошибка: генерат не свеж — выполните vn build` (после смены HEAD)

**Симптомы:** локально ничего не меняли, но `vn build --check` краснеет на `version.gen.rpy`; в CI то же самое.
**Вероятная причина:** компилятор зашивает короткий git-sha в версию игры: `define config.version = "0.1.4+dd1cb3e"` (`game/generated/version.gen.rpy:8`, эмиттер `tools/vn/src/vn/content/compile.py:82-87`). Любой новый коммит делает генерат несвежим по определению — генерат **связан с коммитом**.
**Диагностика:**
```bash
git rev-parse --short HEAD
grep config.version game/generated/version.gen.rpy
```
**Решение:** `vn build`. Это ожидаемое поведение, а не поломка.
**Профилактика:** не удивляйтесь красному `--check` после `git pull`/`rebase`; в CI `vn build` всегда идёт перед `vn content compile --check`. Проверка свежести сравнивает **байты выходов**, а список `manifest["inputs"]` пишется, но обратно не читается (`tools/vn/src/vn/content/compile.py:881-922`) — то есть «свежесть» это «выход совпал», а не «вход не менялся».

### `ошибка: game/assets не свеж — выполните vn build`

**Симптомы:** в режиме `--check` строки `устарело: assets/<путь> (нет файла)` / `(нет в манифесте — соберите vn assets build)` / `(источник изменился)` / `(осиротел)`.
**Вероятная причина:** проверка сравнивает `src_hash` / `transform` / `profile` каждого выхода с `.vncache/assets-manifest.json` (`tools/vn/src/vn/assets/pipeline.py:401-414`). Свежий чекаут или удалённый `.vncache` дают массовое «нет в манифесте».
**Диагностика:** `vn assets validate` — та же проверка, но несвежесть там предупреждение, а не ошибка (`cli.py:537-538`).
**Решение:** `vn assets build` (или `vn build`). Профиль важен: собранное в `draft` не совпадёт с ожиданиями `full` — `profile` входит и в ключ кэша, и в манифест.
**Профилактика:** не смешивайте профили в одном дереве. Итерации — `--profile draft`, всё, что проверяет CI и релиз — `full`.

### `ошибка: внутренняя ошибка компилятора: <Type>: <текст>` + обрезанный трейсбек

**Симптомы:** exit 1, три кадра трейсбека.
**Вероятная причина:** непредусмотренное исключение внутри `compile_content`. Контракт CLI: exit 1 **всегда** с сообщением, никогда голым трейсбеком (`cli.py:119-123`).
**Диагностика:** тип исключения в первой строке; повторите `vn content compile` (без lint), чтобы отделить проблему компилятора от проблемы деклараций.
**Решение:** это баг тулинга — заводите issue с полным выводом и коммитом. Обход на время: возьмите последний зелёный генерат артефактом CI-джобы `build` (`ci.yml:81-86`, 30 дней) и распакуйте в `game/generated/` — игра запустится без локальной компиляции. Автоматизация этого (`vn build --use-artifact <sha>`) — **NOT IMPLEMENTED**, флага не существует; в `docs/ARCHITECTURE.md` он упомянут 14 раз.
**Профилактика:** руководство по эскалации — `../runbooks/pipeline-broken-at-night.md`.

### `<файл>:<строка>: метка 'X' вне контракта ^chNN_sNNN__<suffix>$ (C2; naming.md)`

**Симптомы:** одна или несколько таких строк, затем `ошибка: N ошибок компиляции сцен`.
**Вероятная причина:** авторская `.rpy` нарушила контракт сцены (`tools/vn/src/vn/content/scenes.py:81-104`). Родственные сообщения:
- `<файл>: нет обязательной метки chNN_sNNN__body (C2)`;
- `<файл>:<строка>: jump|call <цель> — переход вне своей сцены; межсценовые переходы только через return "<exit_id>" + exits (C2)`;
- `<файл>:<строка>: jump|call expression запрещён в авторских сценах`;
- `<файл>:<строка>: условный пункт меню #N ('cond') — запрещено (ломает перевод по индексу)`;
- `line N: стейтмент <Class> вне label запрещён в scene.rpy` (из build-bridge, `game/framework/00_core/050_build_bridge.rpy:131-132`).

**Диагностика:** открыть указанный файл на указанной строке. Номера строк приходят из парсера Ren'Py, они точные.
**Решение:** переименовать метку в `<full_id>__<suffix>`; межсценовый переход заменить на `return "<exit_id>"` + запись в `exits:` парного `scene.yaml`. Подробный разбор контракта — [12-scenes.md](12-scenes.md) и [05-renpy-development.md §4](05-renpy-development.md).
**Профилактика:** новые сцены создавайте `vn scene new <chapter> <slug>` — скелет уже соответствует контракту.

### `<scene.yaml>: exits.<id> -> <цель>: сцена chNN_sNNN не существует`

**Симптомы:** в release-главе — ошибка компиляции; в draft-главе — предупреждение плюс хвост `; draft: переход уйдёт на «сцена недоступна»`, и в генерате появляется `# TODO(draft): цель … ещё не написана` + `jump vn_scene_unavailable` (`tools/vn/src/vn/content/scenes.py:184-190,254-257`).
**Вероятная причина:** цель перехода объявлена, но сцены нет.
**Диагностика:** `vn content graph` — Mermaid-граф сцен. Осторожно: он сканирует **только** `content/chapters/`, главы из `packs/*/chapters/` в нём не видны (`tools/vn/src/vn/content/graph.py:15`) — это PARTIALLY IMPLEMENTED.
**Решение:** либо написать сцену, либо создать заглушку: `vn scene stub <chapter> <scene_id>` (`cli.py:484-496`).
**Профилактика:** держите главу в `status: draft`, пока граф не сомкнулся; на `release` те же расхождения станут ошибками.

### `<путь>: <место>: <сообщение> ` — документ не прошёл схему

**Симптомы:** ошибка формата `content/chapters/ch01_awakening/chapter.yaml: scene_order/2: 'sXXX' does not match …`.
**Вероятная причина:** документ валидируется против `tools/schemas/<name>@<N>.schema.json` по полю `schema:` (Draft 2020-12, `schemas.py:34-51`). В реестре 39 схем.
**Диагностика:**
```bash
ls tools/schemas/                      # какие схемы вообще есть
grep -n '"required"' tools/schemas/scene@1.schema.json
```
**Решение:** привести документ к схеме. Если поля действительно не хватает в схеме — новая схема заводится **новым файлом** `name@<N+1>.schema.json`, старая остаётся (норма G16); имя файла и `properties.schema.const` обязаны совпадать, иначе реестр не соберётся вовсе.
**Профилактика:** правьте схему и документы одним PR; `vn doctor` печатает `реестр схем: 39 схем` — если число упало, схема сломана.

### `.vncache/assets-manifest.json: <место>: <сообщение jsonschema>` — манифест ассетов не прошёл свою схему

**Симптомы:** `vn assets build` / `vn build` печатает ошибку с путём `.vncache/assets-manifest.json`; файл при этом всё равно записан.
**Вероятная причина:** схема `assets_manifest@1` **заведена** (`tools/schemas/assets_manifest@1.schema.json`, IMPLEMENTED с 2026-08-08), и манифест валидируется ею при каждой записи — `tools/vn/src/vn/assets/pipeline.py:441-450`. Прежнее нарушение G16 («id схемы эмитится, файла схемы нет») закрыто. Ошибка означает реальное расхождение писателя и схемы: чаще всего — новая ветка конвейера кладёт в `outputs` поле, которого схема не знает.
**Диагностика:**
```bash
ls tools/schemas/ | grep -i assets       # asset_src@1, assets_manifest@1
python -c "import json;d=json.load(open('.vncache/assets-manifest.json'));print(d['schema'],len(d['outputs']))"
```
**Решение:** привести эмиттер к схеме либо завести `assets_manifest@2` новым файлом (G16: имя файла = `properties.schema.const`, старая версия остаётся). Запись манифеста намеренно происходит **даже при ошибке схемы** — иначе следующая сборка потеряет точечную очистку осиротевших выходов.
**Профилактика:** новые декларации сначала получают схему, потом — эмиттер. У синтетических корней (тесты) каталога `tools/schemas/` нет, и проверка там просто не запускается — это ожидаемо, а не дыра.

### `build-bridge (renpy vn_analyze) упал: код N` + stdout/stderr

**Симптомы:** длинное сообщение с хвостами stdout и stderr движка; exit 1.
**Вероятная причина:** разбор авторских `.rpy` идёт **только** парсером Ren'Py из пиннованного SDK (норма G24): `renpy.exe <root> vn_analyze <out.json> <файлы…>` (`tools/vn/src/vn/content/analyze.py:57-66`, мост — `game/framework/00_core/050_build_bridge.rpy:98-144`). Падают обычно три вещи: не тот/битый SDK, синтаксическая ошибка в авторской `.rpy`, ошибка в самом `game/framework/**` (мост исполняется после `init`, то есть весь ваш framework-код тоже выполняется).
**Диагностика:** читать `stderr` — там ошибка парсера Ren'Py с номером строки. Родственные сообщения: `RENPY_SDK не установлен, а в content/ есть главы…`, `RENPY_SDK указывает на <путь>, но renpy.exe там нет` (`analyze.py:26-33`).
**Решение:** починить указанный файл; при подозрении на протухший кэш — `rm .vncache/analyze-*.json` (ключ кэша включает версию тулинга, содержимое моста и содержимое всех входных `.rpy`, `analyze.py:42-53`).
**Профилактика:** не пишите регексов по `.rpy` в обход моста — это запрещено архитектурно; таймаут вызова 300 с.

# 3. Ren'Py-рантайм

### Игра не стартует: экран «errors were detected in your script»

**Симптомы:** окно с текстом `I'm sorry, but errors were detected in your script.`; подробности — в `errors.txt` в корне репозитория. Реальный пример из этого репозитория (уже исправлен):
```
File "game/framework/20_ui/screens/history.rpy", line 42: 'ypadding' is not a keyword argument or valid child of the hbox statement.
    ypadding gui.sp_l - 6
Ren'Py Version: Ren'Py 8.5.3.26051504
```
**Вероятная причина:** ошибка на уровне скрипта/экранного языка. Класс ошибок «свойство не применимо к этому контейнеру»: `ypadding` валиден для `frame`/`window`, но не для `hbox`/`vbox` — вертикальный ритм в боксах задаётся `spacing`.
**Диагностика:** `cat errors.txt` — там файл, строка, символ и точная формулировка движка.
**Решение:** править указанный файл. В том конкретном случае вылечилось заменой на `spacing gui.sp_l - 6` (нынешний `game/framework/20_ui/screens/history.rpy:42`).
**Профилактика:** прогоняйте движковый линт — `"$RENPY_SDK/renpy.sh" . lint` (в CI это шаг `renpy lint по framework и генерату`, `ci.yml:72-73`). Он ловит такие вещи без запуска игры. Плюс `config.check_conflicting_properties = True` (`game/framework/00_core/001_boot.rpy:12`) ловит конфликтующие style-свойства на этапе анализа.

### Строки `[vn] snapshot: ch01.division пропущен (не-простой тип _Feature)` в `log.txt`

**Симптомы:** при старте в `log.txt` появляется десяток строк вида
```
[vn] snapshot: ch01.division пропущен (не-простой тип _Feature)
[vn] snapshot: g.basestring пропущен (не-простой тип tuple)
```
**Вероятная причина:** **это не ошибка.** `vn_state.snapshot()` обходит все не-`_` переменные управляемых stores и берёт только простые типы `str|int|float|bool|list|dict|None`; всё остальное логируется и пропускается (`game/framework/00_core/020_state.rpy:27-46`). `division`, `absolute_import`, `with_statement`, `print_function`, `unicode_literals` — это `__future__`-объекты, которые Ren'Py кладёт в каждый store, а `basestring` — кортеж совместимости. Ничего вашего они не затрагивают.
**Диагностика:** проверьте, что в списке нет **ваших** переменных. Если есть — вот это уже проблема: значение не поедет в сейв и будет невидимо для миграций.
**Решение:** для своих переменных — хранить простые типы. Списки/словари допустимы.
**Профилактика:** декларируйте состояние в `*.vars.yaml`; см. [07-backend.md §4](07-backend.md).

### Картинка не показывается / `ImageNotFound`

**Симптомы:** `show mira a school neutral` или `scene bg rooftop day` падает или показывает пустоту.
**Вероятная причина:** образы **не** автоопределяются по каталогу: `config.images_directory = None` (`001_boot.rpy:17`), а каталог `game/images` запрещён линтером (`tools/vn/src/vn/content/lint.py:50-53`). Все `image`/`layeredimage` эмитит компилятор в `game/generated/registry/images.gen.rpy` по факту **собранных** файлов в `game/assets/`. Нет ассета → нет `image`-стейтмента.
**Диагностика:**
```bash
grep -n "rooftop" game/generated/registry/images.gen.rpy
ls game/assets/bg/rooftop/
```
**Решение:** положить сырец по конвенции, `vn assets build`, затем `vn build` (компилятор перечитает дерево ассетов). Предупреждения компилятора вида `<char>: поза 'a' есть в assets, но не в matrix` / `у позы 'a' нет base@2.webp — поза не собрана` печатаются как раз для этого случая (`tools/vn/src/vn/content/images.py`).
**Профилактика:** порядок всегда «ассет → сборка ассетов → компиляция»; `vn dev` делает обе пересборки автоматически по watcher'у (`cli.py:243-262`).

### Спрайт предыдущей сцены протекает в следующую

**Симптомы:** персонаж из прошлой сцены остаётся на экране после перехода.
**Вероятная причина:** `scene` очищает только **свой** слой (`master`). Персонажи живут на отдельном слое `sprites` (`renpy.add_layer("sprites", above="master")`, `001_boot.rpy:22`), привязка тегов — сгенерированный `define config.tag_layer = {"mira": "sprites"}` (`game/generated/registry/images.gen.rpy:33`). Поэтому обвязка сцены явно вызывает `$ renpy.scene("sprites")` (`tools/vn/src/vn/content/scenes.py:204`, в генерате — `game/generated/scenes/ch01/ch01_s020.gen.rpy:10`).
**Диагностика:** посмотрите начало соответствующего `*.gen.rpy`: строки `$ vn.checkpoint(...)` → `$ renpy.scene("sprites")` → `scene bg …` должны быть на месте.
**Решение:** внутри одной сцены убирайте спрайты штатным `hide <tag>`. Если протекание видно **между** сценами — это баг компилятора, а не контента.
**Профилактика:** не добавляйте персонажные теги в `config.tag_layer` руками: слой должен существовать на момент выполнения `image`-стейтментов, иначе `show` падает в рантайме.

### Игра ушла на «сцена недоступна» (`vn_scene_unavailable`)

**Симптомы:** вместо следующей сцены — два системных сообщения и возврат в главное меню (`renpy.full_restart()`); в smoke-прогоне `RESULT.txt` содержит `FAIL: vn_scene_unavailable`.
**Вероятная причина:** обвязка сцены не нашла ветку для фактического `_return`: либо сцена вернула exit-id, которого нет в `exits:`, либо это draft-переход на ненаписанную цель (`# TODO(draft)`), либо `_return` вообще другой. Метка — `game/framework/00_core/030_flow.rpy:227-232`.
**Диагностика:** откройте `game/generated/scenes/<ch>/<full_id>.gen.rpy` — там перечислены все `if _return == "<exit>"`. Сверьте с `return "…"` в авторской `.rpy` и с `exits:` в `scene.yaml`.
**Решение:** дописать exit в `scene.yaml` (и цель), либо исправить строку в `return`. Компилятор ловит расхождение заранее: `return 'X' не объявлен в exits (…: [список])`.
**Профилактика:** `vn content lint` + `vn build` до запуска; для draft-глав помните, что несуществующая цель — только предупреждение.

### Крах в рантайме: crash-экран и отчёт

**Симптомы:** брендированный экран ошибки с кнопками «Откатиться назад» / «Попробовать продолжить» / «Закрыть игру»; в dev-режиме дополнительно скроллируемый трейсбек.
**Вероятная причина:** необработанное исключение. Обработчик пишет строку в `log.txt`, кладёт отчёт и возвращает `False`, чтобы движок показал наш `screen _exception` (`game/framework/00_core/070_crash.rpy:36-80`, присваивание — `:82`, экран — `game/framework/20_ui/screens/crash_screen.rpy`).
**Диагностика:** начинайте с `grep "\[vn\]" log.txt` — падение оставляет строку `[vn] unhandled exception: <Тип: сообщение>` (`070_crash.rpy:44-52`), она пишется первой и отдельным `try`, чтобы факт краха не пропал, даже если savedir недоступен. Дальше — `traceback.txt` в корне репозитория и отчёт в `<savedir>/crash/crash-YYYYMMDD-HHMMSS.txt`. В отчёте: build-id, флейвор, `config.version`, версия Ren'Py и **breadcrumbs** — последние до 40 авторских меток с временем (`070_crash.rpy:18-25,64-66`). Хранятся 10 последних отчётов.
**Решение:** по breadcrumbs понять, в какой сцене это случилось, воспроизвести через `vn test smoke --picks …`.
**Профилактика:** прежний дефект «два обработчика» **закрыт 2026-08-08** — IMPLEMENTED. Мёртвое присваивание `config.exception_handler` в `001_boot.rpy` удалено (на его месте комментарий-предупреждение, `001_boot.rpy:42-49`); единственный обработчик — `vn_crash_write_report` в `070_crash.rpy:82`. `config.exception_handler` — одно поле, побеждает последнее присваивание, поэтому **второй обработчик заводить нельзя ни при каких условиях**: он либо убьёт крэш-репортер, либо умрёт сам. Инвариант «присваивание ровно одно и именно там» стережёт тест `tools/vn/tests/test_crash_handler.py`.

### `viewport` со `scrollbars "vertical"` не рисует полосу

**Симптомы:** контент скроллится колесом, но полосы не видно.
**Вероятная причина:** в этом проекте полоса рисуется явными свойствами; без них у неё нет ни фона, ни бегунка.
**Диагностика:** сравните со рабочим образцом — `game/framework/20_ui/screens/history.rpy:32-37`:

```
scrollbars "vertical"
vscrollbar_unscrollable "hide"
vscrollbar_base_bar Solid(gui.panel_bg_deep)
vscrollbar_thumb Solid(gui.panel_border2)
vscrollbar_xsize 6
```
**Решение:** скопировать этот блок (второй живой пример — `game/framework/20_ui/screens/gallery.rpy:58-61`).
**Профилактика:** новые скроллируемые области делайте копипастой существующей — единство внешнего вида важнее изобретательности. Подробнее — [06-frontend.md](06-frontend.md).

### `viewport` съел весь экран

**Симптомы:** соседние элементы уехали или исчезли; вьюпорт растянулся на всё доступное место.
**Вероятная причина:** `viewport` без явных `xsize/ysize` забирает всё доступное пространство.
**Диагностика:** посмотрите, заданы ли размеры. В проекте они всегда явные: history — `xsize 1100`, `ysize 830` (`history.rpy:27-28`), галерея — `ysize 800` (`gallery.rpy:53`).
**Решение:** задать `xsize`/`ysize` (или `xysize`).
**Профилактика:** для проверки переполнений при длинных строках гоняйте псевдолокаль: `vn loc pseudo`, затем `vn test smoke --picks 0,0 --lang pseudo` (эта же комбинация есть в `nightly.yml:60`).

### Таймер/overlay-экран не тикает в главном меню

**Симптомы:** `timer` в экране, показанном из `label main_menu`, не срабатывает.
**Вероятная причина:** контекст главного меню отличается от игрового — overlay-экраны и таймеры там не тикают.
**Диагностика:** сравните с автопилотом: его `label main_menu` делает **один** вызов `vn_qa.autopilot_boot()` и сразу `return`, а overlay-экран `vn_autopilot` с `timer 0.6 … repeat True` начинает тикать уже после ухода в `label start` (`cli.py:1268-1282`).
**Решение:** переносить логику в игровой контекст либо выполнять её однократно, без таймера.
**Профилактика:** см. [05-renpy-development.md §10](05-renpy-development.md) и [06-frontend.md](06-frontend.md) — там этот класс граблей разобран для UI.

### Текст с голой `[` ломается или подставляет непонятное

**Симптомы:** в реплике вместо `[текст]` подставляется значение переменной, либо строка падает в рантайме.
**Вероятная причина:** `[` в тексте Ren'Py — интерполяция. Литеральная скобка экранируется как `[[` (и `{{` для фигурной).
**Диагностика:** валидатор переводов ловит это на импорте: `po/<lang>: <ctx>: незакрытая скобка [ или { (литеральная скобка эскейпится: [[ и {{)` (`tools/vn/src/vn/loc/po.py:305-317`).
**Решение:** экранировать. Псевдолокализация специально обрамляет строки как `[[…]` — голая `[` начала бы интерполяцию и уронила бы текст (`tools/vn/src/vn/loc/po.py:539-542`).
**Профилактика:** `vn build --check` вызывает `validate_translations` и падает на битой разметке до мержа (`cli.py:133-141`).

# 4. Ассеты

### Ассет не появился в `game/assets/`

**Симптомы:** файл положили, `vn assets build` отработал, выхода нет; либо в выводе `error: …`.
**Вероятная причина:** ассет не попал в discovery — не та конвенция пути/имени. Полная таблица трансформаций — [16-assets.md §2](16-assets.md), discovery — `tools/vn/src/vn/assets/pipeline.py:102-218`. Типовые сообщения:

| Сообщение | Причина |
|---|---|
| `<путь>: сегмент 'X' вне конвенции ^[a-z][a-z0-9_]*$ (naming.md)` | заглавные буквы, дефисы, пробелы, кириллица в имени |
| `<поза>: нет обязательного base.png` | у позы персонажа должен быть `base.png` |
| `<out>: два источника претендуют на один выход` | конфликт ручного `assets_src/png` и staging-нарезки PSD |
| `<путь>: не читается: …` | файл залочен (открыт в Photoshop) или его ест антивирус |
| `<путь>: трансформация упала: …` | битый PNG / ошибка ffmpeg |
| `assets_src/video_src/<путь>: видео кладутся в группу — video_src/<group>/<name>.<ext>` | видео без каталога-группы |

**Диагностика:** `vn assets validate` — конвенции, обязательные `base.png`, свежесть и ссылки контента разом.
**Решение:** переименовать/переложить по конвенции и пересобрать.
**Профилактика:** `../conventions/naming.md`; для спрайтов — `vn dev`, он пересобирает по watcher'у в `draft`-профиле.

### Осиротевшие ассеты не удаляются

**Симптомы:** сырец удалили, а `game/assets/<...>` остался; счётчик `0 осиротевших удалено`.
**Вероятная причина:** удаление идёт **только** по диффу манифестов: кандидаты = `old_manifest − seen_outputs` (`tools/vn/src/vn/assets/pipeline.py:416-433`). Манифест лежит в `.vncache/assets-manifest.json` и **не в git** (`.gitignore:21`). Потеряли `.vncache` — удаление отключилось навсегда для уже лежащих файлов.
**Диагностика:**
```bash
python -c "import json;d=json.load(open('.vncache/assets-manifest.json'));print(len(d['outputs']))"
ls game/assets/**  # сравнить
```
**Решение:** `rm -rf game/assets` и полная пересборка `vn assets build` — единственный надёжный способ, раз манифест утерян.
**Профилактика:** не чистите `.vncache/` выборочно; если чистите — чистите вместе с `game/assets/`.

### Кэш трансформаций распух

**Симптомы:** `.vncache/assets/` занимает гигабайты.
**Вероятная причина:** кэш контентно-адресуемый и растёт неограниченно: каждая правка сырца оставляет прошлый блоб (`cli.py:748-751`).
**Диагностика:** `vn assets cache` — печатает размер; `vn assets cache --dry-run` — сколько удалится.
**Решение:** `vn assets cache --gc` — mark & sweep от текущего манифеста сборки (`tools/vn/src/vn/assets/pipeline.py:458-491`).
**Профилактика:** GC после крупных итераций по арту. Осторожно: GC считает «живыми» только блобы, упомянутые в текущем манифесте — после `--gc` пересборка на другом профиле пойдёт с нуля.

### В галерее нет превью

**Симптомы:** ячейки галереи показывают полноразмерный CG или пусто.
**Вероятная причина:** превью — отдельная трансформация `png2webp_cg_thumb`, дающая `<name>.thumb.webp` (длинная сторона 512, quality 80, `tools/vn/src/vn/assets/pipeline.py:157,228-231`). Она порождается **только** для источников из `assets_src/png/cg/**`.
**Диагностика:** `ls game/assets/cg/**/*.thumb.webp`.
**Решение:** положить CG именно в `assets_src/png/cg/…` и пересобрать.
**Профилактика:** см. [15-gallery.md](15-gallery.md) — там разобрано, как галерея резолвит `thumb` и что делать, если его нет.

### Положили `.ogg`, а `game/assets/audio/` не появилось

**Симптомы:** файл лежит в `assets_src/`, `vn assets build` его не видит либо видит, но сцена всё равно падает на `music`.
**Вероятная причина:** ветка `copy_audio` **живая с 2026-08-08** (IMPLEMENTED) и читает нормативную зону `assets_src/audio_stems/{bgm,amb,sfx}/*.ogg` (`tools/vn/src/vn/assets/pipeline.py:159-170`); каталоги заведены, выход — `game/assets/audio/<kind>/<id>.ogg`. Прежний дефект «код ждал несуществующий `assets_src/audio/`» закрыт, ветку стережёт тест `test_assets.py:test_audio_stems_branch_copies_ogg`. Значит остаются две настоящие причины: файл лежит не в `audio_stems/<kind>/` (или расширение не `.ogg`), либо имя не проходит проверку слага (`^[a-z][a-z0-9_]*$`) — тогда в отчёте сборки будет строка про `assets_src/audio_stems/<kind>/<файл>`.
**Диагностика:**
```bash
ls assets_src/audio_stems/{bgm,amb,sfx}      # зона на месте; сюда кладут .ogg
ls game/assets/audio/                        # выход конвейера
grep -n "tracks" content/audio/bgm.yaml      # объявлен ли логический id
```
**Решение:** положить файл в `assets_src/audio_stems/<kind>/<slug>.ogg` и **обязательно объявить трек** в `content/audio/<kind>.yaml` — иначе компилятор ответит `<scene.yaml>: music <...>: трек 'X' не объявлен в content/audio/`.
**Профилактика:** знайте, что закрыто **не всё**. Незакрытые остатки на сегодня: `content/audio/{bgm,sfx}.yaml` по-прежнему `tracks: {}` и в репозитории **ноль `.ogg`** — тракт ни разу не гонялся на реальных данных; поля `loop`, `loop_start`, `volume` схемы `audio@1` валидируются, но эмиттером **игнорируются**; нормализации громкости (loudnorm) нет вовсе. См. [23-audio.md](23-audio.md).

### `push без лока запрещён (G14)`

**Симптомы:** `error: <rel>: push без лока запрещён (G14) — возьмите: vn assets lock <rel>`, затем `ошибка: assets push: N ошибок`.
**Вероятная причина:** норма G14: PSD и подобные бинари не мержатся, поэтому заливка требует явного лока (`tools/vn/src/vn/assets/storage.py:179-183`).
**Диагностика:** `vn assets status` — версии, локальное состояние, держатели локов. На чистом репозитории ответ будет `манифестов нет — сырцы ещё не пушились (vn assets lock + push)`: хранилище `~/vn-assets-store` **никогда не использовалось** в этом чекауте.
**Решение:** `vn assets lock <путь относительно assets_src/>`, затем `vn assets push <файл>`.
**Профилактика:** ленивый путь совпадает с правильным: `vn assets pull --edit` забирает файл и сразу берёт лок.

### Чужой лок

**Симптомы:** `error: <rel>: залочен «Имя» — push отклонён (G14)` или `<rel>: уже залочен «Имя»`; при снятии — `<rel>: лок держит «Имя» (снять: --force, эскалация на лида)`.
**Вероятная причина:** лок — файл `<base>/locks/<rel>.lock` с полями `{by, at}`; владелец берётся из `git config user.name`, иначе имя ОС-пользователя (`tools/vn/src/vn/assets/storage.py:46-54,99-118`).
**Диагностика:** `vn assets status` покажет `, лок: <имя>`; сам файл читается глазами.
**Решение:** договориться с держателем. Аварийно — `vn assets lock <rel> --release --force` (это эскалация на лида, не рутина).
**Профилактика:** знайте ограничения реализации — **PARTIALLY IMPLEMENTED**: TTL у локов нет, автоснятия нет, взятие лока не атомарно, уведомлений нет. Долгие локи — вопрос дисциплины, а не тулинга.

# 5. Видео и ffmpeg

### `assets_src/video_src: есть видео-сырцы, но ffmpeg/ffprobe не найдены (vn pipeline doctor) — видео-трек не собирается`

**Симптомы:** `vn assets build` краснеет ровно этой строкой; остальные ветки не собираются, потому что discovery выходит сразу (`tools/vn/src/vn/assets/pipeline.py:182-186`).
**Вероятная причина:** `ffmpeg`/`ffprobe` не в `PATH`. Поиск: сначала env-переопределение `VN_FFMPEG`/`VN_FFPROBE`, и если оно **битое — фоллбека на PATH нет** (`tools/vn/src/vn/pipeline.py:42-59`, это другой `pipeline.py` — не ассетный).
**Диагностика:** `vn pipeline doctor` — строки `ffmpeg <версия> (<путь>)`, `VP9-энкодер (libvpx-vp9)`, `ffprobe`.
**Решение:** `winget install Gyan.FFmpeg` (полная сборка, с libvpx-vp9) либо задать `VN_FFMPEG`/`VN_FFPROBE` на существующие файлы.
**Профилактика:** проверяйте не только наличие ffmpeg, но и `PASS VP9-энкодер` — сборка без libvpx даёт `FAIL` с рецептом `сборка ffmpeg без libvpx — поставьте полную`. В CI дыра закрыта 2026-08-08: `ffmpeg` ставится во **всех четырёх** GitHub-workflow (`ci.yml:49`, `release.yml:45`, `nightly.yml:32`, `canary.yml:33`) — раньше его не было в `nightly` и `canary`, и оба ночных прогона обязаны были краснеть на `assets_src/video_src/demo/ambient.mp4`. Наличие проверяет тест `test_ci_config.py`. В `.gitlab-ci.yml` ffmpeg по-прежнему **нет** — видео-трек там не собирается.

### `.webm` не играет в Ren'Py (а в плеере играет)

**Симптомы:** чёрный прямоугольник или ничего; в плеере файл открывается нормально.
**Вероятная причина:** вне канона ADR-0006. Ren'Py-совместимая комбинация в этом проекте зашита жёстко: контейнер WebM + `libvpx-vp9` + `yuv420p` (`tools/vn/src/vn/assets/video.py:1-15,101-111`).
**Диагностика:**
```bash
vn assets video validate                 # все game/assets/mov/**
vn assets video inspect game/assets/mov/demo/ambient.webm
```
Валидатор скажет точно: `контейнер 'X', ожидается webm` / `кодек 'X', ожидается vp9 (Ren'Py-канон ADR-0006)` / `pix_fmt 'X', ожидается yuv420p` / `нечётные размеры WxH` / `длительность 0.1 c — файл битый/пустой` (`tools/vn/src/vn/assets/video.py:212-236`). Успешная строка выглядит так (единственный собранный луп репозитория):
```
 ✓ ambient.webm: 256x144 24.0fps 2.0c, 0.0 МБ, стык 2.1
```
**Решение:** пересобрать через конвейер: `vn assets video build`. Ручной ffmpeg-энкод в обход конвейера не даст meta-сайдкар и не попадёт в манифест.
**Профилактика:** не подкладывайте `.webm` в `game/assets/mov/` руками — это производная зона; кладите мастер в `assets_src/video_src/<group>/<name>.mp4`.

### Неверный `pix_fmt` (и почему альфа — ловушка)

**Симптомы:** `error: <name>: pix_fmt 'yuv444p', ожидается yuv420p`; либо предупреждение `альфа-канал (yuva420p) — в Ren'Py прозрачность через side-mask, проверьте воспроизведение отдельно`.
**Вероятная причина:** PNG-секвенции и ProRes-мастера толкают libvpx в `yuv444p`/`yuv422p`/10 бит — всё это кодек принимает молча. Ren'Py при этом не аппаратно-ускоряет YUV444 и **не декодирует альфу вовсе** (ресёрч `research/ffmpeg.md`, раздел про видеоподсистему движка).
**Диагностика:** `vn assets video inspect <файл>` — строка `pix_fmt`.
**Решение:** пересобрать конвейером — он всегда ставит `-pix_fmt yuv420p` явно (`tools/vn/src/vn/assets/video.py:105`). Для альфы штатного пути нет: side-mask/`mask=` — **NOT IMPLEMENTED** в этом конвейере.
**Профилактика:** прозрачность в видео пока не используем; если понадобится — это отдельная задача с бюджетом (side-mask удваивает ширину кадра).

### `стык лупа заметен (RMS N > 18.0) — первый/последний кадры расходятся`

**Симптомы:** предупреждение при сборке/валидации; визуально — рывок в момент зацикливания.
**Вероятная причина:** метрика `loop_seam` — RMS-разница первого и последнего кадров, приведённых к 64×64 в градациях серого (`tools/vn/src/vn/assets/video.py:173-197`); порог `LOOP_SEAM_WARN = 18.0`.
**Диагностика:** значение печатается в успешной строке валидации (` ✓ ambient.webm: 1280x720 30fps 6.0c, 1.2 МБ, стык 2.1`) и хранится в сайдкаре — в репозитории живой пример: `game/assets/mov/demo/ambient.webm.meta.json` с `loop_seam: 2.1`.
**Решение:** генерировать клип так, чтобы последний кадр совпадал с первым (I2V loop-воркфлоу), либо честно объявить `loop: false` в сайдкаре `<name>.video.yaml`. Отдельная классическая ловушка: не кодируйте N+1 кадров с повтором нулевого — получите однокадровый рывок каждый цикл.
**Профилактика:** это предупреждение, а не ошибка — сборка не покраснеет. Смотрите на него глазами; в релизном гейте оно всплывёт как `WARN видео: N предупреждений`.

### Превышен `video_file_mb` / `video_total_mb`

**Симптомы:** `error: <name>: 47.3 МБ > бюджета 40 МБ на файл (project.yaml: budgets.video_file_mb)`; либо `бюджет: game/assets/mov: 320.0 МБ > бюджета 300 МБ` + `ошибка: бюджеты G19 превышены (project.yaml: budgets)`.
**Вероятная причина:** бюджеты объявлены в `project.yaml:6-11`: `assets_total_mb 500`, `generated_total_kb 2048`, `video_total_mb 300`, `video_file_mb 40`, `cold_start_s 30`. Проверка одна и та же и в `vn build`, и в релизном гейте (`release.py:29-54`); файловый бюджет дополнительно проверяется прямо при сборке видео.
**Диагностика:** `du -sh game/assets/mov` и `vn assets video validate`.
**Решение:** поднять `crf` (production-дефолт 30, `tools/vn/src/vn/assets/video.py:93`), сократить длительность, снизить `max_height` в сайдкаре. Бюджет — не константа мироздания, но его правка идёт отдельным PR.
**Профилактика:** `cold_start_s` — единственный бюджет, который проверяется **только** внутри `vn test smoke` (`cli.py:1386-1392`), остальные — в каждой сборке.

### Sidecar `<name>.video.yaml` не подхватился

**Симптомы:** поменяли `crf`/`fps`/`loop` — выход не изменился; либо изменения применились, но валидация ругается на аудиодорожку.
**Вероятная причина:** сайдкар входит в хэш источника (`src_hash = blake3(байты видео + 0x00 + байты сайдкара)`, `tools/vn/src/vn/assets/pipeline.py:299-303`), так что правка обязана инвалидировать кэш — если не инвалидировала, вы правите не тот файл (имя должно быть ровно `<name>.video.yaml` рядом с мастером). Отдельный факт: `video_src@1` на пути сборки **не форсируется** — `load_opts(sidecar)` вызывается без реестра схем (`tools/vn/src/vn/assets/video.py:64` против `tools/vn/src/vn/assets/pipeline.py:197`), поэтому опечатка в ключе просто игнорируется, а схему проверяет только `vn content lint`.
**Диагностика:**
```bash
ls assets_src/video_src/demo/                 # ambient.mp4 + ambient.video.yaml
vn content lint                                # схема сайдкара проверяется здесь
vn assets video inspect game/assets/mov/demo/ambient.webm   # meta + провенанс
```
**Решение:** привести имя и ключи к схеме `video_src@1`; поддерживаемые ключи — `loop`, `keep_audio`, `fps`, `max_height`, `crf` (`tools/vn/src/vn/assets/video.py:33-39`).
**Профилактика:** после правки сайдкара запускайте `vn assets video build` и смотрите, что файл действительно пересобрался (`N собрано`, а не `N актуально`). Ошибка `аудиодорожка при keep_audio: false — пересоберите` означает ровно это: выход старый.

# 6. Локализация

### На экране виден сырой ключ вроде `ui.gallery.locked`

**Симптомы:** вместо текста показывается сам идентификатор.
**Вероятная причина:** `vn_loc.t(key)` возвращает **сам ключ**, если его нет ни в `VN_STRINGS`, ни в переводе (`game/framework/00_core/040_localization.rpy:151-157`). То есть ключ на экране = ключа нет в `content/ui/strings.yaml` (сейчас там 95 строк) либо генерат не пересобран.
**Диагностика:**
```bash
grep -n "ui.gallery.locked" content/ui/strings.yaml
grep -rn "VN_STRINGS" game/generated/registry/ | head
```
**Решение:** добавить ключ в `content/ui/strings.yaml`, затем `vn build`. Потом — `vn loc extract` и перевод.
**Профилактика:** в экранах **только** ключи через `vn_loc.t()`; литерал в `.rpy` не попадёт в PO-экстракцию и останется непереведённым (комментарий в шапке `content/ui/strings.yaml`).

### `vn loc keys --check` красный

**Симптомы:** строки `расхождение: <файл>:<строка>: say без id (будет chNN_sNNN_0007)` / `menu без маркера (будет chNN_sNNN_m002)` / `loc/ledger/chNN.json устарел (тексты/структура разошлись со сценами)`, затем `ошибка: loc keys --check: есть строки без id или устаревший ledger — выполните vn loc keys`.
**Вероятная причина:** после правки реплик id и ledger не обновлены. `--check` дополнительно сверяет **тексты** в ledger: правка текста не меняет id, но обязана доехать до `loc/ledger/chNN.json`, иначе переводчики получают старый текст (`tools/vn/src/vn/loc/keys.py:178-194`).
**Диагностика:** сам вывод; ledger лежит в `loc/ledger/`.
**Решение:** `vn loc keys` — допишет `id …` и `$ vn_menu = "…"` в авторские `.rpy` и перегенерирует ledger. Затем `vn loc extract`.
**Профилактика:** это отдельный шаг CI (`ci.yml:69-70`), так что локально зелёный build не спасёт. Не удаляйте `id …` из авторских `.rpy` «для чистоты».

### `verify роунд-трипа не прошла — файлы ОТКАЧЕНЫ`

**Симптомы:** `vn loc keys` падает с этим текстом и списком проблем вида `<файл>: после правки остались say без id (say с хвостовым комментарием?)`.
**Вероятная причина:** дописанный `id` приклеился внутрь хвостового комментария и перестал быть частью стейтмента. Инструмент перечитывает изменённые файлы парсером и при провале **полностью откатывает** правки (`tools/vn/src/vn/loc/keys.py:198-219`).
**Диагностика:** искать в указанной сцене строки `say` с `#` в конце.
**Решение:** убрать хвостовой комментарий (или перенести его на отдельную строку) и повторить.
**Профилактика:** комментарии в авторских сценах — на отдельных строках.

### Покрытие ниже гейта: релиз краснеет на переводах

**Симптомы:** в `vn release validate --flavor …` строка `FAIL покрытие переводов: ниже порога 98% — en 91%`.
**Вероятная причина:** порог `release_coverage_min: 0.98` в `loc/loc.yaml`; форсируется **только** в релизном гейте (`release.py:408-434`). Синтетические пакеты (`pseudo`) исключаются по флагу `synthetic` в `game/tl/<lang>/language.json`.
**Диагностика:** `vn loc report` — `de: 115/115 (100%), fuzzy: 0` по каждому языку.
**Решение:** дособрать переводы или временно убрать язык из поставки. Флагов `vn loc report --gate/--format` **не существует** (NOT IMPLEMENTED) — гейт живёт только в релизе.
**Профилактика:** `vn loc report` в ежедневной проверке; `fuzzy` в поставку не идут — они молча выпадают из `game/tl` (`tools/vn/src/vn/loc/po.py:384-386`).

### Перевод не появился в игре

**Симптомы:** PO переведён, а в игре исходный язык.
**Вероятная причина, по убыванию частоты:** (1) не запускали `vn loc import` — `game/tl/` это производная зона, её нет в git; (2) запись помечена `fuzzy` и потому не поставляется; (3) язык вообще не зарегистрирован в движке.
**Диагностика:**
```bash
ls game/tl/                       # каталоги языков вообще есть?
grep -c "^translate" game/tl/en/dialogue_ch01.rpy
vn loc report
```
**Решение:** `vn loc import` (его же неявно делает `vn build` в конце, `cli.py:151`). Снять `fuzzy` в PO после проверки перевода.
**Профилактика:** язык существует ровно тогда, когда есть `loc/po/<code>/language.yaml` — списка языков в коде нет (ADR-0005). Подробности — [14-localization.md](14-localization.md).

### `vn test smoke --lang xx` → `языка 'xx' нет в game/tl/`

**Симптомы:** `ошибка: языка 'xx' нет в game/tl/ — выполните vn loc import (change_language молча показал бы исходный язык — ложно-зелёный прогон)`.
**Вероятная причина:** защита от ложно-зелёного теста: `renpy.change_language` на несуществующий язык не падает, а просто показывает исходный (`cli.py:1365-1367`).
**Диагностика:** `ls game/tl/`.
**Решение:** `vn loc import`. Для прогона на исходном языке передавайте его код — CLI сам подменит его на маркер `@source` и сбросит язык в `None` (`cli.py:1354-1364`).
**Профилактика:** в nightly матрица уже покрывает `en` и `pseudo` (`nightly.yml:57-60`).

### Английские `layout.*`-строки в диалогах подтверждения

**Симптомы:** в окне «Вы уверены?» часть текста на английском.
**Вероятная причина:** движковые строки `layout.*` наш конвейер переводов не покрывает — он основан на id-lookup (`VN_STRINGS`/`vn_loc.t`), а не на `translate strings`.
**Диагностика:** `grep -n "layout" game/framework/20_ui/screens/core_screens.rpy` — комментарий на `:109`.
**Решение:** передавать в `Confirm(...)` свой текст ключом: так и сделано — `Confirm(vn_loc.t("ui.confirm.quit"), Quit(confirm=False))` (`core_screens.rpy:111`), ключи объявлены в `content/ui/strings.yaml:111` и ниже.
**Профилактика:** любой новый движковый диалог — со своим ключом из `strings.yaml`, иначе он останется английским при любом языке.

### Переключение языка «не применилось»

**Симптомы:** язык сменили, но подсистема (шрифты, озвучка, кэш) осталась на старом.
**Вероятная причина:** `config.change_language_callbacks` в Ren'Py 8.5 — **мёртвый список**, движок его не зовёт. Живой хук — `config.language_callbacks[lang]`, регистрируемый на каждый обнаруженный язык (`game/framework/00_core/040_localization.rpy:19-23,47-51`).
**Диагностика:** в `log.txt` при смене языка должна появиться строка `[vn] language -> <code>` (`040_localization.rpy:121-123`). Нет строки — ваш путь смены языка идёт мимо реестра.
**Решение:** подписываться через `vn_lang.subscribe(fn)`; менять язык через `vn_lang.set(code)` или screen-action `vn_lang.action(code)`.
**Профилактика:** экранам подписка не нужна — они переоцениваются сами. Подписчики обязаны быть идемпотентными: уведомление приходит и при старте, и при полном рестарте.

# 7. Сейвы

### Сейв не грузится / игра ведёт себя после загрузки странно

**Симптомы:** загрузка проходит, но состояние не то; или слот вообще не виден.
**Вероятная причина:** несколько разных: сейв сделан на другой линии `.rpyc` (statement-имена), схема состояния изменилась без миграции, переменная не была в снапшоте.
**Диагностика:**
```bash
vn save check                 # оффлайн: структура слота, JSON-метаданные, версия схемы
vn save corpus                # загрузка фикстур в реальной игре + миграции + автопилот
```
`vn save check` печатает по каждой фикстуре ` ✓ <имя>: schema N, версия X, сцена chNN_sNNN` — эти поля кладёт в JSON-заголовок слота `_vn_save_json` (`game/framework/00_core/001_boot.rpy:31-36`), их можно читать без unpickle.
**Решение:** зависит от причины — см. три следующие записи.
**Профилактика:** держите корпус: `vn save corpus --add <имя>` создаёт фикстуру и одновременно снимает линию `.rpyc` в `ci/fixtures/rpyc-line/`.

### Модальный «confirm» на чужом сейве

**Симптомы:** при загрузке сейва, принесённого с другой машины, движок показывает подтверждение.
**Вероятная причина:** Ren'Py 8 подписывает сейвы per-machine токеном; сейв с чужой подписью показывается как потенциально небезопасный.
**Диагностика:** сейв, созданный локально, грузится молча; принесённый — с диалогом.
**Решение:** подтвердить диалог (для своих же QA-сейвов это нормально). В автоматике проблему обходят иначе: корпус кладёт фикстуру в изолированный `--savedir` и грузит её по слоту `1-1` (`cli.py:1224-1234`), поэтому вопрос доверия не встаёт.
**Профилактика:** не гоняйте пользовательские сейвы между машинами вручную; для регрессий используйте фикстуры корпуса.

### Миграция не отработала

**Симптомы:** после загрузки старого сейва схема осталась прежней; в `log.txt` — `[vn] migrations incomplete: 1 -> 1 (target 2)` или `[vn] migration chain gap: 1 -> 3`.
**Вероятная причина:** цепочка `vn_state.MIGRATIONS` пуста или в ней дыра. Раннер применяет только строго возрастающие номера и повышает `vn_save_schema` **до фактически применённой** миграции, а не до целевой (`game/framework/00_core/020_state.rpy:60-107`). Генерат миграций — `game/generated/state/migrations.gen.rpy`.
**Диагностика:**
```bash
cat content/migrations/registry.yaml       # сейчас: зарезервирован номер 2 (route_prologue)
cat game/generated/state/migrations.gen.rpy
grep -n "migration" log.txt
```
**Решение:** дописать недостающую миграцию, зарезервировав номер в `content/migrations/registry.yaml` тем же PR (норма G5).
**Профилактика:** миграции исполняются **только** в `label after_load` — контракт G5: `config.after_load_callbacks` пригоден лишь для чистой валидации без переходов. Внешнего тулинга (`vn save migrate`, `vn migrate`) нет — это заглушки фаз 3 и 2.

### `save corpus` красный

**Симптомы:** ` ✗ <фикстура>: <вердикт>; schema после загрузки: N (цель M)`, затем хвост `traceback.txt` в красном и `ошибка: save corpus: N фикстур не прошли`.
**Вероятная причина:** прогон считается успешным только при трёх условиях сразу: не было таймаута, `RESULT.txt` начинается с `OK`, и `state.json` показывает схему, равную `project.yaml: save_schema` (`cli.py:1243-1248`).
**Диагностика:** артефакты прогона лежат в `.vncache/corpus/`: `RESULT.txt`, `state.json`, `gallery.json`, скриншоты. Плюс `traceback.txt` в корне.
**Решение:** по вердикту. `FAIL: vn_scene_unavailable` — сломан граф переходов; расхождение схем — не отработала миграция; таймаут — игра зависла (лимит по умолчанию 180 с, `--timeout`).
**Профилактика:** с 2026-08-08 корпус **действительно проверяет миграции** (IMPLEMENTED): фикстур две — `ci/fixtures/saves/schema2-demo.save` (на текущей схеме) и `ci/fixtures/saves/schema1-demo.save` (`vn_save_schema=1`, сцена `ch01_s010`). На второй прогон печатает `schema после загрузки: 2 (цель 2)`, а в `log.txt` появляется строка `[vn] migration 0002` — то есть цепочка исполняется в реальной игре, а не проверяется на бумаге. Знайте оставшийся предел: обязательные классы фикстур из `ARCHITECTURE.md:3681` (сейв внутри переименованной сцены, «грязный» call-стек, релиз N−1, DLC-контент без DLC) по-прежнему не заведены, и джобы `rpyc-compat` нет.

### `save_schema` забыли бампнуть

**Симптомы:** старые сейвы грузятся, но часть состояния «съехала»; корпус зелёный, потому что сравнивает с тем же (не поднятым) числом.
**Вероятная причина:** несовместимое изменение переменных без бампа `project.yaml:3 save_schema` (сейчас `2`).
**Диагностика:** сравните набор переменных в `content/**/vars.yaml` с тем, что было на прошлом релизе (`git log -p` по этим файлам), и с `game/generated/state/snapshot.gen.rpy`.
**Решение:** поднять `save_schema` и написать миграцию с этим номером; номер зарезервировать в `content/migrations/registry.yaml`.
**Профилактика:** отдельный механизм ловит другое — исчезновение выпущенных id (`content/registry/id_registry.json`, G7). Но он сейчас **инертен**: все массивы пусты, потому что `ch01` в статусе `draft`, а штампуются только `release`-главы (`release.py:69-121`). Не рассчитывайте на него как на защиту.

# 8. Сборка релиза и CI

### `ошибка: release validate --flavor <X>: есть FAIL`

**Симптомы:** таблица строк `PASS/WARN/FAIL`, затем эта ошибка.
**Вероятная причина:** гейт — агрегатор существующих проверок, **своих правил у него нет** (`release.py:276-481`). Всего в коде 19 проверок, но часть условная (VaM/Sims4/лицензии печатаются только при наличии деклараций, покрытие — только при заданном пороге), поэтому на текущем дереве строк 16. Частые FAIL:

| Строка гейта | Что означает |
|---|---|
| `project.yaml: <ошибки схемы>` | `project.yaml` не проходит `project@1` |
| `флейвор 'X' не описан в project.yaml (есть: patron, public)` | опечатка во `--flavor`; гейт после этого сразу выходит |
| `пак <id>: нет packs/<id>/manifest.yaml` | флейвор ссылается на несуществующий пак |
| `lint: N ошибок, M предупреждений` | чинить как в разделе 2 |
| `шрифты UI: … УКАЗАТЕЛИ LFS` | чекаут без git-lfs |
| `ассеты: N ошибок, M несвежих (vn build)` | пересобрать |
| `видео: N ошибок — <первая>` | см. раздел 5 |
| `генерат: N несвежих (vn build)` | пересобрать |
| `бюджеты G19: <список>` | превышение размеров |
| `провенанс: …` / `DAZ-декларации: …` / `VaM-…` / `Sims4-…` | битые декларации в `assets_src/**` |
| `покрытие переводов: ниже порога 98% — …` | см. раздел 6 |
| `лицензии ассетов: N нарушений` | ассет не разрешён в коммерческой игре или в NSFW |
| `сырцы изменены, но не запушены (N)` | `vn assets push` |
| `сейв-корпус: N фикстур` | не FAIL, а информационная строка: PASS при непустом корпусе, WARN при пустом. Сейчас — `PASS сейв-корпус: 2 фикстур` |

**Диагностика:** `vn release validate --flavor public` (и `--flavor patron`) — печатает всё разом, ничего не пишет.
**Решение:** по строке. `WARN` не блокирует.
**Профилактика:** `vn release build` намеренно запускает `vn build` **до** гейта (`cli.py:1526-1530`), иначе в свежем чекауте CI «генерат не свеж» валил бы каждый релиз.

### Тег не совпал с версией

**Симптомы:** в GitHub Actions джоба падает с `::error::тег v0.1.3 != project.yaml version 0.1.4 — бампните версию или тег`.
**Вероятная причина:** явная проверка в `release.yml:47-54`.
**Диагностика:** `grep ^version project.yaml` и `git tag --points-at HEAD`.
**Решение:** привести в соответствие: либо бампнуть `project.yaml:2`, либо перевесить тег.
**Профилактика:** релиз-коммит меняет `project.yaml` и создаёт тег вместе. Смежная проверка мягкая: гейт даёт `WARN release-manifest: версия X != Y — прогоните vn release changelog`.

### Дистрибутив тащит лишнее / не исключил NSFW

**Симптомы:** в public-сборке лежат NSFW-ассеты; либо в `build-info.json` пустой `"exclude": []`.
**Вероятная причина:** исключения считаются от **фактических каталогов**: для каждой категории в `game/assets/<cat>/` проверяется наличие подкаталога `nsfw/` (`release.py:192-203`). Сейчас категорий пять (`bg cg mov spr ui`) и ни в одной нет `nsfw/`, поэтому оба уже собранных `build/dist/0.1.0-{public,patron}/build-info.json` несут `"exclude": []` — это корректный результат, а не баг.
**Диагностика:** `ls game/assets/*/nsfw` и `cat build/dist/*/build-info.json`.
**Решение:** класть взрослый контент строго в `nsfw/`-подпапку своей категории (`assets/cg/nsfw/**`, `assets/mov/nsfw/**`).
**Профилактика:** знайте, что **не** гейтится: список `packs` флейвора ни на что не влияет (`VN_PACKS` перечисляет все паки), `early_content` пишется и нигде не читается, провайдер владения паками не установлен и `owned()` всегда True. Работают только `nsfw`, `watermark` и `patron_tag` (`game/framework/00_core/060_build_info.rpy:40,42-45`, `20_ui/screens/build_overlay.rpy`). Поле называется именно `patron_tag`, а не `patron_token`: с ADR-0011 наружу уходит `blake2s(токен, digest_size=4, person=b"vnpatron")` — 8 hex-символов, — а сам токен в дистрибутив не попадает. Подробности — [30-packs-and-dlc.md](30-packs-and-dlc.md).

### `ошибка: pack build: у пака '<id>' объявлены главы (chNN), но в game/generated/scenes/ нет ни одной их скомпилированной сцены — сначала vn build`

**Симптомы:** `vn pack build <id>` падает с exit 1, `build/packs/<id>.zip` **не создан**.
**Вероятная причина:** в `packs/<id>/chapters/` есть каталоги глав, а генерата для них нет — типично «забыли `vn build`» либо главу переименовали и `game/generated/scenes/<ch>/` опустел. Охранник считает сцены **отдельно** от манифеста (`cli.py:1620-1626`) и падает **до** открытия архива — иначе неполный zip из одного манифеста уже лежал бы в `build/packs/` и мог уехать в депот. До 2026-08-08 счётчик был общий с манифестом, проверка была недостижима, и команда печатала `OK` на пустом паке — теперь этого не бывает, инвариант закрыт тестом `test_release.py:149-159`.
**Диагностика:**
```bash
ls packs/<id>/chapters/            # какие главы объявлены
ls game/generated/scenes/          # для каких есть генерат
```
**Решение:** `vn build`, затем повторить `vn pack build <id>`.
**Профилактика:** пак **без** глав — это нормально: `packs/nsfw` возит только ассеты, собирается штатно и печатает `warning: пак 'nsfw' не объявляет глав (packs/nsfw/chapters/ пуст) — в архиве только манифест` (`cli.py:1635-1637`). Предупреждение не глушить: архив из одного файла иначе читается как поломка сборки. Остаток честного ограничения: охранник требует «хоть одну сцену на весь пак», а не по каждой объявленной главе — пак из двух глав, где скомпилирована одна, пройдёт.

### `ошибка: rpyc-перенос: кэш X есть, но не восстановлено ни одного .rpyc — save-совместимость под угрозой (G6), сборка остановлена`

**Симптомы:** `vn package` / `vn release build` падает этой строкой.
**Вероятная причина:** кэш прошлого релиза в `build/rpyc-cache/<version>/` есть, но ни один `.rpyc` не лёг на парный `.rpy` — раскладка разошлась (`cli.py:313-332`). Statement-имена в `.rpyc` — основа save-совместимости.
**Диагностика:** `ls build/rpyc-cache/` и сравнить дерево с `game/`.
**Решение:** если это первый релиз в новой раскладке — удалите устаревший кэш осознанно (тогда будет `rpyc-перенос: кэша прошлых релизов нет (первый релиз)`), понимая, что старые сейвы могут не подхватить имена.
**Профилактика:** в CI кэш восстанавливается через `actions/cache` **отдельно на флейвор** (`release.yml:71-76`), хотя локальный кэш `build/rpyc-cache/<version>/` ключуется **только по версии**, без флейвора. Расхождение существует — держите его в голове.

### LFS в CI

**Симптомы:** джоба падает на шрифтах или игра из артефакта не стартует.
**Вероятная причина:** чекаут без `lfs: true`.
**Диагностика:** в логе шага checkout нет скачивания LFS-объектов; гейт даёт `FAIL шрифты UI`.
**Решение:** во всех четырёх workflow чекаут уже с `with: {lfs: true}` — если добавляете новый, скопируйте это.
**Профилактика:** тот же детектор работает локально в `vn doctor`, так что проблему видно до пуша.

### Красный nightly

**Симптомы:** ночная джоба `smoke` красная, а `ci` на том же коммите зелёная.
**Вероятная причина:** nightly делает существенно больше (`.github/workflows/nightly.yml`): сборка + `vn loc import` + `vn loc report`, smoke-матрица из четырёх прогонов (`--picks 0,0`; `--picks 0,1 --lang en`; `--picks 1`; `--picks 0,0 --lang pseudo`), `vn save check` + `vn save corpus`, и релизный путь целиком на удалённом `game/generated` для обоих флейворов.
**Диагностика:** артефакт `smoke-shots-<run_id>` (скриншоты `.vncache/smoke/`, 7 дней) плюс лог шага.
**Решение:** воспроизвести локально ровно ту команду, что упала; при таймауте смотрите `smoke: игра не завершилась за N c — прогон снят (дерево процессов убито)`.
**Профилактика:** прогоняйте `vn test smoke --picks 0,0` перед мержем крупных изменений в `game/framework/**`.

### GitLab CI ведёт себя иначе, чем GitHub Actions

**Симптомы:** `.gitlab-ci.yml` зелёный, а GitHub-джобы красные (или наоборот).
**Вероятная причина:** это **два разных пайплайна разной полноты**. GitHub Actions — 4 workflow: `ci` (джобы `lint`, `build-test`), `nightly` (`smoke`), `canary` (`fresh-renpy`), `release` (`build` матрицей на два флейвора, `dmg`, `publish`). GitLab — 3 джобы (`lint`, `build`, `test`), и в них **нет**: релиза, флейворов, LFS, ffmpeg, локализационных проверок, smoke, корпуса сейвов. Одно расхождение закрыто 2026-08-08: `pip install -r tools/vn.lock` теперь стоит и в GitLab (`.gitlab-ci.yml:23,37`), так что тулчейн в обоих пайплайнах одинаковый. Статус GitLab-конфига — PARTIALLY IMPLEMENTED / STALE, при этом `ci/README.md` до сих пор пишет «Конфиг пайплайна — корневой `.gitlab-ci.yml`».
**Диагностика:** сравнить `.gitlab-ci.yml` (59 строк) с `.github/workflows/ci.yml`.
**Решение:** считать источником истины GitHub Actions.
**Профилактика:** любое изменение CI-контракта вносите в оба файла либо явно выведите GitLab из эксплуатации отдельным PR. См. [29-build-and-release.md](29-build-and-release.md).

# 9. DAZ Studio

> Всё в этом разделе — внешнее окружение: **render automation NOT IMPLEMENTED** (ни `.dsa`-скриптов, ни headless-вызова, ни сборщика секвенций в репозитории нет). Проект умеет только детектировать DAZ (`vn pipeline doctor`) и валидировать декларации рендеров (`vn assets daz validate`), которых сейчас ноль.

### Iray считает минуты→часы, а GPU молчит

**Симптомы:** кадр, который должен считаться 3–5 минут, идёт час; загрузка GPU около нуля, CPU в потолок.
**Вероятная причина:** тихий CPU-fallback. Два источника: (1) старая ветка DAZ Studio, чей Iray собран до Blackwell — на RTX 50xx она физически не может использовать GPU; (2) сцена не влезла в VRAM (16 ГБ на RTX 5080) и Iray откатился на CPU.
**Диагностика:** лог Iray в момент старта рендера перечисляет устройства — там должно быть GPU-устройство, а не только CPU. Заодно `nvidia-smi` во время рендера.
**Решение:** держать свежий DAZ Studio (на референс-машине определяется DAZ Studio 6 по пути `D:\DAZ3D\Library\Applications\64-bit\DAZ 3D\DAZStudio6\DAZStudio.exe`); в Render Settings → Advanced → Devices **снять галку CPU**, чтобы нехватка VRAM падала явно, а не деградировала молча; уменьшать сцену через Scene Optimizer.
**Профилактика:** `docs/pipeline/phase-0.md §3.4` — настройки GPU; правило «никогда не переполнять VRAM» из ресёрча стоит выше любых настроек качества.

### OOM по VRAM на 16 ГБ

**Симптомы:** рендер падает или уходит в CPU на стадии «Retrieving Geometry».
**Вероятная причина:** пик потребления приходится на загрузку геометрии и текстур; текстуры дороже геометрии.
**Диагностика:** `nvidia-smi` во время загрузки сцены; в `vn pipeline doctor` строка GPU показывает модель, объём и версию драйвера.
**Решение:** даунскейл текстур второстепенных объектов (4K→2K и ниже), снижение subdivision, удаление внекадровой геометрии, HD-морфы только для фигуры в фокусе.
**Профилактика:** держать сцену заметно ниже потолка VRAM; для крупной библиотеки — Scene Optimizer как обязательный инструмент.

### Сторонние плагины не работают в DAZ Studio 6

**Симптомы:** привычный плагин (менеджер рендер-очереди, морф-утилиты и т.п.) не грузится или не виден в меню.
**Вероятная причина:** плагины и скрипты для 4.x должны быть обновлены авторами под DS6; часть инструментов на момент ресёрча (2026) сломана или требует платного апгрейда. Также в DS6 ретирован ряд подсистем (3Delight, Collada-экспорт, Dynamic Clothing и др.), а «избранное» и пункты меню скриптов из 4.x не мигрируют.
**Диагностика:** проверить страницу плагина на совместимость с DS6.
**Решение:** для батч-рендера предпочитать **не плагины, а внешние драйверы процесса** — они переживают смену SDK.
**Профилактика:** 4.x и 6 ставятся рядом; если критичный плагин ещё не обновлён, авторить можно в 4.x, но рендерить на Blackwell — только в свежей ветке.

### DIM поставил контент не туда

**Симптомы:** купленный контент не виден в Content Library; Smart Content пуст.
**Вероятная причина:** пути установки живут в per-account настройках DIM (`%APPDATA%\DAZ 3D\InstallManager\UserAccounts\*.ini`), а не в `AppSettings.ini` — именно оттуда их читает наш детектор (`tools/vn/src/vn/pipeline.py:82-137`). Плюс рассинхрон метаданных CMS.
**Диагностика:** `vn pipeline doctor` печатает `библиотека DAZ: <путь>` (из `CurInstallPath`) либо `не найдена в конфиге DIM` с рецептом `DIM -> Settings -> Installation: путь контента`.
**Решение:** выставить пути в DIM; при пустом Smart Content — Content DB Maintenance → Re-Import Metadata.
**Профилактика:** одна библиотека для DIM-контента, другая — для ручных установок; база CMS бэкапится наравне со сценами. Референс-раскладка проекта — `D:\DAZ3D\Library\Applications\Data\DAZ 3D\My DAZ 3D Library`.

### Рассинхрон имён морфов/материалов между сценами

**Симптомы:** персонаж «уплыл» между кадрами: другая форма лица, другой оттенок кожи, слетевший материал.
**Вероятная причина:** сцена ссылается на морфы/материалы, которых нет либо они другой версии; переустановка контента поменяла набор.
**Диагностика:** декларация рендера обязана указывать сцену и пресеты персонажей — `assets_src/daz/**/<name>.render.yaml` (`daz_render@1`: `source` вида `daz/....duf`, `output` в `png/**` или `video_src/**`, `render.resolution|renderer|camera`). Проверка — `vn assets daz validate`, она же скажет `сцены <путь> нет ни локально, ни в манифестах (vn assets push после сохранения .duf)`.
**Решение:** зафиксировать исходник идентичности (Character Preset) и ссылаться на него из каждой декларации; `.duf` заливать в хранилище, чтобы кадр был воспроизводим.
**Профилактика:** конвейер именно для этого и придуман: `<name>.render.yaml` → рендер → `vn assets daz validate` (пишет провенанс) → `vn build`. Сейчас деклараций **ноль**, команда честно отвечает `деклараций нет (assets_src/daz/**/<name>.render.yaml)`.

### daz3d.com не открывается из РФ

**Симптомы:** магазин/DIM не может достучаться до серверов DAZ; страницы не грузятся.
**Вероятная причина:** известная особенность окружения владельца — блокировка на стороне CDN. Обходится маршрутизацией через уже настроенный на домашнем роутере WireGuard-туннель.
**Диагностика:** проверить, ходит ли трафик к домену через туннель.
**Решение:** сетевые настройки — вне области этого хендбука; здесь фиксируется только сам факт, чтобы недоступность магазина не диагностировали как поломку конвейера.
**Профилактика:** тяжёлые загрузки контента планируйте заранее; конвейер от доступности магазина не зависит — он работает с уже установленной библиотекой.

# 10. ComfyUI и генерация

> Статус: `vn pipeline doctor|models` — **IMPLEMENTED** (`tools/vn/src/vn/pipeline.py:290-581`). Вызов ComfyUI из тулинга и воркфлоу-JSON в репозитории — **NOT IMPLEMENTED**: ни API-клиента, ни единого workflow-файла. Провенанс ComfyUI-PNG написан целиком и **ни разу не использован** (ноль `*.provenance.json`).

### `torch.cuda.is_available() == False`

**Симптомы:** `vn pipeline doctor` → `WARN PyTorch 2.x.y, CUDA НЕдоступна` с рецептом `нужен torch с индексом cu128 (Blackwell) — tools/setup-comfyui.ps1`; в ComfyUI генерация идёт на CPU или падает.
**Вероятная причина:** в venv ComfyUI стоит torch не с тем CUDA-индексом. Старые колёса не знают sm_120: CUDA формально «есть», а ядра не запускаются.
**Диагностика:**
```bash
D:/ComfyUI/venv/Scripts/python.exe -c "import torch; print(torch.__version__, torch.cuda.is_available())"
```
(эталон на референс-машине — PyTorch 2.11.0+cu128).
**Решение:** перезапустить `pwsh -File tools/setup-comfyui.ps1` (идемпотентен); при упорстве снести `D:\ComfyUI\venv` и повторить.
**Профилактика:** `docs/pipeline/phase-0.md §1` — два критичных пина Blackwell: torch cu128 и свежий DAZ. Отдельно держите в голове, что 4-битные NVFP4-оптимизации требуют torch, собранного под CUDA 13.0 — на других сборках они не «ничего», а замедление.

### OOM на Wan 14B

**Симптомы:** ComfyUI падает по памяти на видео-модели.
**Вероятная причина:** 16 ГБ VRAM против жирного воркфлоу/высокого разрешения. Модель A14B — это **два** экспертных чекпоинта (high-noise + low-noise), то есть примерно вдвое больше, чем подразумевает «14B».
**Диагностика:** `vn pipeline models` — таблица со статусами и размерами; `nvidia-smi` во время прогона.
**Решение:** брать fp8-варианты из манифеста `tools/comfyui-models.yaml`; держать 480p, максимум 720p; подключать LightX2V-лоры (4 шага вместо 20); полагаться на автоматический RAM-offload ComfyUI (61 ГБ RAM на референс-машине хватает).
**Профилактика:** таблица требований — `docs/pipeline/phase-0.md §1`; ниже 30 ГБ свободного места `vn pipeline doctor` уже предупреждает.

### Генерация видео «висит»

**Симптомы:** прогон идёт десятки минут без прогресса.
**Вероятная причина:** считается недистиллированный путь — 20+ шагов вместо 4.
**Диагностика:** посмотреть на число шагов сэмплера в воркфлоу и на то, подключены ли LightX2V-лоры.
**Решение:** подключить LightX2V-лоры и выставить 4 шага.
**Профилактика:** держите «шиппинговый» воркфлоу отдельно от экспериментального; ComfyUI-Manager умеет снапшотить состояние установки — это ваш механизм заморозки окружения.

### Модель не качается / загрузка рвётся

**Симптомы:** `vn pipeline models --pull` печатает `ошибка: <id>: curl вернул код N: <url>` и в конце `models: N загрузок не удалось` (exit 1).
**Вероятная причина:** сеть. Загрузка идёт `curl -L --fail --retry 3 --retry-delay 5 -C -` в файл `<dest>.part` и только потом `os.replace` — обрезанный файл никогда не выглядит готовой моделью (`pipeline.py:333-359`).
**Диагностика:** `vn pipeline models` — статусы `✓ / ✗ / ! / ?`; `!` (`undersized`) означает обрезанную докачку или подмену.
**Решение:** повторить `vn pipeline models --pull` — докачает с места обрыва.
**Профилактика:** после загрузки sha256 пишется в `<ComfyUI>/models/.vn-models.json`; при расхождении с манифестом файл **удаляется** (`pipeline.py:414-419`). Учтите: в манифесте `tools/comfyui-models.yaml` все `sha256` сейчас `null`, то есть эта проверка фактически не срабатывает — контроль идёт по размеру.

### `CIVITAI_API_KEY` не виден после `setx`

**Симптомы:** `нужен ключ: <id> — Civitai отдаёт файл только с API-ключом вашего аккаунта`, а ключ вы только что задали.
**Вероятная причина:** `setx` пишет в реестр User-окружения; текущий процесс и его родительская оболочка унаследовали старое окружение.
**Диагностика:** тулинг сам это различает — если ключ есть в реестре, но не в процессе, печатается `ключ ЕСТЬ в User-окружении, но не виден этому процессу — откройте НОВЫЙ терминал и повторите vn pipeline models --pull` (`pipeline.py:318-330,391-396`).
**Решение:** открыть новый терминал и повторить.
**Профилактика:** та же грабля, что с `RENPY_SDK` (раздел 1). Значение ключа не попадает ни в логи, ни в провенанс, ни в git — так и оставьте.

### Расползание лица между кадрами

**Симптомы:** персонаж узнаваем в одном кадре и «другой человек» в соседнем; особенно заметно на длинной дистанции игры.
**Вероятная причина:** идентичность держится на face-swap-подобных инструментах, которые фиксируют лицо, но отпускают волосы, пропорции тела и одежду.
**Диагностика:** собрать контактный лист из десятка кадров одного персонажа и посмотреть подряд.
**Решение:** по ресёрчу 2026 порядок такой: (1) обученная LoRA персонажа — основной якорь идентичности; (2) мультиреференсная edit-модель для новых поз/нарядов от одобренных рендеров; (3) ControlNet-поза для компоновки. В нашем конвейере первичный источник идентичности другой — DAZ Character Preset, а AI используется как полировка поверх рендера.
**Профилактика:** воспроизводимость: фиксированные seed'ы, сохранённые `workflow_api.json` в git, пиннованные хэши моделей. Механика записи этого уже есть — `vn assets provenance record` разбирает PNG из ComfyUI (workflow, seed, модель, LoRA, промпты) и `vn assets provenance verify` сверяет цепочки. Пока не использовалось ни разу.

# 11. Virt-a-Mate и The Sims 4

> Оба источника — опциональные (VaM — ADR-0006, Sims 4 — ADR-0007, «задел»). Их отсутствие даёт **WARN**, а не FAIL. Деклараций сейчас ноль в обоих деревьях.

### VaM не детектится

**Симптомы:** `vn pipeline doctor` → `WARN Virt-a-Mate: не установлен (опционально)`.
**Вероятная причина:** поиск идёт по `VN_VAM` → `D:\VaM\VaM.exe` / `C:\VaM\VaM.exe` → Steam-библиотеки (appId 2149830, включая пути из `libraryfolders.vdf`) — `pipeline.py:173-188`.
**Диагностика:** `ls "$VN_VAM"`; проверить, есть ли `VaM.exe` по указанному пути.
**Решение:** `pwsh -File tools/install-vam.ps1` либо задать `VN_VAM` на каталог с `VaM.exe`.
**Профилактика:** это предупреждение — конвейер без VaM полностью рабочий; основной путь анимации DAZ-кадр → Wan I2V.

### Sims 4 не детектится

**Симптомы:** `WARN The Sims 4: не установлен (опционально)`.
**Вероятная причина:** поиск: `VN_SIMS4` → реестр Maxis (`SOFTWARE\Maxis\The Sims 4`, включая WOW6432Node) → стандартные каталоги EA/Origin → Steam-библиотеки (appId 1222670); исполняемый — `Game\Bin\TS4_x64.exe` (`pipeline.py:191-226`).
**Диагностика:** `ls "<путь>/Game/Bin/TS4_x64.exe"`.
**Решение:** `pwsh -File tools/install-sims4.ps1` либо `VN_SIMS4` на корень установки.
**Профилактика:** источник — задел; продакшен-трек проекта DAZ.

### `capture.game_version` не указан в декларации Sims 4

**Симптомы:** `vn assets sims4 validate` → ошибка схемы вида `assets_src/sims4/.../x.render.yaml: capture: 'game_version' is a required property`, затем `ошибка: sims4 validate: N ошибок`.
**Вероятная причина:** `sims4_render@1` требует `capture.resolution`, `capture.mode` и `capture.game_version` (`tools/schemas/sims4_render@1.schema.json:31`) — патчи EA меняют картинку и ломают моды, кадр без версии игры невоспроизводим.
**Диагностика:** `vn content lint` тоже валидирует эти декларации (они попадают в `_iter_declarations` как `assets_src/**/*.yaml`).
**Решение:** дописать точную версию игры на момент захвата, а задействованные моды/CC — в `capture.mods`.
**Профилактика:** тот же принцип у VaM (`vam_render@1`: сцена, разрешение, режим, камера, плагины) — что не объявлено, то невоспроизводимо.

### Моды сломались после патча (VaM / Sims 4)

**Симптомы:** сцена открывается иначе, чем при захвате; позы/CC не работают; картинка «поехала».
**Вероятная причина:** обновление игры/приложения разошлось с зафиксированной в декларации версией и набором модов.
**Диагностика:** сравнить `capture.game_version`/`capture.mods` в декларации с текущей установкой; провенанс захвата покажет, чем и когда файл был получен (`vn assets provenance verify`).
**Решение:** либо откатить/зафиксировать версию, либо перезахватить кадр и обновить декларацию — вместе с новым провенансом.
**Профилактика:** захваты, попадающие в игру, обязаны иметь декларацию **до** захвата, а не после. Сама декларация ошибок вида «нет выхода» не считает фатальными: `<rel>: выход <путь> ещё не захвачен` — это предупреждение.

## Куда смотреть в первую очередь

Алгоритм на любой непонятный симптом. Не пропускайте шаги: каждый следующий имеет смысл, только если предыдущий зелёный.

1. **`vn doctor`.** Окружение раньше кода. Exit 1 — дальше не идём, чиним по рецепту `→`.
2. **Определить зону.** Ошибка про `game/generated/`, `game/assets/`, `game/tl/` — это про **источник** (`content/`, `assets_src/`, `loc/po/`), а не про файл, который вы видите: производные зоны перезаписываются сборкой и их нет в git.
3. **`vn content lint`.** Печатает ровно те `error:`-строки, что валят `vn build`, но быстро и без сборки. Помните G15: у `draft`-главы граф-ошибки — предупреждения.
4. **`vn build --check`.** Ничего не пишет; ловит несвежесть ассетов и генерата, битую разметку переводов и бюджеты G19. Красный `version.gen.rpy` после смены HEAD — норма (git-sha в `config.version`).
5. **Три файла в корне.** Не стартует → `errors.txt`. Стартует, но странно → `log.txt` (строки `[vn] …`). Упала → `traceback.txt`, плюс отчёт в `<savedir>/crash/` с breadcrumbs последних меток.
6. **`vn test smoke --picks …`.** Воспроизвести путь автопилотом: `RESULT.txt`, `picks.log`, `startup.txt` и скриншоты в `.vncache/smoke/`. Синтетический ввод в окно игры слать нельзя — только этот путь.
7. **`vn release validate --flavor public`.** Даже вне релиза: 19 проверок разом — быстрый способ понять, что именно в дереве не в порядке.
8. **`vn pipeline doctor`.** Только если проблема в производстве картинок/видео: ffmpeg и VP9, GPU и драйвер, torch/CUDA, ComfyUI и модели, DAZ и библиотека, свободное место, SDK.

Если после всех восьми шагов непонятно — это, скорее всего, баг тулинга: соберите вывод команды целиком, `git rev-parse --short HEAD` и содержимое трёх лог-файлов, и заводите issue. Аварийный обход на время разбирательства — взять `game/generated/` артефактом зелёной CI-джобы `build` (30 дней хранения) и распаковать локально.

## Чего НЕ делать

- **Не «чинить» правкой производных зон.** `game/generated/`, `game/assets/`, `game/tl/` и `.vncache/` перезаписываются ближайшей сборкой. Симптом там — причина в `content/`, `assets_src/`, `loc/po/`.
- **Не удалять `.vncache/assets-manifest.json`, чтобы «пересобрать начисто».** Без него удаление осиротевших ассетов отключается навсегда для уже лежащих файлов — придётся сносить `game/assets/` целиком.
- **Не считать зелёный `vn build` признаком настроенного окружения** — тёплый `.vncache/analyze-*.json` пропускает сборку без SDK.
- **Не гоняться за красным `vn build --check` после `git pull`** — git-sha в `config.version` делает генерат несвежим по определению. Просто `vn build`.
- **Не подкладывать `.webm` руками в `game/assets/mov/`** — без сайдкара `.webm.meta.json` компилятор не эмитит `Movie`-образ, а следующая сборка файл удалит как осиротевший.
- **Не слать синтетический ввод (SendKeys и подобное) в окно игры** — единственный поддерживаемый автопрогон это in-process автопилот `vn test smoke` / `vn save corpus`.
- **Не убивать `vn test smoke` по Ctrl+C на Windows наполовину.** Раннер сам убивает дерево процессов по таймауту (`taskkill /T /F`) и чистит `game/generated/qa/`; осиротевший `autopilot.rpyc` превратил бы обычный `vn play` в самопроигрывающуюся игру. Если такое случилось — удалите каталог `game/generated/qa/` руками.
- **Не читать `docs/ARCHITECTURE.md` как описание построенного.** Это целевой документ. `vn validate`, `vn build --use-artifact <sha>`, `vn content lint --strict/--arch/--schemas`, `vn test perf`, `game/assets/registry.json`, `rpyc-compat`-джоба — всё это **NOT IMPLEMENTED**; неизвестная команда даст exit 2, а не подсказку.
- **Не считать `tools/vn.lock` полной гарантией окружения.** Сам лок с 2026-08-08 читается всеми семью установками CI (G17 закрыт для 18 пиннованных пакетов), но транзитивные зависимости в нём не закреплены (`pygments`) — «одинаковый лок» не означает «побайтово одинаковое дерево пакетов».

## Проверка

Полный «зелёный круг» на референс-машине (Windows 11, RTX 5080, Python 3.12.10):

```bash
export RENPY_SDK="C:/Users/Vadim/renpy-sdk/renpy-8.5.3-sdk"   # в bash — обязательно

vn doctor                              # 8 галок, exit 0
vn content lint                        # lint: OK (N предупреждений)
vn build                               # build: OK
vn build --check                       # check: генерат свеж
vn assets validate                     # assets validate: OK
vn assets video validate               # video validate: OK (N файлов)
vn loc keys --check                    # все строки с id, ledger свеж
vn loc report                          # de/en/pseudo — 115/115 (100%), fuzzy 0
python -m pytest tools/vn/tests -q     # 240 passed
vn test smoke --picks 0,0              # smoke: OK: vn_end_of_content (N скриншотов)
vn save check && vn save corpus        # 2 фикстур: schema1-demo мигрирует 1 -> 2, schema2-demo уже на 2
vn release validate --flavor public    # 16 PASS, exit 0
vn release validate --flavor patron
vn pipeline doctor                     # exit 0; WARN по VaM и Sims 4 — норма
```

Если что-то из этого списка красное **до** ваших изменений — сначала выясните, было ли оно красным на `main`: `git stash -u && <команда>`.
