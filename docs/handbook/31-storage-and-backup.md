## 2. Что НИКОГДА не попадает в git

`.gitignore:1-22` — это не гигиена, а норма G2/G4. Производные зоны не коммитятся, потому что derived-бинари недетерминированы между версиями энкодеров и платформами, а массовая перегенерация раздувала бы append-only историю на десятки ГБ.

| Паттерн | Строка `.gitignore` | Почему |
|---|---|---|
| `game/generated/` | 2 | генерат компилятора; правки бесполезны |
| `game/assets/` | 3 | результат `vn assets build` |
| `game/tl/` | 4 | результат `vn loc import` |
| `game/cache/` | 5 | кэш движка |
| `game/saves/` | 6 | сейвы разработчика |
| `game/build_id.json` | 8 | пишется на время distribute, удаляется в `finally` (`release.py:307`, `cli.py:1558-1560`) |
| `*.rpyc`, `*.rpymc`, `*.rpyb` | 9-11 | байткод движка |
| `log.txt`, `errors.txt`, `traceback.txt` | 15-17 | вывод движка |
| `build/` | 20 | дистрибутивы, rpyc-cache, паки |
| `.vncache/` | 21 | кэш трансформаций и артефакты прогонов |
| `.vnstorage.local.yaml` | 22 | машинно-локальный оверрайд |

### 2.1 Единственное исключение: `!ci/fixtures/rpyc-line/**`

`.gitignore:12-14`:

```
# Линия statement-имён фикстур сейв-корпуса — ЕДИНСТВЕННЫЕ .rpyc в git (G6):
# без неё фикстуры валидны только на машине, где создавались
!ci/fixtures/rpyc-line/**
```

Причина — движковая. Ren'Py идентифицирует не-label стейтменты служебными именами (файл + версия + serial), и при перекомпиляции изменённого `.rpy` имена **неизменённых** стейтментов переносятся только если рядом лежит старый `.rpyc`. Сейв-фикстуры `ci/fixtures/saves/schema1-demo.save` и `schema2-demo.save` ссылаются на конкретные имена; без «линии» они валидны лишь на той машине, где создавались.

Механика (`../../tools/vn/src/vn/cli.py:1130-1164`): `_rpyc_line_restore` перед прогоном `vn save corpus` копирует **52** `.rpyc` из `ci/fixtures/rpyc-line/` в `game/` **с перезаписью** (только туда, где рядом есть `.rpy`), `_rpyc_line_snapshot` после — пересобирает каталог целиком (`rmtree` + копия всех `.rpyc` из `game/`).

Линия пересобрана 2026-08-08 вместе с добавлением второй фикстуры: старые 34 файла были сняты до появления галереи, ачивок и генерируемых UI-панелей, то есть половина framework и реестров в ней отсутствовала.

**Не путайте с `build/rpyc-cache/`** — это другой механизм с другой судьбой (§7.3): `rpyc-line` едет в git и служит детерминизму QA-фикстур, `rpyc-cache` не едет никуда и служит save-совместимости релизов.

## 4. Хранилище сырцов

**Статус: IMPLEMENTED (`type: file`) / NEVER RUN HERE.** `~/vn-assets-store` на этой машине не существует, `assets_src/**/*.manifest.json` — ноль, `vn assets status` печатает «манифестов нет — сырцы ещё не пушились (vn assets lock + push)».

Полная таблица команд и семантики `push/pull/lock/status` — в [Ассеты §8](16-assets.md). Здесь — только то, что относится к сохранности данных.

### 4.1 Логические имена: переезд в облако = один коммит

`.vnstorage.yaml` (`schema: storage@1`, обязательный файл для линта — `tools/vn/src/vn/content/lint.py:37`) целиком:

```yaml
schema: storage@1
storages:
  default: {type: file, path: "~/vn-assets-store"}
```

Смысл конструкции (норма G21): манифест-сайдкар `<файл>.manifest.json`, который коммитится в git, ссылается на **имя** хранилища (`"storage": "default"`), а не на физику. Пример документа `asset_src@1`, который пишет `push` (`../../tools/vn/src/vn/assets/storage.py:197-207`):

```json
{"schema": "asset_src@1", "path": "png/characters/mira/a/base.png", "version": 1,
 "size": 12345, "hash": {"algo": "blake3", "hex": "…"},
 "storage": "default", "key": "png/characters/mira/a/base.png/v1",
 "uploaded_by": "vkonovalov", "uploaded_at": "2026-08-08T12:00:00+00:00"}
```

Переезд «внешний диск → S3» — замена одной строки в `.vnstorage.yaml`; ни один манифест в git не меняется. Объекты иммутабельны (`key = <rel>/v<N>`, версия монотонно растёт), поэтому история сырцов не переписывается.

### 4.2 `type: file` против `type: s3`

| `type` | Статус | Что это даёт для бэкапа |
|---|---|---|
| `file` | IMPLEMENTED (`storage.py:65-118`) | `path` — любая папка: внешний диск, NAS, смонтированная сетевая шара, синхронизируемый каталог. Раскладка `<base>/objects/<key>` + `<base>/locks/<rel>.lock`, запись атомарная (`.tmp` + `os.replace`) |
| `s3` | **NOT IMPLEMENTED** | честный `StorageError`: «s3-бэкенд подключается при переходе команды на облако (G21: манифесты не изменятся) — пока используйте type: file» (`storage.py:129-133`) |
| прочее | ошибка | `StorageError: неизвестный type` (`storage.py:134`) |

Практический вывод для соло-разработчика: **включить хранилище можно прямо сейчас, без облака** — достаточно указать `path` на внешний диск. Это единственный существующий в проекте механизм, который делает сырцы восстановимыми не из головы.

### 4.3 `.vnstorage.local.yaml`

Мержится поверх основного конфига (`storage.py:57-62`), лежит в `.gitignore:22`. Смысл: у каждого своя буква диска / свой путь к NAS, а общий `.vnstorage.yaml` остаётся одинаковым у всех. `vn doctor` отдельной строкой сообщает, что оверрайд активен (`doctor.py:104-106`) — чтобы «у меня работает» не превращалось в загадку.

### 4.4 Локи (G14)

Зачем: PSD и другие бинарные сырцы **не мержатся**. Потерянная работа художника дороже дисциплины, поэтому `push` без лока просто отказывает.

| Аспект | Факт | Код |
|---|---|---|
| Где файл | `<storage base>/locks/<rel>.lock` | `storage.py:74-75` |
| Формат | `{"by": "<git config user.name>", "at": "<utc isoformat seconds>"}` — ровно два поля | `storage.py:106-108` |
| Владелец | `git config user.name`, fallback `getpass.getuser()` | `storage.py:46-54` |
| Где enforced | **только внутри `vn assets push`**: нет лока → отказ, чужой лок → отказ | `storage.py:178-187` |
| Снять свой | `vn assets lock <rel> --release` | `cli.py:927-940` |
| Снять чужой | `vn assets lock <rel> --release --force` — текст ошибки без `--force` прямо говорит про эскалацию: «лок держит «X» (снять: --force, эскалация на лида)» | `storage.py:255-260` |
| Взять при получении | `vn assets pull --edit` | `storage.py:237-242` |

**Честно про гарантии:**

- `acquire_lock` — read-then-write **без атомарного создания** (`storage.py:99-109`): гонка двух клиентов — оба «выигрывают». `docs/ARCHITECTURE.md:293` требует условной записи `If-None-Match` — NOT IMPLEMENTED.
- **TTL нет**, автоматической эскалации нет, бот-нотификаций нет (`ARCHITECTURE.md:79`, `:295`) — NOT IMPLEMENTED. Забытый лок висит вечно.
- `--force` снимает чужой лок **без записи в аудит** (`storage.py:111-118`).
- Личность = `git config user.name`, то есть переопределяется одной командой. Гарантия G14 процедурная, не техническая.
- Локальную правку файла в `assets_src/` ничто не блокирует; `pull` без `--edit` лок не берёт и не проверяет.

Единственная **техническая** гарантия целостности здесь — перехэширование скачанного: `pull` считает blake3 полученного блоба и падает на несовпадении с манифестом (`storage.py:227-229`).

### 5.4 Сейвы: две локации, не одна

Ren'Py 8.5.3 держит `MultiLocation` (`<SDK>/renpy/savelocation.py:679-707`): (1) `config.savedir`, (2) `<gamedir>/saves`, если каталог существует, (3) `config.extra_savedirs`. `game/options.rpy:7` задаёт `config.save_directory = "vn-1755000000"`, поэтому на Windows первая локация — `%APPDATA%\RenPy\vn-1755000000\` (**Roaming**, не Local).

**Имя `vn-1755000000` переименовывать нельзя.** Оно выглядит временным, но это штатное имя от лаунчера Ren'Py — `<simple_name>-<unixtime создания проекта>` (`$RENPY_SDK/launcher/game/gui7/parameters.py:113`), литерал, а не вычисление. Переименование = смена каталога сейвов: у игроков «пропадает» весь прогресс и `persistent` (галерея, достижения, настройки), а маски Steam Auto-Cloud начинают синхронизировать пустой каталог, продолжая держать старый в облаке ([39-platforms.md](39-platforms.md) §6, `ci/steam/README.md`). Если однажды понадобится — это миграция «скопировать старый каталог в новый при первом запуске», а не правка `options.rpy`; в самой строке стоит предохранитель-комментарий.

Проверено на диске: **обе** локации существуют (616 КБ и 232 КБ) и содержат пересекающиеся наборы слотов (`1-1-LT1.save`, `auto-*.save`, `_tracesave-*.save`). Туда же движок кладёт `persistent` (галерея, ачивки, настройки — [Галерея](15-gallery.md)), а краш-хендлер — отчёты в `<savedir>/crash/crash-YYYYmmdd-HHMMSS.txt` (`game/framework/00_core/070_crash.rpy:27-34` — каталог, `:53-69` — запись отчёта).

Копировать при бэкапе нужно **обе**: `%APPDATA%\RenPy\vn-1755000000\` и `<repo>\game\saves\`.

Отдельная грабля: Ren'Py 8 подписывает сейвы per-machine токеном. Ключ подписи генерируется **на устройстве** и лежит в `<корень>/tokens/security_keys.txt`, то есть **вне** каталога сейвов (`$RENPY_SDK/renpy/savetoken.py:290-306`) — поэтому чужой сейв, принесённый на другую машину (или приехавший из Steam Cloud), встречает модальный вопрос «This save was created on a different device…» (`renpy/common/00gui.rpy:459-460`, логика — `savetoken.py:141-185`): игрок один раз подтверждает доверие, ключ дописывается в файл. **Обойти это подстановкой общего ключа нельзя** — `config.save_token_keys` принимает только verifying-ключи и явно отвергает signing (`savetoken.py:316-337`). Для бэкапа это не блокер, но означает, что «перенести сейвы» ≠ «положить файлы», и что папку `tokens/` в облако синхронизировать бессмысленно.

```bash
# 3. Движок

#    ↑ ОТКРОЙТЕ НОВЫЙ ТЕРМИНАЛ: setx виден только новым процессам

# 4. Диагностика ПЕРЕД сборкой
vn doctor                                      # 8 галок, exit 0

# 5. Производные зоны
vn bootstrap                                   # doctor -> assets build (full) -> compile -> loc import

# 6. Сырцы из хранилища (когда оно заведено)

# 7. Только для контент-продакшена

vn pipeline models --pull                      # ~35 ГБ обязательных моделей

# 8. Проверка

python -m pytest tools/vn/tests -q             # 400 passed

```

### 6.1 Что восстановится само, а что руками

|---|---|

| Шрифты UI — `git lfs pull` | ffmpeg с libvpx-vp9 (только для видео) |

**Про `tools/vn.lock` — что изменилось.** Файл существует, точен (18 пинов, `Pillow==12.3.0`, `PyYAML==6.0.3`, `blake3==1.0.9`, `pytest==9.1.1`, …) и **теперь действительно читается CI**: `pip install --quiet -r tools/vn.lock` идёт **перед** editable-установкой во всех 8 джобах установки тулчейна (`ci.yml` ×2, `nightly.yml` ×3, `canary.yml`, `release.yml`, `steam-upload.yml`). Порядок важен: после лока `>=`-диапазоны из `pyproject.toml` уже удовлетворены и pip ничего не поднимает. Инвариант закреплён тестом `tools/vn/tests/test_ci_config.py::test_lock_installed_before_editable`. На новой машине ставьте так же — сначала лок, потом editable.

**Остаток по G17, честно.** В локе закреплены только прямые зависимости; транзитивные (например `pygments`, приезжающий с `pytest`) не пиннованы, поэтому окружение всё ещё не бит-в-бит воспроизводимо. Полное закрытие — регенерация лока с транзитивными пинами (`pip-compile` / `uv pip compile`), это отдельная задача.

**`vn bootstrap` — тоже честно.** G4 (`docs/ARCHITECTURE.md:59`, `:425`) обещает, что bootstrap *скачивает* три производные зоны из remote cache / CI-артефактов последнего зелёного main с гарантией «clone → bootstrap → запуск ≤ 5 минут». Это **NOT IMPLEMENTED**; докстринг команды сам это признаёт (`cli.py:205-206`). Текущий bootstrap собирает всё локально, а значит **требует полного тулчейна** (Python + Pillow + при наличии видео — ffmpeg) даже сценаристу и QA. Аварийный режим `vn build --use-artifact <sha>` (14 упоминаний в ARCHITECTURE.md) не существует: во всём тулчейне строка встречается один раз — в *заголовке* схемы `gen_manifest@1`.

Единственный работающий обходной путь без тулчейна описан в `docs/runbooks/pipeline-broken-at-night.md:9-11`: скачать артефакт `generated-<sha>` CI-джобы `build-test` (хранится 30 дней, `.github/workflows/ci.yml`) и распаковать в `game/generated/`.

## 7. Сценарии катастроф

### 7.1 Потеря `.vncache/`

Каталог не в git и ниоткуда не восстанавливается. Что именно ломается:

| Файл/каталог | Что теряется | Последствие |
|---|---|---|
| `.vncache/assets-manifest.json` | манифест сборки ассетов (55 выходов) | **удаление осиротевших молча отключается**: `old_manifest` остаётся пустым (`tools/vn/src/vn/assets/pipeline.py:393-399`), `candidates = set(old_manifest) - set(seen_outputs)` пусто (`:422`), сборка зелёная. Файлы, которых уже не должно быть в `game/assets/`, останутся навсегда и поедут в каждый дистрибутив |
| `.vncache/assets/<2hex>/<64hex>` | 24 блоба кэша трансформаций | только время: всё перекодируется заново |
| `.vncache/analyze-*.json` | кэш разбора `.rpy` через SDK | только время; **но** тёплый кэш маскирует отсутствие SDK — на холодном вы наконец узнаете, что `RENPY_SDK` не задан |
| `.vncache/psd_png/` | staging PSD | пересоздаётся при `vn assets build` (не при `--check`!) |
| `.vncache/{smoke,corpus,corpus-savedir,video-tmp}` | артефакты прогонов | ничего |
| `.vncache/langqa/` | 4 PNG + `RESULT.txt` разовой ручной языковой проверки (377 КБ) | **невосстановимо**: производящего кода в проекте нет (grep `langqa` по `tools/ game/ docs/ .github/` — ноль), значит это единственная копия. См. [27-testing.md §4.8](27-testing.md). Ценность низкая (ручной артефакт), но «пересобрать» его нечем |

**Рецепт.** Если удалили `assets-manifest.json` — снесите `game/assets/` целиком и пересоберите: `rm -rf game/assets && vn assets build`. Полусостояние хуже, чем чистая пересборка.

**Манифест теперь валидируется схемой при записи (G16 закрыт).** Файл `tools/schemas/assets_manifest@1.schema.json` заведён, и `build_assets` прогоняет собранный документ через `SchemaRegistry` перед записью (`pipeline.py:441-455`): ошибки схемы попадают в `rep.errors` и валят сборку. Записывается файл при этом **всё равно** — комментарий в коде объясняет почему: манифест описывает то, что уже лежит на диске, и без записи следующая сборка потеряет точечную очистку сирот. Так что «битый манифест» — это теперь красная сборка, а не тихая деградация. Раньше документ объявлял `"schema": "assets_manifest@1"`, которой не существовало.

Отдельная ловушка: `vn build --check` на чистом чекауте с PSD-источниками. `slice_all_psd` в режиме `check` пропускается (`pipeline.py:263-268`), `_discover` читает пустой `.vncache/psd_png/`, и **все** PSD-производные выходы объявляются осиротевшими.

### 7.2 Потеря `game/generated/` или `game/assets/`

Штатная ситуация — обе зоны и так не в git. `vn build` (или `vn bootstrap`) восстанавливает обе. `game/generated/manifest.json` (`gen_manifest@1`, 36 входов / 21 выход) пересоздаётся сборкой; свежесть компилятор определяет **побайтовым сравнением выходов** (`tools/vn/src/vn/content/compile.py:1168-1178`), а `inputs` пишется, но обратно не читается.

Единственная команда, которая жёстко падает без `game/generated/manifest.json` — автопилот: `game/generated/ пуст — сначала vn build` (`cli.py:1297-1298`).

Ночная CI-джоба специально проверяет этот путь: `nightly.yml` делает `rm -rf game/generated` и запускает `vn release build` — «ловит регрессии вида «гейт требует генерат, которого в CI ещё нет»».

### 7.3 Потеря `build/rpyc-cache/` — самый недооценённый риск

Что это: снимок **всех** `.rpyc` из `game/` после прошлого релиза (`cli.py:357-367`; сейчас на диске два каталога — `build/rpyc-cache/0.1.0/` 48 файлов и `0.1.4/` 52 файла, оба включая `framework/`, потому что «framework-метки тоже попадают в сейвы/rollback»). При следующем `vn package` они восстанавливаются в `game/` **с перезаписью** до вызова `renpy compile` (`cli.py:303-334`), чтобы движок перенёс имена стейтментов.

Почему это критично: без переноса имён любая правка файла сцены меняет имена **всех** его стейтментов; сейв середины сцены и его rollback-лог теряют опорные точки, и загрузка падает с «Couldn't find a place to stop rolling back» — до всяких `after_load`-миграций.

Что защищает и что нет:

| | |
|---|---|
| В git? | **нет** — `build/` целиком в `.gitignore:20` |
| Есть ли предупреждение при потере? | частично: если каталог кэша есть, но не восстановлен **ни один** файл → `_fail("rpyc-перенос: кэш … есть, но не восстановлено ни одного .rpyc — save-совместимость под угрозой (G6), сборка остановлена")`. Если каталога **нет вовсе** — печатается «кэша прошлых релизов нет (первый релиз)» и сборка идёт дальше **молча** |
| CI | `actions/cache` с ключом `rpyc-<flavor>-<ref>` (`release.yml:71-76`). Это кэш, а не архив: записи вытесняются, долговременных гарантий нет |
| Ключ каталога | **только версия**, не флейвор (`cli.py:358`) — public и patron одной версии пишут в один каталог, последний собранный побеждает |
| Регрессионная джоба `rpyc-compat` (`ARCHITECTURE.md:3508`) | **NOT IMPLEMENTED** — никто не проверяет, что перенос имён реально работает |

**Рекомендация:** после каждого выпущенного релиза копируйте `build/rpyc-cache/` наружу целиком (в тот же внешний диск, где хранилище сырцов) — там теперь по каталогу на линию флейвора, и линия public не заменяет линию patron. Это ~190 КБ на версию и флейвор, которые нельзя воссоздать.

### 7.4 Потеря хранилища сырцов

Сегодня хранилища нет, терять нечего. Когда заведёте — модель такая:

- в git остаются `*.manifest.json` (путь, версия, blake3, имя хранилища, ключ);
- бинарей нет нигде, кроме `<base>/objects/`;
- `vn assets pull` без объекта в хранилище выдаст `объекта '<key>' нет в хранилище <base>` (`storage.py:86-87`) — и восстановить будет **нечем**.

То есть каталог `objects/` становится таким же критичным, как git-репозиторий, и обязан бэкапиться отдельно. Иммутабельность ключей (`<rel>/v<N>`) означает, что инкрементальная копия каталога дёшева: старые объекты не переписываются.

Пока хранилища нет, страховкой служит ADR-0004 + линт-порог: суммарный вес нетекстовых байт под `assets_src/` > 30 МБ → warning, > 50 МБ → **error** и красная сборка (`tools/vn/src/vn/content/lint.py:47`, `:371-399`). Сейчас 129,3 КБ — 0,25 % порога.

### 7.5 Потеря машины

По пунктам таблицы §5.1: 1-3 возвращает `git clone` + `git lfs pull` (2,9 МБ), 4 — из бэкапа внешнего диска, 6 — `vn pipeline models --pull` (~35 ГБ, часы), 5 — DIM под вашим аккаунтом (15,6 ГБ, часы), 8 — renpy.org.

**Не вернётся ничем:** сейвы и `persistent`, `build/rpyc-cache/`, локальные `.duf`-сцены DAZ, любые сырцы, не попавшие ни в git, ни в хранилище, и `CIVITAI_API_KEY` (заводится заново).

Порядок действий — runbook §6. Ожидаемое время: минуты до `vn play` без контент-продакшена; часы-сутки с ним.

### 7.6 Порча git-истории

Единственный бэкап истории — remote `origin` (`github.com/Onemyname/renpy`, приватный). Локально 51 коммит, ветка `main`.

- **Локальная порча** (`.git` побился, ребейз ушёл не туда): `git clone` заново с origin — при условии, что всё запушено. Проверяйте `git status` и `git log origin/main..HEAD` перед выключением машины.
- **Порча на origin** (force-push поверх истории): восстанавливается только из чьего-то локального клона или из reflog GitHub. Ветка защищена? — в репозитории нет ни настройки branch protection в файлах, ни упоминания; считайте, что нет.
- **Потеря LFS-объектов** — отдельный риск: `git clone` без `git lfs pull` даст указатели, и `vn doctor` это поймает (§3). Но если объект пропал на сервере, вернуть его можно только из локального `.git/lfs`.
- **`.gitignore` защищает от обратной ошибки** — случайно закоммитить 89 МБ `build/dist/` нельзя.

### 7.7 Потеря сейвов

Источника нет: `game/saves/` и `%APPDATA%\RenPy\vn-1755000000\` не в git и ничем не генерируются. Что есть в проекте про сейвы — это **корпус фикстур для проверки совместимости**, а не бэкап:

- `ci/fixtures/saves/` — **две** фикстуры в git: `schema2-demo.save` (`vn_save_schema: 2`, сцена `ch01_s020`) и `schema1-demo.save` (`vn_save_schema: 1`, сцена `ch01_s010`);
- `ci/fixtures/rpyc-line/` — линия имён стейтментов к ним (§2.1);
- `vn save check` — оффлайн-проверка структуры слота и метаданных (`cli.py:1099-1124`);
- `vn save corpus` — прогон фикстур в реальном движке со скретч-`--savedir`, с прогоном миграций через `label after_load` и требованием `schema_after == project["save_schema"]`;
- `vn save corpus --add <name>` — **создать** новую фикстуру.

**Корпус наконец проверяет миграции, а не только загрузку.** Пока фикстура была одна и уже лежала на целевой схеме, `vn save corpus` доказывал лишь «сейв грузится». Фикстура `schema1-demo` приходит со **старой** схемы, поэтому прогон даёт «schema после загрузки: 2 (цель 2)», а в `log.txt` появляется строка `[vn] migration 0002` — миграция реально исполняется в движке, а не считается исполненной.

Релизный гейт про корпус только предупреждает: «сейв-корпус: 0 фикстур — создайте (vn save corpus --add) до релиза, иначе совместимость сейвов не проверена» (проверка №19, `release.py:542-549`) — FAIL никогда. Сегодня строка гейта — `PASS сейв-корпус: 2 фикстур`.

Практика: **перед бампом `save_schema` и перед крупным рефактором сцен** снимите фикстуру (`vn save corpus --add`) и скопируйте живые сейвы обеих локаций наружу. Детали модели состояния и миграций — [Backend / состояние и сейвы](07-backend.md).

## Чего НЕ делать

- **Не коммитить производные зоны.** `game/generated/`, `game/assets/`, `game/tl/`, `build/`, `.vncache/`, `*.rpyc` — вне git по норме G2/G4. Правка этих файлов бесполезна: перезапишет ближайшая сборка.
- **Не снимать `!ci/fixtures/rpyc-line/**` из `.gitignore`.** Это единственные `.rpyc` в git, и без них сейв-фикстуры валидны только на машине, где создавались.
- **Не удалять `.vncache/assets-manifest.json` «чтобы пересобралось».** Удаление осиротевших после этого молча отключается, а сборка остаётся зелёной. Если удалили — сносите `game/assets/` целиком.
- **Не считать `build/rpyc-cache/` мусором.** Полторы сотни килобайт на версию, которые нельзя воссоздать; их потеря ломает совместимость сейвов у игроков, и предупреждения при полной потере каталога **не будет**.
- **Не заводить LFS для сырцов ассетов.** `.gitattributes:2` прямо фиксирует политику: game-ready ассеты не коммитятся вовсе, сырцы живут в хранилище через манифесты. LFS-хранилище дорогое и не даёт версионирования, которое уже есть в манифестах.
- **Не пушить сырцы без лока** — `push` откажет (G14). И не считать лок защитой: не атомарный, без TTL, владелец = `git config user.name`, `--force` снимает чужой без следа.
- **Не мигрировать файл между хранилищами повторным `push`** — имя хранилища закрепляется первым манифестом (`storage.py:176`), новый `--storage` для уже опубликованного файла игнорируется.
- **Не рассчитывать на `vn bootstrap` как на скачивание** — он собирает локально и требует полного тулчейна. Аварийный `vn build --use-artifact <sha>` не существует.
- **Не ставить `pip install -e "tools/vn[dev]"` без предшествующего `pip install -r tools/vn.lock`** — порядок обязателен: editable, поставленный первым, уже отрезолвит `>=`-диапазоны, и пины станут декоративными. И помните остаток: транзитивные зависимости в локе не закреплены.
- **Не хранить `CIVITAI_API_KEY` в репозитории.** Он читается из окружения (`pipeline.py:313-315`); `setx` виден только **новым** процессам, и загрузчик специально ловит этот случай, заглядывая в реестр (`pipeline.py:318-331`).
- **Не считать `%APPDATA%\RenPy\vn-1755000000\` единственной локацией сейвов** — их две (§5.4), и бэкапить нужно обе.
