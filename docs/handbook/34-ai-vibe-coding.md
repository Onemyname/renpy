## 1. Почему репозиторий устроен именно так

Архитектура этого проекта — не «чистый код ради красоты». Почти каждое решение раздела 0 `ARCHITECTURE.md` попутно решает конкретную проблему агентной разработки: сокращает пространство, в котором агент может выдумать правдоподобное и неверное.

| Приём | Механизм в коде | Что закрывает у агента | Статус |
|---|---|---|---|
| **Декларации вместо кода** | `content/**/*.yaml` — 39 схем в `../../tools/schemas/`, `additionalProperties: false` (ADR-0002) | выдуманное поле в YAML падает на линте за секунды, а не молча игнорируется в рантайме | IMPLEMENTED |
| **Кодоген** | [`tools/vn/src/vn/content/compile.py`](../../tools/vn/src/vn/content/compile.py) (1211 строк) → 21 выход в `game/generated/` | label-обвязка, `default`, реестры образов, экран выбора глав — вне зоны творчества; агент правит вход, а не выход | IMPLEMENTED |
| **`schema: <name>@<int>` в каждом YAML (G16)** | [`schemas.py:13-51`](../../tools/vn/src/vn/schemas.py) — Draft 2020-12, `properties.schema.const` == id файла | нельзя «просто добавить поле»: формат — это версионируемый контракт | IMPLEMENTED |
| **Единый CLI (G1)** | [`cli.py`](../../tools/vn/src/vn/cli.py), 2117 строк, 20 команд/групп верхнего уровня (68 листовых) | нет соблазна «напишу одноразовый скрипт»; `vn --help` — исчерпывающий и проверяемый список возможностей | IMPLEMENTED |
| **Честные заглушки с номером фазы** | `_stub(phase)` → `exit 3` + сообщение «эта команда появится в фазе N» (`cli.py:34-38`) | агент видит «фаза 2» вместо тихого no-op, который он принял бы за рабочую фичу | IMPLEMENTED |
| **Контракт exit-кодов** | `cli.py:22-24`: `exit 1` **всегда** сопровождается строкой `ошибка: …`, голого трейсбека не бывает | 1 = сломал; 2 = выдумал флаг (click usage error); 3 = ещё не реализовано. Диагноз без чтения трейсбека | IMPLEMENTED |
| **Нормы G1–G24 / C1–C24 как контракт ревью** | [`../ARCHITECTURE.md:36-201`](../ARCHITECTURE.md), полный справочник — [02-architecture.md](02-architecture.md) | «это нарушает C2» — одна строка вместо абзаца объяснений; норма проверяема, вкус нет | IMPLEMENTED |
| **Производные зоны в `.gitignore`** | `../../.gitignore:1-21` — `game/generated/`, `game/assets/`, `game/tl/`, `*.rpyc`, `build/`, `.vncache/` | правка генерата физически не попадёт в коммит; ошибка становится видимой немедленно | IMPLEMENTED |
| **Парсер вместо регексов (G24)** | `renpy.exe <root> vn_analyze` → [`tools/vn/src/vn/content/analyze.py`](../../tools/vn/src/vn/content/analyze.py) + `game/framework/00_core/050_build_bridge.rpy` | нельзя «почти правильно» распарсить `.rpy` регексом — типичнейший фейл агента | IMPLEMENTED |
| **Пометки статуса в самом хендбуке** | этот корпус: каждый механизм помечен IMPLEMENTED / PARTIAL / NOT IMPLEMENTED | агент не принимает целевой документ за описание реальности | IMPLEMENTED (в `docs/handbook/`) |

Вывод, который стоит держать в голове при любой правке: **всё, что делает состояние проекта машинно-проверяемым, окупается в агентном режиме вдвойне**. Правило «новая проверка — это правило линтера, а не абзац в документе» — прямое следствие.

**Чего в этом ряду НЕТ (NOT IMPLEMENTED):** pre-commit-хука (`ARCHITECTURE.md:659` его требует, `.git/hooks/` содержит только четыре стандартных хука git-lfs), автоматической проверки согласованности `renpy_sdk` в `project.yaml` с `RENPY_VERSION` в трёх workflow, и любого механизма, который бы заставил агента прочитать правила до первой правки.

Порядок не переставляется. Каждый шаг дешевле следующего и отсекает часть ошибок.

## 4. Как не плодить дублирующие системы

Это главная болезнь агентной разработки: агент, который не нашёл существующий механизм за 10 секунд, напишет второй — правдоподобный, работающий и несовместимый. Академическая оценка масштаба: из 567 PR, сгенерированных агентом в 157 OSS-проектах, [83,8 % были смержены, но лишь 54,9 % смерженных — без доработок](https://arxiv.org/abs/2509.14745), и доработки концентрируются как раз в «соблюдении внутренних стандартов проекта».

### 4.3. Где дубли уже возникали — реальные следы в репозитории

Это не гипотетика; вот что видно в коде сегодня:

- **Два CI-конфига — было и вылечено 2026-08-18.** `.gitlab-ci.yml` (3 джобы) и `.github/workflows/` (5 workflow, 9 определений джоб) решали одну задачу, авторитетен был второй, а документирован — первый. Дубль дожил до продакшна и снят удалением зеркала; чтобы он не вернулся, отсутствие чужих CI-конфигов теперь проверяется тестом. Мораль для агентской работы: дубль, который «пока пусть полежит», через полгода читается как источник истины.
- **Два источника разблокировки галереи.** Здесь дубль **осознанный и задокументирован** в [ADR-0010](../adr/0010-gallery-extras.md): `persistent._seen_images` для картинок (движок знает) и `persistent.vn_gallery_unlocked` для видео и событий (движок не знает). Разница между этим случаем и предыдущим — ровно в наличии ADR.
- **`vn_frame_panel` и `vn_frame_toast`** генерируются и не используются ни одним экраном — мёртвая ветка, то есть дубль, у которого не осталось второй половины. Соседний случай **закрыт 2026-08-08**: `copy_audio` больше не ждёт несуществующий `assets_src/audio/` — конвейер читает нормативную зону `assets_src/audio_stems/` (`pipeline.py:159-170`), каталоги `{bgm,amb,sfx}` заведены, ветку стережёт тест `test_assets.py:test_audio_stems_branch_copies_ogg`. Ветка живая, но **ещё не работала на данных**: `content/audio/{bgm,sfx}.yaml` по-прежнему `tracks: {}` и в репозитории ноль `.ogg`.

Мораль: дубль сам по себе не преступление — преступление это **необъявленный** дубль. Если второй механизм нужен, он объявляется ADR-ом (§ 7).

Причина не в недоверии: у моделей документирована [self-evaluation bias](https://www.anthropic.com/engineering/harness-design-long-running-apps) — при самооценке агент склонен уверенно хвалить собственную работу. Здесь эту роль выполняет `vn`, а не второй агент.

## 7. Большие фичи: декомпозиция, фазы, ADR

### 7.1. Декомпозиция

История репозитория показывает обе крайности. Четыре «фазовых» коммита — гиганты (`3b77c9c` — 86 файлов, `9c419fc` — 38, `72c44ca` — 37, `79c9bef` — 32). Всё, что после, — нормального размера: медиана по 51 коммиту — **6 файлов**. Фичевые коммиты живут в диапазоне 2–12 файлов (`d5f292b` UI-панели — 8 файлов; `a18be12` достижения — 12; `05be376` галерея — 24, и это верхняя граница разумного).

Рабочее правило: **одна задача агента = один коммит = одна подсистема + её тесты + её ADR, если он нужен**. Признак, что пора делить: задача трогает больше одной зоны из списка «`tools/` / `game/framework/` / `content/` / `tools/schemas/`».

Для многошаговой работы план пишется **в файл в репозитории до начала**, а не держится в разговоре: контекст сессии не переживает `/compact` и `/clear`, а файл переживает. Готовый образец такого плана в этом проекте — `docs/pipeline/design-brief-choices.md` (132 строки): файлы к правке, доступные механизмы, жёсткие контракты, известные проблемы, приёмочные команды. По нему сделан коммит `de888de`, и результат зафиксирован в CHANGELOG 0.1.3.

### 7.2. ADR — когда писать двенадцатый

Сейчас в `docs/adr/` — **14 решений (0001–0014) плюс `template.md`**. Ни одно не имеет статуса «заменено»; тринадцать приняты, ADR-0008 (лицензии AI-моделей для коммерческого 18+) — единственное со статусом «предложено», ждёт решения владельца. Свежие: [ADR-0012](../adr/0012-render-profile-and-oversampling.md) (render-профиль и oversampling), [ADR-0013](../adr/0013-layered-shots.md) (послойные шоты) и [ADR-0014](../adr/0014-platform-services.md) (Platform Services: Steam как одна из платформ, а не фундамент — [39-platforms.md](39-platforms.md)).

Шаблон (`docs/adr/template.md`, 17 строк) требует: Статус · Дата · **Затрагивает нормы: G…/C…** (обязательно, если решение меняет норму раздела 0) · Контекст · Решение · Последствия, включая план отступления.

**ADR пишется, если верно хотя бы одно:**

- решение меняет или уточняет норму G1–G24 / C1–C24 (ADR-0003 сдвинул init-шкалу C8; ADR-0010 уточнил C9);
- решение вводит новую зону каталогов или новую схему-семейство (ADR-0006 — `assets_src/daz/**`, `video_src/**`; ADR-0007 — `sims4/`);
- решение осознанно ослабляет обещание (ADR-0004 временно легализовал PNG-сырцы в git вопреки «в git только манифесты»);
- решение вводит второй механизм там, где логично был бы один (ADR-0010 — два источника разблокировки);
- решение меняет формат документа, который уезжает наружу (ADR-0011 — бамп `build_info@1` → `build_info@2`, потому что старое поле выносило секрет игроку);
- решение имеет правовые последствия (ADR-0008).

**ADR не пишется** на выбор имени переменной, порядок полей, локальный рефакторинг и всё, что дешевле переделать, чем описать. Каталог из сорока ADR, который никто не индексирует, хуже, чем ноль ADR.

**Грабля агентного режима:** устаревший ADR активно вредит — агент ему доверяет и строит против системы, которую вы уже удалили. Правка ADR — часть того же диффа, что и правка кода. Пример живого несоответствия: `ARCHITECTURE.md` до сих пор описывает галерею через штатный `Gallery` + `_seen_images`, хотя ADR-0010 эту схему уже уточнил; догадаться, какой документ свежее, можно только по дате.

Отдельный долг: `ARCHITECTURE.md:4137` требует `docs/adr/engine-assumptions.md` — сводный список движковых допущений с планом отступления. **NOT IMPLEMENTED**: файла нет, допущения рассыпаны (ADR-0003 — про предел приоритетов init −999…999; ADR-0005 — про то, что `config.change_language_callbacks` в Ren'Py 8.5 мёртв, живой хук — `config.language_callbacks[lang]`).

## 8. Коммиты и git в AI-режиме

Полная конвенция, история типов и scope'ов — [04-development-workflow.md](04-development-workflow.md) § 2–3. Здесь только то, что специфично для агента.

- **Формат тот же, что у человека:** `type(scope): описание по-русски` + непустое тело + трейлер. 35 из 51 коммита — Conventional Commits; 16 ранних — свободная форма, их не переписывают.
- **Трейлер обязателен и единообразен:** `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>` — он есть в **51 коммите из 51**. Это единственная машиночитаемая метка авторства в проекте; терять её нельзя.
- **Тело объясняет «почему», а не пересказывает дифф.** Эталон разбора инцидента — `ff28ba9`: симптом (`FreetypeError`), причина (LFS-указатели вместо шрифтов), две линии защиты, как проверено на реальном артефакте.
- **Ссылки на нормы прямо в теле:** `(ADR-0010)`, `(G6)`, `(раздел 7)`. Это то, что через полгода отвечает на вопрос «зачем это здесь».

**Что обязательно проверить до коммита** (минимум): `vn content lint`, `git status --short`. Перед push — полный набор уровня 3 из § 6.

**Почему релиз — отдельный коммит.** Релизные коммиты `dd1cb3e` (0.1.4) и `9e1170c` (0.1.3) трогают **ровно три файла**: `project.yaml`, `docs/CHANGELOG.md`, `ci/release-manifest.json`. Причина механическая: `release.yml:47-54` первым шагом сверяет тег с `project.yaml: version` и падает при расхождении. Смешав бамп версии с фичей, вы получаете коммит, который нельзя ни откатить без потери фичи, ни перетегировать. Плюс `vn release changelog` вставляет свой блок в начало `CHANGELOG.md` — запускать его надо **до** написания прозы, иначе текст окажется под сгенерированным блоком.

**Ветки.** Сегодня одна ветка `main`, 51 коммит, ноль merge-коммитов — осознанное состояние соло-разработки. Ветка + PR обязательны для правок в `tools/vn/`, `tools/schemas/`, `game/framework/00_core/`, `content/migrations/`, `save_schema` и workflow-файлов: `ci.yml` уже триггерится на `pull_request`, так что ветка ничего не стоит, а откат «плохого» коммита в `main` — это ещё один коммит в истории, поверх которого придётся тегировать.

| **Рост throughput при падении стабильности** | [DORA 2025](https://dora.dev/research/2025/dora-report/): AI — «великий усилитель», связь с delivery stability остаётся отрицательной без сильных тестов и быстрой обратной связи | 373 теста, 4 workflow, smoke-автопилот, сейв-корпус, релизный гейт | не отключать проверки ради скорости |

Отдельно про «сколько мы экономим»: собственное ощущение ускорения ненадёжно в известную сторону. METR в [обновлении от 2026-02-24](https://metr.org/blog/2026-02-24-uplift-update/) сама пометила знаменитый результат «19 % медленнее» как устаревший и перепроектирует эксперимент — цитировать старую цифру как актуальную нельзя. Практический вывод для этого репозитория один: мерить не ощущением, а тем, что не является вами — `vn`, тестами и CI.

## 10. Управление контекстом на этом репозитории

Ограничение простое: контекст заполняется быстро, и качество падает по мере заполнения (`context rot` — см. [Anthropic, effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

**`docs/ARCHITECTURE.md` целиком не грузится.** 4182 строки, 461 296 байт — это ≈230 тысяч символов русского текста, десятки тысяч токенов, и почти всё из этого описывает фазы, которых нет. Загрузив его, агент получает наиболее убедительный в репозитории источник ложных фактов.

**Что читать вместо него:**

| Вопрос | Куда идти | Объём |
|---|---|---|
| «что вообще есть в проекте» | [README.md](README.md) этого хендбука | карта |
| «как устроена подсистема X» | соответствующий файл `docs/handbook/NN-*.md` | 260–930 строк |
| «какая норма это регулирует» | [02-architecture.md](02-architecture.md) § 5–6 — полный справочник G1–G24 / C1–C24 | таблица |
| «почему так решили» | `docs/adr/NNNN-*.md` — 14 файлов по 23–111 строк | точечно |
| «как это называется» | `docs/conventions/naming.md` (30 строк), `folder-layout.md` (39) | целиком |
| «что делает команда» | `vn <cmd> --help` → `tools/vn/src/vn/cli.py` | точечно |
| «нормативная формулировка» | `../ARCHITECTURE.md:<строка>` по ссылке из хендбука | 5–40 строк |

**Зачем существует этот хендбук.** Ровно затем: 38 файлов how-to плюс карта `README.md`, каждый отвечает на один практический вопрос, каждый механизм помечен статусом, `ARCHITECTURE.md` цитируется по номерам строк. Это разница между «загрузить 450 КБ целевого документа» и «загрузить 15 КБ проверенного факта». До хендбука практические how-to существовали ровно для трёх областей: `docs/pipeline/phase-0.md` (окружение), `docs/runbooks/pipeline-broken-at-night.md` (авария), `docs/pipeline/design-brief-choices.md` (дизайн экрана выбора).

**Гигиена сессии** (правило из [официальных практик](https://code.claude.com/docs/en/best-practices)): если вы поправили агента дважды по одному и тому же поводу — контекст засорён неудачными попытками. Начинать заново с более точным промптом дешевле, чем поправлять третий раз. Новая сессия — между несвязанными задачами: «сцена» / «UI» / «тулинг» / «конвейер ассетов» — это четыре разные задачи.

**Что имеет смысл держать вне контекста:** `game/generated/**`, `game/assets/**`, `build/**`, `.vncache/**`, `*.rpyc`. Все они уже в `.gitignore`, но `.rpyc` физически лежат рядом с `.rpy` в `game/framework/` — при рекурсивном чтении каталога они попадаются. Читать их не нужно никогда.

## 11. Практика 2026: чего в репозитории нет

Всё в этом разделе — **NOT IMPLEMENTED** в репозитории. Ни `CLAUDE.md`, ни `AGENTS.md`, ни `.claude/`, ни `REVIEW.md`, ни хуков здесь не существует (проверено: `find . -maxdepth 3 -iname "CLAUDE.md" -o -iname "AGENTS.md" -o -name ".claude"` → пусто). 51 коммит написан агентом, которому контекст подавали руками. Раздел — про то, что стоит завести, и с какими оговорками.

### 11.1. Инструктивный слой

| Артефакт | Что это | Оговорки, важные для Windows и для этого репо |
|---|---|---|
| `CLAUDE.md` | контекст, загружаемый в каждую сессию: команды сборки, жёсткие правила, грабли | целевой объём — **до 200 строк**; официальная формулировка прямая: раздутый файл приводит к тому, что инструкции игнорируются. `@path`-импорты **не экономят контекст** — они разворачиваются при старте. Файл подаётся как пользовательское сообщение, то есть это контекст, а не принуждение |
| `AGENTS.md` | вендор-нейтральный эквивалент, стандарт под эгидой Agentic AI Foundation (Linux Foundation) | Claude Code читает `CLAUDE.md`, **не** `AGENTS.md`. Симлинк `ln -s` на Windows требует прав администратора или Developer Mode — вместо него `CLAUDE.md`, первой строкой которого стоит `@AGENTS.md`. Если инструмент один — второй файл только создаёт рассинхрон |
| `.claude/rules/` | правила, привязанные к путям через `paths:`-глоб | естественно ложится на зоны этого репозитория (`content/**`, `game/framework/**`, `tools/vn/**`) |
| хуки | детерминированный гейт, который срабатывает всегда | здесь напрашивается очевидный: `vn content lint` + `vn build` как Stop-хук — ровно те две команды, что уже являются приёмкой |

Что **не** надо писать в `CLAUDE.md` этого репозитория: раскладку каталогов и списки модулей — агент выведет их из дерева за один `ls`. Писать надо то, что из дерева не выводится: «`ARCHITECTURE.md` — целевой документ», «генерат не править», «`RENPY_SDK` экспортить вручную», «`config.change_language_callbacks` мёртв», «в экранах только `gui.*` и `vn_loc.t()`». Тест на каждую строку — «если это убрать, агент начнёт ошибаться?».

### 11.2. Spec-driven

Формальный фреймворк ([GitHub Spec Kit](https://github.github.com/spec-kit/), MIT, `/speckit.*`-команды) для этого проекта избыточен: он генерирует в репозиторий заметный объём markdown и вводит второй источник истины, который придётся поддерживать. Лёгкая версия здесь уже работает и называется **бриф**: `docs/pipeline/design-brief-choices.md` — 132 строки, файлы к правке, доступные механизмы, жёсткие контракты, известные проблемы, приёмочные команды. Этого формата достаточно для любой фичи масштаба «новая подсистема».

Полезная оговорка от инженеров Anthropic ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)): спека должна оставаться **высокоуровневой** — ошибка в преждевременно детализированной спеке каскадом уезжает в реализацию. Бриф отвечает на «что должно получиться и чем это проверяется», а не «какими строками кода».

### 11.3. Ревью свежим контекстом

Единственная работающая замена человеческому ревью в соло-режиме — прогон ревьюера в **новой сессии**, которая не писала этот код: агент не предвзят к собственному тексту. Обязательно — перед мержем всего, что трогает сейвы, persistent-данные, `save_schema`, релизный путь и лицензии.

Оговорка из официальных доков: ревьюер, которому поручено найти проблемы, найдёт их даже в здоровом коде — гнаться за каждой находкой значит получить лишние слои абстракции, оборонительный код и тесты на невозможные случаи. Фильтр для этого репозитория: находка принимается, если её можно выразить как нарушение нормы G/C, как падение команды `vn` или как конкретный сценарий поломки у игрока.

## Как изменить / Как расширить

- **Завести `CLAUDE.md`.** До 200 строк, только невыводимые факты (§ 11.1). Проверка качества — снять его и посмотреть, начнёт ли агент ошибаться.
- **Завести Stop-хук `vn content lint && vn build`.** Самая дешёвая автоматизация из возможных: команды уже есть, они быстрые (10 с + 0,3 с на прогретом кэше), и они же — приёмка § 6.
- **Заполнить `CODEOWNERS` реальными хэндлами** и включить branch protection: `ci.yml` уже триггерится на `pull_request`, настраивать больше нечего. Непокрытыми остаются `/content/gallery/`, `/content/achievements/`, `/content/ui/`, `/content/licenses.yaml`, `/packs/`, `/assets_src/`, `/game/fonts/`, `/.github/`.
- **Написать `docs/adr/engine-assumptions.md`** — сводный список движковых допущений (требование `ARCHITECTURE.md:4137`). Стартовое содержимое уже известно: предел приоритетов init −999…999 (ADR-0003), мёртвый `config.change_language_callbacks` (ADR-0005), неявный `Return` в конце `.rpy`, per-machine подпись сейвов.
- **Расширить CLI-уровневые тесты.** Первый прецедент уже есть: `test_release.py:140-192` гоняет `vn pack build` (3 теста) через `click.testing.CliRunner` и стережёт охранника «главы объявлены, генерата нет». Остальная поверхность по-прежнему пуста: `cli.py` (2117 строк) покрыт одной этой командой, а `analyze.py`, `content/scaffold.py`, `psd.py`, `devloop.py` не импортируются ни одним из 373 теста — самое вероятное место, где агент сломает что-то незаметно.
- **Синхронизировать `README.md:43`** («Статус: фаза 0») с реальностью: код закрывает почти всю фазу 1 и половину фазы 2. Устаревший статус в корневом README — первое, что читает агент.

## Чего НЕ делать

- **Не выдавать `ARCHITECTURE.md` за описание реализованного.** Это утверждённый целевой документ; 14 упоминаний `--use-artifact` в нём и ноль реализаций — образцовая иллюстрация.
- **Не отключать проверки ради скорости итерации.** Проверки — единственное, что отличает эту практику от vibe coding в исходном смысле.
- **Не сочинять чеклист «вообще».** Чеклист этого проекта состоит из команд `vn`; всё остальное — литература.
- **Не смешивать релиз с фичей в одном коммите** — `release.yml:47-54` сверяет тег с `project.yaml`.
- **Не начинать новую сессию с «продолжи»** — контекст не переживает `/clear` и `/compact`. План должен лежать файлом в репозитории.
- **Не поправлять агента третий раз по одному поводу** — начать заново дешевле.
- **Не заводить одновременно `CLAUDE.md` и `AGENTS.md` с пересекающимся содержимым** — рассинхрон двух инструкций и есть главная причина дублей систем.
- **Не полагаться на `/rewind`-подобные механизмы как на откат** — единственный настоящий откат здесь git, и то, что записал bash-скрипт, чекпоинтами не покрывается.
- **Не хранить рабочие заметки в корне репозитория.** `log.txt`, `errors.txt`, `traceback.txt` — выхлоп движка, они в `.gitignore:15-17`; временные файлы туда же не класть.
