## 1. Что такое Deck с точки зрения движка: три независимых факта

Новичок обычно склеивает их в один — и потом не может объяснить, почему «на Deck всё как на десктопе».

| Факт | Значение | Кто его создаёт | Зависит от Steam? |
|---|---|---|---|
| **Физический экран** | 1280×800, 16:10 (LCD-модель 7″ ≈ 216 ppi, OLED 7.4″ ≈ 204 ppi) | железо | **нет** |
| **Варианты Ren'Py** `steam_deck`, `medium`, `touch` | включают наш авто-масштаб и фуллскрин | `steamapi.SteamUtils().IsSteamRunningOnSteamDeck()` внутри `steam_init()` (`$RENPY_SDK/renpy/common/00steam.rpy:1052-1059`) | **ДА** — нужны и библиотека `libsteam_api.so` рядом с исполняемым, и валидный App ID |
| **Steam Input** (пад видится как контроллер, раскладка, оверлей, скриншоты) | клиент Steam подменяет устройство ввода | Steam-клиент, а не игра | да, но достаточно «Non-Steam Game» |

Отсюда главное практическое следствие, которое ломает первый прогон почти всем:

> Deck **сам по себе** ничего игре не сообщает. Если игра запущена не как настоящее Steam-приложение с App ID, `renpy.variant("steam_deck")` = `False`, `vn_platform.controller_first()` = `False`, и вы получите десктопный профиль: оконный режим и кегли интерфейса без множителя 1.4. Экран при этом всё равно 1280×800 — то есть вы увидите **самый мелкий возможный** вариант интерфейса и решите, что масштаб не работает.

Цепочка выключения (`00steam.rpy:996-1030`), любое звено — тихий no-op без единой ошибки:

```
нет libsteam_api.so рядом с исполняемым  -> return (has_steam = False)
config.enable_steam == False             -> return
RENPY_NO_STEAM в окружении               -> return
steamapi.InitFlat() не вернул 0          -> exception -> steam = None
```

`config.steam_appid` эмитит наш генерат `game/generated/platform.gen.rpy` из `project.yaml: platform.steam.appid`; сейчас там `define config.steam_appid = None`, и движок при старте **удаляет** `steam_appid.txt` рядом с исполняемым (`00steam.rpy:981-983`), чтобы игра не подцепила чужой App ID. Значит без заполненного `appid` путь «настоящее Steam-приложение» недоступен ни на Deck, ни где-либо ещё.

**`RENPY_NO_STEAM`** — штатный аварийный рычаг движка (`00steam.rpy:1024-1025`): переменная окружения выключает Steam-инициализацию даже при живой библиотеке. Единственный способ сравнить на одной машине «как ведёт себя standalone» и «как ведёт себя Steam-сборка», не переставляя файлы. В хендбуке до этой страницы не упоминался.

## 2. Сборка

### 2.1 Какой пакет нужен

Deck — Linux x86_64 (SteamOS 3, Arch-based). Нужен пакет `linux`. Ren'Py кладёт в архив всё, включая свой Python и библиотеки, — на SteamOS ставить ничего не надо.

```bash
vn release build --flavor public --package linux
```

Что делает команда (`tools/vn/src/vn/cli.py:1762-1816`): `vn build` → релизный гейт (`validate_release`) → `game/build_id.json` → `vn package` → `build-info.json` в каталог дистрибутива. `--flavor` обязателен; `--package` можно повторять.

Для быстрой итерации без гейта: `vn package --package linux` (`cli.py:301-393`) — та же раскладка, но без флейвора, без вотермарки и без исключения NSFW-глобов. Для проверки вёрстки этого достаточно; для проверки того, что уедет игроку, — нет.

### 2.2 Что получается на диске

Каталог: `build/dist/<version>-<flavor>/`, где `<version>` — `project.yaml: version` (сейчас `0.1.5`). Имя архива — `build.directory_name + "-" + <имя пакета>`, где `directory_name` = `build.name` + `-` + `config.version` (`00build.rpy:648-653`, `launcher/game/distribute.rpy:627,1501`). `build.name = "vn"` (`game/options.rpy:21`), `config.version = "0.1.5+8ce8e2c"` (генерат `game/generated/version.gen.rpy:8`).

| `--package` | Формат Ren'Py 8.5.3 | Имя файла | Годится для Deck? |
|---|---|---|---|
| `linux` | `tar.bz2` (`00build.rpy:424`) | `vn-0.1.5+<sha>-linux.tar.bz2` | **да, это то, что нужно** |
| `win` | `zip` (`:426`) | `vn-0.1.5+<sha>-win.zip` | нет (только под Proton, а это не то, что вы тестируете) |
| `mac` | `app-zip` + `app-dmg` (`:425`) | `…-mac.zip`, `…-mac.dmg` | нет |
| `market` | `bare-zip` (`:427`) | `…-market.zip` — win+linux+mac в одном архиве без префикса каталога | можно, но внутри лишние платформы |
| `steam` | `zip`, **скрытый** пакет (`:429`) | `…-steam.zip` — win+linux+mac одним зипом | это то, что просит депот Steam; у `vn package` этого имени в help нет, но `--package steam` уйдёт в launcher как есть (`distribute.rpy:1813,1824-1825`) |

Внутри linux-архива: каталог `vn-0.1.5+<sha>-linux/` с `vn.sh` (переименованный `renpy.sh`, `distribute.rpy:1297-1310`) и `lib/py3-linux-x86_64/vn` (`:1161-1165`). Оба помечены битом исполнения; `tar.bz2` его сохраняет, зипы Ren'Py тоже (`launcher/game/package_formats.rpy:94`).

### 2.3 `vn release steam` принимает linux-`tar.bz2` — но обёртку депота никто не проверял

`steam_stage_content` (`tools/vn/src/vn/release.py:266-309`) знает, что формат пакета зависит от платформы, и распаковывает архив **по фактическому типу файла**:

```python
_DIST_SUFFIX = {                              # release.py:158-162
    "windows": ("-win", (".zip",)),
    "linux": ("-linux", (".tar.bz2", ".zip")),   # порядок = приоритет
    "mac": ("-mac", (".zip",)),
}
...
if archive.name.endswith(".tar.bz2"):         # _extract_archive, release.py:174-184
    with tarfile.open(archive, "r:bz2") as tf: tf.extractall(dest)
else:
    with zipfile.ZipFile(archive) as zf: zf.extractall(dest)
```

То есть `--package linux` (`tar.bz2`) — ровно то, что раскладка ждёт; `.dmg` игнорируется намеренно (кроссплатформенно не распаковать, `app-zip` несёт то же содержимое). Ожидаются при этом **только платформы с объявленным депотом** в `platform.steam.depots`, так что ради linux-депота не нужно собирать win и mac. Это зафиксировано тестом на настоящих архивах: `tools/vn/tests/test_platform.py:96-121` кладёт win-`zip` **и** linux-`tar.bz2` и требует, чтобы встали оба депота с `errors == []`.

**Что это значит для вас сегодня:** ручной шаг для linux-депота больше не нужен. Путь «выложить в тестовую ветку Steam и скачать на Deck» (§3.1) блокирует не формат архива, а отсутствие приложения в Steamworks: `platform.steam.appid: null` и ключа `depots` в `project.yaml` нет, поэтому `vn release steam` останавливается на первом шаге. Ручная раскладка остаётся годным обходом, если нужно подменить содержимое депота:

```bash
mkdir -p build/steam/content/public/linux
tar xjf build/dist/0.1.5-public/vn-*-linux.tar.bz2 -C build/steam/content/public/linux
# получится build/steam/content/public/linux/vn-0.1.5+<sha>-linux/vn.sh
# ВНИМАНИЕ: при ручной раскладке обёртку vn-<версия>-linux/ надо снять самому —
# vn release steam делает это за вас (см. ниже), а tar/unzip — нет.
```

**Каталог-обёртку раскладка теперь снимает — вопрос закрыт.** `tar` и `zipfile.extractall` её сохраняют, потому что launcher её добавляет: у форматов `zip` и `tar.bz2` четвёртое поле `FORMATS` (`prepend`) равно `True` (`launcher/game/distribute.rpy:1513-1530`, применение — `:1580-1581`), а у `app-zip` — `False`. Поэтому после распаковки вызывается `_flatten_wrapper_dir` (`release.py:186-212`): единственный верхний каталог разворачивается на уровень выше, mac-бандл (`*.app`) не трогается, коллизия имён — `ReleaseError`, и платформа тогда **не** попадает в `staged` (депот с чужой раскладкой хуже отсутствующего).

Следствие для Steamworks: **Launch Options задаются от корня депота и не содержат версии** — `vn.sh` для Linux, `vn.exe` для Windows. Смена версии игры их больше не меняет.

Чего это всё ещё не доказывает: разворачивание проверено тремя тестами на **синтетических** архивах (`test_platform.py:112-157`), а не на артефакте живого `launcher distribute`, и через реальный SteamPipe депот ни разу не проходил. Первую выкладку по-прежнему сверяют глазами.

## 3. Три пути доставки на Deck

Сравнение сначала, процедуры — ниже. Разница между путями не в удобстве, а в том, **что игра узнаёт о себе**.

| | А. Через Steam (тестовая ветка) | Б. Вручную + Non-Steam Game | В. `ssh`/`scp` из Desktop Mode |
|---|---|---|---|
| Нужен App ID в `project.yaml` | **да** | нет | нет |
| Нужна `libsteam_api.so` на build-машине | **да** | нет | нет |
| `renpy.variant("steam_deck")` | **True** | `False` | `False` (если не задать `RENPY_VARIANT`) |
| `controller_first()` → фуллскрин + масштаб 1.4 | **автоматически** | нет (форсировать вручную) | нет (форсировать вручную) |
| Steam Input, оверлей, скриншоты `STEAM+R1` | да | **да** (даёт клиент, не игра) | нет, пока не добавили в Steam |
| Ачивки, `dlc_installed`, Steam Cloud | да | нет | нет |
| Экранная клавиатура Deck для `renpy.input` | да | нет (`00steam.rpy:704-705` гейтит по варианту `steam_deck`) | нет |
| Готово в этом репозитории | **нет** — `appid: null`, ключа `depots` нет, аплоад ручной (раскладка депотов при этом рабочая, §2.3) | да | да |
| Скорость итерации | минуты (аплоад + докачка) | ~минута | секунды |

Практический вывод: **пути Б и В проверяют вёрстку и производительность, путь А проверяет платформу.** Оба нужны, и путь А остаётся обязательным перед `setlive default` (`ci/steam/README.md`).

### 3.1 Путь А: через Steam, в тестовую ветку

Предпосылки, которых в репозитории нет: `platform.steam.appid` + `platform.steam.depots` в `project.yaml`, `libsteam_api.so` в `$RENPY_SDK/lib/py3-linux-x86_64/`, аккаунт с правами на аплоад. Как это включается и что генерирует `vn release steam` — [39-platforms.md](39-platforms.md) §3.

```bash
vn release build --flavor public --package linux    # достаточно платформ с депотом (§2.3)
vn release steam --flavor public --branch beta      # -> build/steam/app_build_public.vdf
#   ЗДЕСЬ упрётесь в appid/depots: в этом репозитории их нет — exit 1 на первом шаге
steamcmd +login <account> +run_app_build build/steam/app_build_public.vdf +quit
```

Дальше, уже на Deck: Steam → библиотека → игра → шестерёнка → **Properties → Betas** → выбрать ветку `beta` → дождаться докачки → Play.

Что нужно знать про ветку: `--branch` подставляется в `"SetLive"` VDF-шаблона (`release.py:168-234`) и публикует билд **в существующую** ветку. Ветку `beta` заводит человек в Steamworks (App Admin → Builds → Betas); в несуществующую ветку `SetLive` не публикует. Переключение default-ветки — тоже вручную в Steamworks, **после** прогона на живом Deck.

Полезное, чего мы не используем: движок умеет спросить у Steam текущее имя беты — `achievement.steam.get_current_beta_name()` (`00steam.rpy:227`). Одна строка в `035_platform.rpy` дала бы «какую ветку я запустил» в `log.txt` и в крэш-отчёт. STATUS: NOT IMPLEMENTED.

### 3.2 Путь Б: скопировать архив на Deck и добавить как Non-Steam Game

Всё делается на самом Deck.

1. Кнопка **STEAM** → Power → **Switch to Desktop**.
2. Перекинуть архив: флешка/microSD, KDE Connect, `wget` из локальной сети — любым способом. Класть в `/home/deck/` (или на microSD `/run/media/deck/<label>/`). **Корневая ФС SteamOS смонтирована только для чтения** — `/usr`, `/opt` и подобное не годятся; `/home` пишется всегда и переживает обновления SteamOS.
3. Распаковать и разрешить исполнение:
   ```bash
   mkdir -p ~/Games && cd ~/Games
   tar xjf ~/vn-0.1.5+*-linux.tar.bz2
   cd vn-0.1.5+*-linux
   chmod +x vn.sh lib/py3-linux-x86_64/vn
   ./vn.sh                     # первый запуск из Desktop Mode, чтобы увидеть stderr
   ```
4. Steam (Desktop Mode) → **Games → Add a Non-Steam Game to My Library → Browse** → выбрать `vn.sh`. В свойствах ярлыка полезно сразу выставить **Controller Layout**, иначе Steam Input по умолчанию отдаст паду профиль «Keyboard (WASD) and Mouse», а не геймпад.
5. STEAM → Power → **Switch to Gaming Mode**, запустить ярлык.

**Что вы получаете и чего нет.** Steam-клиент даёт Steam Input (пад видится игре как обычный контроллер через SDL), оверлей, скриншоты, Steam Cloud не даёт (Non-Steam Game не имеет депотов). **Игра при этом не Steam-приложение:** `libsteam_api.so` рядом с `lib/py3-linux-x86_64/vn` отсутствует, `config.steam_appid` = `None`, `steamapi.InitFlat` не вызывается → `achievement.steam` = `None` → `vn_platform.backend()` = `"standalone"`, `is_steam_deck()` = `False`.

Проверяется это одной строкой: `035_platform.rpy:89` пишет `vn_log("platform: %s" % vn_platform.describe())` **только внутри** `if vn_platform.steam() is not None`. Значит:

```bash
grep '^\[vn\] platform:' ~/Games/vn-*/log.txt
# строка есть  -> Steam живой, deck=/bigpicture=/touch= показывают правду
# строки нет   -> standalone: платформенные варианты выключены, это ожидаемо для пути Б
```

`log.txt` пишется в каталог установки игры (`config.logdir` = `config.basedir`, `$RENPY_SDK/renpy.py:218-230`), с откатом в `$TMPDIR/renpy-log.txt`, если каталог только для чтения. Пишется и в релизной сборке — не только в dev (`renpy/log.py:247`, `developer=False`).

**Как получить правильный профиль интерфейса на этом пути.** Форсировать варианты окружением — движок принимает `RENPY_VARIANT` раньше любой автодетекции и **полностью заменяет** список (`renpy/main.py:157-160`):

```bash
RENPY_VARIANT="steam_deck medium touch" ./vn.sh
```

В ярлыке Steam то же самое ставится в **Launch Options**: `RENPY_VARIANT="steam_deck medium touch" %command%`. После этого `controller_first()` = `True`, интерфейс получает масштаб 1.4 и фуллскрин по умолчанию — то есть вы видите ровно ту вёрстку, которую увидит покупатель. Steam-специфика (ачивки, DLC, оверлей-API) при этом всё равно выключена, и это правильное разделение: вёрстку проверяем так, платформу — только путём А.

### 3.3 Путь В: `ssh` + `scp` с рабочей машины

Самый быстрый цикл: пересобрал → залил → запустил, не трогая Deck руками. Процедура — SteamOS, вне репозитория.

На Deck, один раз, в Desktop Mode (Konsole):

```bash
passwd                                   # у пользователя deck по умолчанию пароля НЕТ,
                                         # а sshd без пароля вас не пустит
sudo systemctl enable --now sshd          # включить сейчас и после перезагрузок
ip -4 addr show | grep -w inet            # узнать адрес
```

С рабочей машины:

```bash
DECK=deck@192.168.1.42
ssh $DECK 'mkdir -p ~/Games'
scp build/dist/0.1.5-public/vn-*-linux.tar.bz2 $DECK:~/Games/
ssh $DECK 'cd ~/Games && tar xjf vn-*-linux.tar.bz2'
ssh $DECK 'cd ~/Games/vn-*-linux && chmod +x vn.sh lib/py3-linux-x86_64/vn'
# запуск с прокинутым дисплеем Gaming Mode:
ssh $DECK 'cd ~/Games/vn-*-linux && DISPLAY=:0 RENPY_VARIANT="steam_deck medium touch" ./vn.sh'
```

Три предупреждения, которые экономят вечер:

- **`chmod +x` обязателен, если файлы прошли через `zipfile.extractall`.** Python не восстанавливает права из зипа. Для `build/steam/content/**` это зависит от платформы: linux-депот `vn release steam` распаковывает через `tarfile` (`release.py:179-182`), и бит исполнения приезжает сам; windows/mac идут через `zipfile` (`:183-184`) и остаются **без** него — если будете копировать оттуда, а не из архива, права выставляйте руками.
- **Обновление SteamOS может выключить `sshd`** (системный раздел перезаписывается образом). `systemctl enable` придётся повторить; `/home` не страдает.
- **`ssh`-сессия — не сеанс рабочего стола.** Без `DISPLAY=:0` (Gaming Mode) игра не найдёт дисплей и упадёт на инициализации SDL. Проще: держать игру ярлыком в Steam, а по `ssh` только обновлять файлы.

## 4. Ren'Py variants: полная карта

Вариант — строка в `config.variants`, по которой движок выбирает объявление `screen`/`style`. Список формируется один раз при старте, до всех `init` (`renpy/main.py:341`), и `renpy.variant("x")` — просто проверка вхождения.

### 4.1 Откуда берётся каждый вариант (проверено по SDK 8.5.3)

| Вариант | Где выставляется | Когда активен |
|---|---|---|
| `RENPY_VARIANT` из окружения | `renpy/main.py:157-160` | **заменяет весь список целиком** + `None`; вся автодетекция пропускается |
| `pc`, `large` | `main.py:298,300` | любой десктоп (Windows/Linux/macOS) — наш обычный случай |
| `steam_big_picture` | `00steam.rpy:1049-1050`, по `SteamUtils().IsSteamInBigPictureMode()` | Steam-клиент в режиме Big Picture; **вставляется в начало**, `large` остаётся |
| `steam_deck` + `medium` + `touch`, и `large` **удаляется** | `00steam.rpy:1052-1059`, по `SteamUtils().IsSteamRunningOnSteamDeck()` | Steam Deck; `large` снимается сознательно — Deck по геометрии ближе к планшету |
| `mobile`, `android`, `ios`, `phone`/`tablet`, `small`/`medium`, `touch`, `chromeos`, `firetv`, `tv` | `main.py:163-244` | Android/iOS; `tv` — только Android-устройство с `android.hardware.type.television` |

Важные следствия, о которых легко забыть:

- **`tv` к Big Picture отношения не имеет.** Это Android TV. Телевизор через Big Picture даёт `steam_big_picture`, и `large` при этом остаётся.
- **`steam_deck` и `steam_big_picture` независимы** и в принципе могут оказаться оба (Deck в Gaming Mode). Проверять это надо на живом устройстве: обе строки печатает `vn_platform.describe()` в `log.txt`. Наш `controller_first()` = `is_steam_deck() or is_big_picture()` — то есть от их сочетания не зависит, а вот `gui.overscan_pad` = `48` только при `is_big_picture()` (`scale.rpy:42`). Если Gaming Mode Deck отчитается как Big Picture, встроенный экран получит ненужный отступ 48 px. **Это надо проверить глазами на первом же прогоне пути А** и, если так, сузить условие до «Big Picture и не Deck». STATUS: не проверено ни разу.
- **`RENPY_VARIANT` заменяет, а не дополняет.** `RENPY_VARIANT="steam_deck"` уберёт и `pc`, и `large`. Полный эмулирующий набор для Deck — `"steam_deck medium touch"`, ровно то, что вставил бы движок.

Прямых обращений к `renpy.variant()` вне фасада **нет** — проверяется grep'ом и гард-тестом `test_platform.py:183-193`:

| Потребитель | Что делает | Код |

### 4.3 Как правильно добавлять платформенную адаптацию

Правило: **capability-запрос в фасаде + токен `gui.*`.** Ни `renpy.variant()` в экране, ни второй вариант экрана.

```renpy
# 1. Новый вопрос к платформе — только 035_platform.rpy (init -960):
def is_handheld():
    return is_steam_deck()          # завтра сюда добавится Switch/мобилка

# 2. Новый токен — только 20_ui/scale.rpy, между init -4 и init offset = -3
#    (то есть ДО gui.rpy на -2, который его использует):
define gui.touch_hit_pad = (12 if vn_platform.has_touch() else 0)

# 3. Экран читает ТОЛЬКО токен:
style vn_nav_button:
    padding (gui.sp_m, 13 + gui.touch_hit_pad)
```

Почему именно так:

- **Копия экрана под платформу — это два экрана, которые расходятся.** Локализация, панели ADR-0009, контракты id (`window`/`who`/`what`), QA-автопилот — всё придётся править дважды, и вторая копия отстанет молча.
- **`if renpy.variant(...)` в экране прячет платформу в вёрстке.** Следующая платформа = рефакторинг всех экранов; и гард-тест точки касания это не поймает (он ищет `_renpysteam`/`steamapi`, а не `variant`).
- **Порядок init обязателен.** `gui.rpy` (`init offset = -2`) умножает кегли на уже посчитанный `gui.ui_scale`. Токен, объявленный позже `-2`, не успеет; объявленный до `init -4` — не увидит `vn_platform` (store создаётся на `init -960`, то есть раньше, это норма). Окно для платформенных токенов — `scale.rpy`, между `-4` и `offset = -3`. Правка приоритета здесь молча даёт масштаб `1.0` без единой ошибки — самая хрупкая связка в проекте.
- **Только увеличение (`>= 1.0`).** Генерируемые 9-patch панели считают минимум `2*Borders` от базовых кеглей (`game/generated/registry/ui_frames.gen.rpy`: `vn_frame_choice_hover` — минимум 60×60 px). Уменьшение сплющит фоны выборов и чипов.

## 5. Геометрия: 1280×800 против виртуальной сетки 1920×1080

Вся вёрстка проекта написана в пикселях сетки `gui.init(1920, 1080)` (`game/gui.rpy:9`, источник — `project.yaml: render.screen`). Движок растягивает эту сетку на физическое окно, сохраняя пропорции.

**Расчёт для Deck.** Сетка 16:9 (1.778), экран 16:10 (1.600) — экран «выше». Масштаб выбирается по узкому измерению:

```
по ширине:  1280 / 1920 = 0.6667
по высоте:   800 / 1080 = 0.7407      -> берётся минимум, 0.6667
виртуальные 1080 px -> 1080 * 0.6667 = 720 физических
неиспользованная высота: 800 - 720 = 80 px  ->  по 40 px сверху и снизу
```

Итог: **letterbox 40 px вверху и внизу, картинка 1280×720 по центру.** Цвет полос — `config.gl_clear_color`, по умолчанию `"#000"` (`$RENPY_SDK/doc/config.html`, раздел `gl_clear_color`); мы его не переопределяем (grep по `game/` — 0 попаданий), то есть полосы чёрные. Это не баг и настраивать нечего: 16:10 не совпадает с 16:9, и альтернатива — обрезать кадр.

Что из этого следует практически:

| Следствие | Число | Почему важно |
|---|---|---|
| Один виртуальный px = **0.667 физического** | | любой размер из `gui.*` делите на 1.5, чтобы понять реальный кегль |
| `draw_per_virt` = **0.667** (< 1.0) | | **`@2`-варианты на Deck не грузятся вообще**: `get_oversampled_image` возвращает базовый образ при `draw_per_virt <= 1.0` (`renpy/display/im.py:743-746`). Настройка «Качество текстур» (`095_quality.rpy`) на Deck ни на что не влияет — опускать уже некуда |
| Оверсэмпл текста = **0.667** | | шрифты растеризуются в физическом размере (`renpy/text/text.py:715`), то есть кегль 21 виртуальный превращается в 14 реальных px |
| Дока к внешнему 4K-экрану | `draw_per_virt` → 2.0 | тогда `@2` включается, память сцены считается по крупному варианту (§7.5) |
| Полосы 40 px — вне вёрстки | | элемент с `ypos 1079` физически не срезается, он просто у самой кромки кадра. На встроенном экране Deck overscan'а нет, поэтому `gui.overscan_pad` = 0 — это правильно |

## 7. Чеклист прогона на Deck

Порядок выбран так, чтобы каждый следующий пункт опирался на уже проверенное. Всё, что ниже, проверяется **только глазами и руками**: движковый `lint` не видит ни обрезанного текста, ни сплющенной панели, а `vn test smoke` не умеет нажимать кнопки пада.

### 7.1 Окружение — сначала подтвердить, потом смотреть

```bash
grep '^\[vn\] platform:' log.txt
# ожидаемо на пути А: [vn] platform: steam deck=True bigpicture=? touch=True
```

Если строки нет — вы на пути Б/В и обязаны были задать `RENPY_VARIANT`, иначе всё остальное в чеклисте вы проверяете не на том профиле. Отдельно зафиксируйте фактическое `bigpicture=` — от него зависит `gui.overscan_pad` (см. §4.1).

### 7.2 Управление (Steam Input + пад)

Раскладка пада — **одно место**, `game/framework/20_ui/input.rpy:29-41`; дефолты движка (`$RENPY_SDK/renpy/common/00keymap.rpy:164-217`) не переопределяются, только дополняются. Что должно работать:

| Кнопка | Ожидание | Откуда | Проверять в |
|---|---|---|---|
| **A** / **RT** | продвинуть реплику, нажать кнопку, активировать слайдер, **подтвердить текстовый ввод** | `pad_a_press`, `pad_righttrigger_pos` → `dismiss`, `button_select`, `bar_activate` (`00keymap.rpy:182-183`) + наше `input_enter` (`input.rpy:37-38`) | say, любое меню, поле ввода |
| **B** | game_menu; **в модалках** — отмена | `pad_b_press` → `game_menu` (`:184`); в модалке перехватывает `key "game_menu"` из `vn_modal_dialog` (`components.rpy:173`) | say → открылось меню; `confirm` → закрылось только окно |
| **X** | `button_alternate` | `:177` | ни к чему не привязано в наших экранах — нажатие не должно ничего ломать |
| **Y** | скрыть интерфейс | `pad_y_press` → `hide_windows` (`:176`) | say: quick menu и текст исчезают, картинка остаётся |
| **LB** / **LT** / **Back** | rollback (назад по репликам) | `:165-171` | say |
| **RB** | rollforward | `:179-180` | say после rollback |
| **LB** / **RB** | **дополнительно** листание вьюпорта (`viewport_pageup`/`pagedown`) | наше дополнение, `input.rpy:33-36` | история, галерея, достижения, список языков, трейсбек крэш-экрана |
| **LB** / **RB** в просмотрщике галереи | предыдущий/следующий элемент | `gallery.rpy:168-169` | просмотрщик |
| **L3** (клик левого стика) | `toggle_skip` | наше, `input.rpy:30` | say |
| **R3** (клик правого стика) | `toggle_afm` (авто-чтение) | наше, `input.rpy:31` | say |
| **Start** / **Guide** | game_menu | `:173-174` | say |
| **dpad** / стики | перемещение фокуса, движение слайдера, скролл | `:186-216` | все меню |

Отдельно проверьте **grab-паттерн слайдеров**: A на слайдере захватывает его (`Bar.event`, `renpy/display/behavior.py:2549-2556`), затем dpad влево/вправо меняет значение, второе A отпускает (`:2614-2621`). Пока слайдер захвачен, dpad **не** уводит фокус. Признак захвата — только смена цвета (`hover_`-вариант), поэтому у `style vn_slider` обязательны `hover_*`/`selected_*` (`components.rpy:351-362`). Если захваченный слайдер визуально не отличается от обычного — на паде это читается как «не работает».

**Почему `input_enter` подсажен к A и RT, а не к свободной кнопке.** Свободных не осталось: A/B/X/Y, LB/LT/Back = rollback, RB = rollforward, Start/Guide = game_menu, dpad и стики = фокус, L3/R3 мы заняли под skip/auto. У движка подтверждение ввода висит **только** на `Enter`/`KP_Enter` клавиатуры, поэтому первое же `renpy.input` на Deck стало бы тупиком: экранную клавиатуру движок покажет сам, а «ОК» нажать нечем. Конфликт мнимый — `input_enter` забирает только **живое** editable-поле (`renpy/display/behavior.py`, `Input.event`: `if not self.editable: return None`), а `screen input` кнопок не содержит. На клавиатуре у движка та же схема: `K_RETURN` — это и `dismiss`, и `input_enter`.

**Оговорка (не дефект):** если однажды появится экран с полем ввода **и** кнопками одновременно, A подтвердит ввод, а не нажмёт кнопку. Единственное такое место сегодня — движковая консоль (dev-only).

**Подсказки управления не должны содержать клавиатурной лексики.** «Esc» на Deck игроку не нажать, поэтому строка подсказки объявляется **парой ключей** — `<key>_kbd` и `<key>_pad`, — а выбирает между ними `vn_ui.hint(key)` (`components.rpy:142-153`), спрашивая `vn_platform.controller_first()` на каждый вызов. Сегодня так сделана одна подсказка (`ui.history.hint_kbd` / `..._pad`, экран истории); все новые обязаны следовать той же конвенции. Это второй потребитель `controller_first()` — после `gui.ui_scale`. Автоматической проверки «на каждый `vn_ui.hint("X")` есть оба ключа» пока нет — см. [42-big-picture.md](42-big-picture.md) §5.5.

Два места, где Steam Input вмешивается и это надо увидеть своими глазами:

- **Профиль ярлыка.** Non-Steam Game по умолчанию может получить раскладку «клавиатура+мышь» — тогда dpad будет двигать курсор, а не фокус. Ставьте Gamepad-профиль в свойствах ярлыка.
- **Тачпады.** По умолчанию правый тачпад — мышь. Наши экраны от мыши не зависят, но hover-состояние при этом будет прыгать между «фокус с пада» и «курсор» — это нормально и не баг.

**Чего в игре нет:** ни экрана настроек управления, ни калибровки пада. Движок это умеет — `GamepadCalibrate()` / `GamepadExists()` (`00gamepad.rpy:254-278`) и готовая секция «Gamepad» с Enable/Disable/Calibrate в служебном экране `_choose_renderer` (`00gltest.rpy:110-128`), который открывается **Shift+G** (`00keymap.rpy:54`, не гейтится `config.developer`). На Deck без клавиатуры игрок туда не попадёт. Подробнее — [42-big-picture.md](42-big-picture.md) §5.

### 7.3 Тачскрин

Вариант `touch` на Deck выставляется вместе с `steam_deck` (`00steam.rpy:1059`), и движок переводит `renpy.display.touch = True` (`renpy/main.py:342`), то есть hover-состояния перестают возникать от «наведения». Наш фасад его опрашивает (`has_touch()`), но **ни один экран решения по нему не принимает** — hit-area под палец нигде не увеличивается.

Что проверять пальцем: say (тап продвигает текст), варианты выбора (ряд ≈ 65 виртуальных px = 43 физических — проходит), quick menu (`padding (13, 17)` + `tiny` 18 → ≈ 52 виртуальных px = 35 физических — на грани), кнопка удаления сейва `×` (`vn_slot_delete`, `components.rpy:335-338`: `padding (12, 6)` — самый мелкий кликабельный элемент в игре), вкладки галереи (`vn_gal_tab`: 6+19+6 ≈ 31 виртуальный px = 21 физический — **мелко для пальца**).

STATUS: PARTIAL. Норма «≥ 48 px» соблюдена сознательно только в quick menu (`quick_menu.rpy:4`); сплошного аудита hit-area не было. Рычаг для исправления уже есть и не требует правки экранов — новый токен `gui.*` в `scale.rpy` по образцу §4.3.

### 7.4 Экранная клавиатура

Движок умеет штатную клавиатуру Deck и включает её **сам**: `keyboard_periodic()` вызывается из Steam-callbacks только при `renpy.variant("steam_deck")` (`00steam.rpy:704-705`), и когда движок сообщает о наличии текстового поля (`renpy.display.interface.text_rect`), вызывается `SteamUtils().ShowFloatingGamepadTextInput(...)` (`00steam.rpy:790-792`), плюс слои сдвигаются вверх переходом `_KeyboardShift`, чтобы поле не оказалось под клавиатурой. Закрытие — `DismissFloatingGamepadTextInput()` (`:803-804`).

Проверять сегодня **нечего**: `renpy.input` в проекте не вызывается ни разу (grep по `game/` и `tools/vn/src/` — 0 попаданий). `screen input(prompt)` объявлен (`core_screens.rpy:59-66`) как контракт движка, но в него никто не заходит: сейв пишется `FileSave(slot)` без имени (`components.rpy:277`), поиска и полей ввода в UI нет.

Практический вывод для будущего: первая же фича с текстовым вводом (имя героя, подпись сейва) на Deck заработает бесплатно, а **вне** Deck на паде — нет: OSK движка гейтится вариантом `steam_deck`, и в Big Picture на десктопе поле ввода останется без клавиатуры. Разбор и предлагаемое решение — [42-big-picture.md](42-big-picture.md) §5.

### 7.5 Производительность и время загрузки

Два числа, оба уже есть в проекте.

**Cold start.** Бюджет `budgets.cold_start_s: 30` (`project.yaml:63`). Меряется **только** в `vn test smoke`: `vn_qa._T0` берётся на `init` (`030_flow.rpy:94`), результат пишется в `.vncache/smoke/startup.txt`, сравнение с бюджетом — `cli.py:1608-1616`. На Deck запустить `vn test smoke` нельзя (нет SDK и тулинга), поэтому измеряйте секундомером от нажатия Play до появления главного меню. Ориентир из `project.yaml:63`: CI-раннер на llvmpipe ~14 c, RTX ~1 c; Deck — между ними, ближе к нижней границе.

**Память образов.** Реальный потолок производства — не диск, а кэш декодированных образов: при переполнении Ren'Py не падает, а перестаёт предзагружать и начинает перерасшифровывать образы посреди сцены — игрок видит необъяснимые фризы при зелёной сборке (докстринг `tools/vn/src/vn/assets/memory.py:1-9`). Проверяется до выезда на Deck:

```
$ vn assets memory --scale 1
кэш образов: 1024 МБ -> 268 Мпикс; бюджет сцены 89.5 Мпикс (3 поколения), масштаб @1
  ch01_s030           10.3 Мпикс    12%
      ui+текстбокс                    4.17
      bg rooftop/day                  2.78
      mira (a)                        0.41
      shot sunset                     2.96
рекомендуемый render.image_cache_mb: 119
память: OK
```

`--scale 1` — это ровно случай Deck: `draw_per_virt` = 0.667 < 1, `@2` не грузятся (§5), сцена стоит в 2.8 раза дешевле, чем на 4K-мониторе (`--scale 2` даёт 28.5 Мпикс на той же сцене). Значит **Deck — не узкое место по памяти образов, узкое место — 4K-монитор.** Тот же анализ гоняется внутри `vn build` и валит сборку сообщением «бюджет памяти сцены превышен» (`cli.py:176-203`).

Чего в проекте нет: замера FPS, профиля GPU, бюджета энергопотребления. STATUS: NOT IMPLEMENTED. Штатные инструменты движка на месте и работают в релизной сборке: оверлей производительности — **F3** (`00keymap.rpy:155`, обработчик `ToggleScreen("_performance")` на `:461`), выбор рендерера — **Shift+G**. На Deck к ним нужна клавиатура (или Steam-раскладка с назначенными клавишами).

### 7.6 Видео

Профиль энкода зафиксирован: WebM + `libvpx-vp9` + `yuv420p`, без звука по умолчанию (`tools/vn/src/vn/assets/video.py:100-111`). Декодирует **FFmpeg внутри движка, программно** — hardware-декодера у Ren'Py нет; аппаратно ускоряется только конверсия цвета, и именно поэтому `yuv420p` обязателен (`$RENPY_SDK/doc/movie.html`: «YUV444 movies are not hardware accelerated, use YUV420 or YUV422 instead»). На четырёхъядерном Van Gogh это заметная нагрузка: 1080p VP9 — то, что надо проверить на Deck в первую очередь, особенно **под экраном выбора**, где поверх лупа рисуется полупрозрачный scrim и стек кнопок (`choice.rpy:34-35`).

Честная оговорка: в репозитории **нет чем это проверить**. Единственное видео — плейсхолдер 256×144, 2 c (`game/assets/mov/demo/ambient.webm.meta.json`: `width: 256, height: 144`). Пока не появится настоящий 1080p-луп, вопрос «тянет ли Deck наше видео» остаётся открытым.

Постер-кадр закрывает вторую половину проблемы: `Movie(play=…, loop=True, image="assets/mov/demo/ambient.poster.webp")` (`game/generated/registry/images.gen.rpy:15`) — пока первый кадр не декодирован и на платформах, где видео не играет, вместо прозрачной вспышки виден статичный кадр.

### 7.7 Сейвы, автосейв, suspend/resume

**Где лежат сейвы на Deck.** `~/.renpy/vn-1755000000/` — `config.save_directory` (`game/options.rpy:7`) внутри платформенного корня для Linux (`$RENPY_SDK/renpy.py:200-202`). Полезные рычаги: `RENPY_PATH_TO_SAVES` в окружении (`renpy.py:172-173`) и каталог `Ren'Py Data` рядом с игрой — тогда сейвы становятся портативными (`renpy.py:176-186`).

> Осторожно при настройке Steam Auto-Cloud: тот же код для Windows даёт `%APPDATA%/RenPy/<save_directory>` (`renpy.py:194-196`), то есть Roaming. Формулировка `%LOCALAPPDATA%` в [39-platforms.md](39-platforms.md) §6 и `ci/steam/README.md` требует перепроверки против этого кода до заполнения Auto-Cloud-путей в Steamworks.

**Что проверять.** Сохранение в слот (сетка 3×2, 4 страницы + «Авто» + «Быстрые» — `core_screens.rpy:244-257`), загрузка, страница квиксейвов (`FilePage("quick")`, `:245` — без этого пункта `QuickSave()` некуда было бы загрузить), удаление слота (свой `Confirm`, `components.rpy:276-277`), миниатюры слотов (`config.thumbnail_width/height` = `gui.slot_width`/`slot_thumb_height`, `core_screens.rpy:15-16`).

**Suspend/resume.** Deck засыпает по кнопке питания, и это **не** мобильный сценарий: `check_suspend` реагирует на `APP_WILLENTERBACKGROUND` (`renpy/display/core.py:1934-1939`), который SDL на Linux-десктопе не присылает. Значит `mobile_save()` не срабатывает, игра просто замирает вместе с процессом. Защита — штатный автосейв: `config.has_autosave = True`, `autosave_slots = 10` (`game/options.rpy:8-9`), частота по умолчанию `autosave_frequency = 200` интеракций (`renpy/config.py:331`) плюс автосейв на выборе (`config.autosave_on_choice = True`, `:579`).

Проверять так: сцена → sleep → wake → продолжить (звук должен вернуться, музыка не оборваться, кадр отрисоваться), затем sleep на **несколько часов** → wake, затем принудительное завершение через Steam при спящей игре → перезапуск → «Продолжить» из главного меню (`Continue(confirm=False)`, `core_screens.rpy:181-189`) должен поднять автосейв, а не отбросить в начало главы.

### 7.8 Оверлей Steam

Оверлей — целиком движковый: `steam.overlay_needs_present` в `config.needs_redraw_callbacks` и позиция тостов `POSITION_TOP_RIGHT` на init (`00steam.rpy:1045-1047`). Проверяется только на пути А. Что смотреть: **STEAM+X** (или Guide) открывает оверлей поверх игры, игра при этом не крашится и не теряет звук; после закрытия кадр перерисовывается.

Наш фасад умеет спросить, открыт ли оверлей (`vn_platform.overlay_enabled()`, `035_platform.rpy:43-48`), но **потребителей у метода нет ни одного** — это задел. Практическое следствие: наш тост `notify` (`core_screens.rpy:463-471`) может нарисоваться под оверлеем, и мы этого не подавляем.

### 7.9 Скриншоты

Два независимых механизма, не путать:

- **Steam-клиент:** `STEAM+R1`. Работает на путях А и Б, кладёт снимок в библиотеку Steam. Единственный способ снять экран на Deck без клавиатуры.
- **Ren'Py:** клавиша `S` (`screenshot = ['alt_K_s', 'alt_shift_K_s', 'noshift_K_s']`, `00keymap.rpy:40`). Пишет `screenshot%04d.png` **в каталог установки игры** (`config.renpy_base`, `00keymap.rpy:296-330`). Если каталог только для чтения, снимок молча не сохраняется — будет `notify` «Failed to save screenshot as …». На Deck игра стоит в `/home/deck/...`, каталог писать можно.

### 7.10 Полный экран и оконный режим

`config.default_fullscreen = True` ставится **только** при `controller_first()` (`game/options.rpy:15-17`) — игрок без мыши не должен искать переключатель. На десктопе дефолт движка (`None`, то есть оконный с сохранением выбора) не трогается.

Одна тонкость, из-за которой проверка легко даёт ложный результат: `config.default_fullscreen` применяется **только на первом запуске** — `_apply_default_preferences()` работает под `if not persistent._set_preferences` (`$RENPY_SDK/renpy/common/00defaults.rpy:76-81`). Второй и последующие запуски используют сохранённый выбор игрока.

Чтобы честно проверить первый запуск на Deck, надо снести persistent:

```bash
rm -rf ~/.renpy/vn-1755000000        # сотрёт И сейвы, и настройки, и открытую галерею
```

Переключение вручную — сегмент «Оконный / Полный экран» в настройках (`core_screens.rpy:287-289`), плюс движковые `F11` / `Alt+Enter` / `f` (`00keymap.rpy:42`).

## 8. Локальная эмуляция без Deck

```bash
RENPY_VARIANT="steam_deck medium touch" vn test smoke --picks 0,0
RENPY_VARIANT="steam_deck medium touch" VN_AUTOPILOT_SCREENS=gallery,achievements,preferences,chapter_select \
    vn test smoke --picks 0,0
ls .vncache/smoke/
```

Почему это работает: `vn test smoke` запускает игру подпроцессом, наследуя окружение — `env = dict(os.environ, VN_AUTOPILOT="1", …)` (`cli.py:1538`), поэтому `RENPY_VARIANT` доезжает до движка и `choose_variants()` берёт его вместо автодетекции. `VN_AUTOPILOT_SCREENS` читает `vn_qa.autopilot_screens()` (`030_flow.rpy:166-183`) в конце прогона: показывает каждый экран, ждёт 0.3 c, снимает `screen_<name>.png`, прячет.

**Что этот прогон проверяет:**

| Проверяет | Как это видно |
|---|---|
| игра не падает под Deck-профилем | `traceback.txt` отсутствует, `RESULT.txt` = `OK: vn_end_of_content` |
| масштаб 1.4 действительно применился | на скриншотах кегли меню крупнее, чем в прогоне без `RENPY_VARIANT` |
| панели ADR-0009 не сплющены | глазами: фон кнопки выбора не превратился в пилюлю |
| текст не обрезан и не переполняет кнопки | глазами, особенно на длинных языках (`--lang en`, `--lang pseudo`) |
| фактический путь по сценам | `picks.log` |
| cold start против бюджета | строка `cold start (init -> первая интеракция): N c`; превышение — `_fail` |
| вёрстку меню и галереи | `screen_*.png` от `VN_AUTOPILOT_SCREENS` |

**Что он НЕ проверяет, и это принципиально:**

| Не проверяет | Почему |
|---|---|
| **letterbox 40 px и физический масштаб** | окно у прогона десктопное; `RENPY_VARIANT` меняет варианты, но не разрешение экрана. Реальные 1280×800 не эмулируются |
| **`draw_per_virt` и подбор `@N`** | зависит от физического окна. Для этого есть отдельная команда: `vn test oversample --scale 2` (`cli.py:1622-1656`) — она подменяет `draw_per_virt` и дёргает настоящий `Image.get_oversampled_image()` (`game/framework/90_debug/030_oversample.rpy`) |
| **пад** | автопилот не генерирует события `pad_*` вообще. Ни один фокус-путь, ни один `default_focus`, ни одна пад-кнопка автоматикой не проверены |
| **Steam-инициализацию** | `RENPY_VARIANT` подставляет варианты, но не поднимает `steamapi`. `owned() == False`, ачивки, оверлей, `dlc_installed` — только живой Steam |
| **тач** | вариант `touch` есть, событий тача нет |
| **производительность** | десктопный GPU, десктопный CPU |
| **suspend/resume** | нет |

**Этот же прогон гоняет CI — джоба `controller-first`** (`.github/workflows/nightly.yml:85-152`). Матрица из двух профилей: `steam_deck medium touch` и `steam_big_picture`; `VN_AUTOPILOT_SCREENS=main_menu,preferences,gallery,chapter_select`; шоты уходят артефактом `controller-shots-<profile>-<run_id>` с `if: always()`. Гейта нет намеренно — поломка вёрстки видна на картинке, а не в коде выхода; джоба даёт человеку диффабельные скриншоты. Она в `nightly`, а не в `ci`, потому что прогон движка на профиль стоит минуты, а MR-пайплайн держим под 10 минут (G15); отсутствие `RENPY_VARIANT` в `ci.yml` проверяет `tools/vn/tests/test_ci_config.py`. Отдельной джобой, а не шагами внутри `smoke`, — потому что `_autopilot_run` чистит `.vncache/smoke` перед каждым прогоном: один прогон = один артефакт.

Остальные прогоны по-прежнему десктопные: `nightly.yml:57-60` (четыре smoke), `canary.yml:51` (один), `ci.yml:91` (`vn test oversample --scale 2`). И джоба `controller-first` **не** закрывает список выше: пад, Steam, тач, letterbox и производительность остаются за человеком.

## Чего НЕ делать

- **Не считать, что Deck сам себя объявит.** Без App ID и `libsteam_api.so` `renpy.variant("steam_deck")` = `False`. Ручной прогон **обязан** идти с `RENPY_VARIANT="steam_deck medium touch"`, иначе вы смотрите десктопный профиль на маленьком экране и делаете неверные выводы про кегли.
- **Не задавать `RENPY_VARIANT="steam_deck"` в одиночку** — он заменяет список целиком, а движок вставил бы ещё `medium` и `touch` (и снял бы `large`). Копируйте набор из `00steam.rpy:1052-1059`.
- **Не искать причину в конвейере, когда на Deck «мыльные текстуры».** `draw_per_virt` = 0.667 < 1, значит `@2` не грузятся by design (`renpy/display/im.py:743-746`). Проверять оверсэмпл надо `vn test oversample --scale 2`, а не глазами на Deck.
- **Не распаковывать сборку через `zipfile`/Python и потом удивляться `Permission denied`.** Права не восстанавливаются. Для linux берите `tar.bz2`, для зипов делайте `chmod +x vn.sh lib/py3-linux-x86_64/vn`.
- **Не класть игру вне `/home`.** Корневая ФС SteamOS только для чтения; кроме того Ren'Py пишет туда `log.txt` и скриншоты и молча их потеряет.
- **Не проверять первый запуск на «грязном» persistent.** `config.default_fullscreen` применяется только при пустом `persistent` (`00defaults.rpy:76-81`); для честной проверки — `rm -rf ~/.renpy/vn-1755000000`.
- **Не писать `if renpy.variant("steam_deck")` в экране.** Точка касания одна (`035_platform.rpy`), адаптация — токенами `gui.*`. Второй копии экрана под Deck в проекте не существует и появляться не должна (ADR-0014 §6).
- **Не уменьшать `gui.ui_scale` ниже 1.0** «чтобы влезло на маленький экран» — сплющит генерируемые 9-patch панели.
- **Не выкладывать в release-ветку без прогона на живом Deck.** `RENPY_VARIANT`-smoke проверяет вёрстку и не проверяет ни пада, ни оверлея, ни Steam API, ни suspend/resume.
- **Не считать `vn test smoke` заменой ручному прогону.** Событий пада в автопилоте нет вообще — вся controller-навигация проверяется только руками.

```bash
# Оверсэмпл подтверждён движком (то, что нельзя проверить на Deck)
vn test oversample --scale 2                             # oversample: OK

# Deck-профиль локально: скриншоты в .vncache/smoke/, смотреть ГЛАЗАМИ
RENPY_VARIANT="steam_deck medium touch" vn test smoke --picks 0,0
RENPY_VARIANT="steam_deck medium touch" VN_AUTOPILOT_SCREENS=gallery,preferences \
    vn test smoke --picks 0,0

# Сборка для Deck
vn release build --flavor public --package linux
ls build/dist/0.1.5-public/                              # vn-0.1.5+<sha>-linux.tar.bz2 + build-info.json

# Релизный гейт (платформенных проверок в нём нет, но краснеть он не должен)
vn release validate --flavor patron                      # 21 строка: 20 PASS + 1 WARN (озвучка), exit 0
#                                                        public — 20 строк, +WARN зрелости контента, тоже exit 0
```
