### 1.1 Почему `cold_start_s: 30` — это про CI-раннер, а не про RTX

Комментарий в `project.yaml:9` фиксирует калибровку буквально: «референс — CI-раннер (llvmpipe): ~14 c; RTX — ~1 c». Причина в том, что Ren'Py **не бывает по-настоящему headless** — ему нужен GL-контекст (`ARCHITECTURE.md:3559`, норма G23), поэтому в CI он идёт под `xvfb-run` с программным рендером Mesa llvmpipe. Программный рендер тратит секунды там, где дискретная карта тратит миллисекунды: создание GL-контекста, компиляция шейдеров, первая загрузка текстур.

Практический вывод: **порог 30 с бессмысленно проверять локально** — на RTX 5080 фактический замер `.vncache/smoke/startup.txt` = `1.13`, то есть запас более чем 25-кратный. Порог существует ради nightly (`nightly.yml`) и weekly canary (`canary.yml`), где он ловит регрессии на референсно медленном железе. Если вы «оптимизировали старт» и проверили это только локально — вы ничего не проверили.

### 1.2 Что именно меряет `cold_start_s` (и чего он не меряет)

Механика — три точки в коде:

| Точка | Код |
|---|---|
| `_T0 = time.time()` в `init -999 python in vn_qa` | `game/framework/00_core/030_flow.rpy:96` |
| `startup.txt` пишется на **первом** тике автопилота (`n == 0`) | `030_flow.rpy:115-118` |
| тик приходит от `timer 0.6 ... repeat True` во внедряемом раннере | `../../tools/vn/src/vn/cli.py:1281` |

Отсюда три честных оговорки:

1. **У метрики есть пол ≈ 0,6 с** — период таймера. Фактические 1,13 с — это примерно 0,5 с реального старта плюс один такт таймера.
2. **Метрика начинается на `init -999`, а не при запуске процесса.** Всё, что до init-кода — запуск python, `Early init`, `Loading script` — в неё **не входит**. Именно `Loading script` растёт с числом `.rpyc` (см. §3), то есть главный механизм деградации старта бюджетом не покрыт.
3. Метрика существует только под автопилотом: в обычном `vn play` её никто не считает.

### 3.1 Арифметика памяти на реальном персонаже

`mira` показывается как `layeredimage` из трёх одновременно декодированных слоёв (`game/generated/registry/images.gen.rpy:17-30`): `base` + один `outfit` + одна `face`.

```
слой 1200×2200 RGBA        = 10,07 МиБ
mira в кадре (3 слоя)      = 30,2 МиБ
+ фон 1920×1080            =  7,9 МиБ
сцена «один персонаж + фон»= 38,1 МиБ
сцена «четыре + фон»       = 128,7 МиБ
```

Дефолтный `image_cache_size_mb = 400` вмещает ~3 таких четырёхперсонажных сцены. Ren'Py при переполнении кэша не падает — он начинает молча перерасшифровывать образы посреди сцены (thrash). `ARCHITECTURE.md:2409` требует trim-оптимизатора (обрезка наряда по bbox: 47 → 26 МБ на персонажа) и валидатора worst-case — **ни того, ни другого в коде нет**.

Обратите внимание: суффикс `@2` — **чистая конвенция имени**, кода масштабирования в конвейере нет (`tools/vn/src/vn/assets/pipeline.py:121-137` собирает путь f-строкой, `_webp_encode` без `max_side` — `:223`). Движок отрисует спрайт в 600×1100 виртуальных пикселей, но **декодирует полные 1200×2200**. Экономии памяти `@2` не даёт — только резкость на HiDPI.

### 4.1 Модель стоимости `vn assets build` — важнее, чем параметры качества

Читайте цикл сборки как есть (`tools/vn/src/vn/assets/pipeline.py:288-357`):

```python
src_bytes = src.read_bytes()          # :293 — ВСЕГДА, для каждого источника
src_hash  = _b3_bytes(src_bytes)      # :298
...
if blob.is_file(): data = blob.read_bytes()      # :334-335 — попадание в кэш
if dest.is_file() and dest.read_bytes() == data: # :352 — сравнение с выходом
```

Следствия, которые определяют потолок роста:

1. **Даже полностью прогретая сборка читает каждый байт `assets_src/` с диска** — mtime/size-шортката нет, хэш считается по содержимому. Плюс читается блоб кэша и читается текущий выход. Итого объём чтения ≈ `сырцы + 2 × выходы` **на каждый вызов**.
2. **Никакого параллелизма.** Ни `multiprocessing`, ни `ThreadPool`, ни `concurrent.futures` в `tools/vn/src/` нет ни одного вхождения. Флаг `--jobs N` существует только в `ARCHITECTURE.md:1242,3517` — **NOT IMPLEMENTED**; у `vn assets build` есть ровно одна опция, `--profile` (`cli.py:515-519`).
3. **Нарезка PSD не инкрементальна**: `slice_all_psd` вызывается безусловно в начале каждой не-`check` сборки (`pipeline.py:266-268`) и режет каждый PSD целиком; кэшируется только последующий WebP-энкод. Требование послойной инкрементальности и бюджета «P95 < 15 с на PSD до 500 МБ» (`ARCHITECTURE.md:1204`) — NOT IMPLEMENTED.
4. **Кэш растёт без границ**: каждая правка сырца оставляет прошлый блоб в `.vncache/assets/<2hex>/<64hex>` навсегда. Подметает только `vn assets cache --gc` (mark & sweep от манифеста, `pipeline.py:458-491`). `.vncache/video-tmp/` не подметается вообще.

Прикидка: 5000 спрайт-слоёв по 8 МБ = 40 ГБ сырцов. No-op сборка прочитает ~40 ГБ + 2×(выходы). На NVMe 3 ГБ/с это ~15 с; на SATA-SSD 500 МБ/с — ~80 с. Цифры сырцов здесь — допущение (реальный вес меряется после первой партии рендеров), но **линейность по объёму и однопоточность — факты из кода**.

- Кодировка **однопроходная**, 2-pass нет нигде в коде; профили `hd`/`mobile` из `ARCHITECTURE.md:1179` — NOT IMPLEMENTED.

### 6.1 Дадут ли выигрыш `.rpa`-архивы

`build.archive(...)` в проекте **нет ни одного вызова** — и это норма: `ARCHITECTURE.md` §2.4 (`:943`) фиксирует поставку россыпью ради Steam-дельта-патчей, а тематические `.rpa` оставляет опцией mobile-поставки фазы 3 (появление их в desktop-дистрибутиве — осознанное решение с ADR). Оценка по факту формата:

- RPA-3.0 хранит **индекс** сжатым zlib и обфусцированным XOR-ключом, а сами данные — сырыми срезами `(offset, dlen)` (`$RENPY_SDK/renpy/loader.py:157-181`). **Пофайлового сжатия у `.rpa` нет.**
- Содержимое `game/assets/` — WebP и WebM, то есть уже сжатые форматы. **Выигрыш по размеру ≈ 0.**

Что `.rpa` реально даёт: (а) один файл вместо тысяч — быстрее распаковка инсталлятором, меньше проверок антивирусом, меньше записей в файловой таблице; (б) барьер против «щёлкнул правой кнопкой — вытащил все CG»; (в) удобную единицу поставки DLC. Что забирает: пересборка всего архива при правке одного ассета и патч размером с архив вместо размера файла.

**Вердикт: в desktop-каналах — нет** (норма §2.4: пересборка/перекачка архива при правке одного ассета убивает Steam-дельта-патчи). Единственный легальный сценарий — тематические `.rpa` мобильной поставки фазы 3, и то через ADR. Приоритизация — [Роадмап](37-roadmap.md).

### 7.1 Ключевой факт: инкрементальности по главам нет

Проверено по коду, формулировка точная:

| Механизм | Как есть | Код |
|---|---|---|
| Компилятор | **все** выходы пересчитываются в память на каждый вызов; на диск пишутся только изменившиеся байты | `tools/vn/src/vn/content/compile.py:899-910` (запись), `:882-890` (`--check`) |
| Ren'Py-мост (парсинг авторских `.rpy`) | ключ кэша считается по **всему набору** файлов сразу: `for f in sorted(files): update(path); update(bytes)` | `tools/vn/src/vn/content/analyze.py:84-95` |
| Свежесть генерата | побайтовое сравнение выходов; `manifest["inputs"]` пишется, но **никогда не читается обратно** | `compile.py:882-886`, `:912-922` |

Плюс: файлы `.vncache/analyze-*.json` не подметаются ничем — `cache_gc` знает только `.vncache/assets` (`pipeline.py:462`).

### 7.2 Когда упрётся `generated_total_kb: 65536`

Формула выводится из реальных файлов. Сгенерированная сцена = шапка + обвязка + **дословная копия авторского `.rpy`** (`tools/vn/src/vn/content/scenes.py:270-271`). Замер: `s010_intro.scene.rpy` = 676 Б → `ch01_s010.gen.rpy` = 1997 Б, то есть фиксированная часть ≈ 1,3 КБ. Отношение `.rpyc`/`.rpy` по четырём реальным сценам — 1,39 / 1,53 / 1,41 / 1,46, в среднем **≈ 1,45**.

```
вес одной сцены в game/generated ≈ (1,3 КБ + размер авторского .rpy) × 2,45
```

| Сценарий | Авторский `.rpy` | Пара `.rpy`+`.rpyc` | 10 сцен = глава | Бюджет 65 536 КБ упрётся |
|---|---|---|---|---|
| Демо (как сейчас, ~4 реплики) | 0,7 КБ | 4,9 КБ | 49 КБ | ~1300 глав |
| Реальная сцена, 30 реплик | 2,4 КБ | 9,1 КБ | 91 КБ | **~720 глав** |
| Плотная сцена, 80 реплик | 6,4 КБ | 18,9 КБ | 189 КБ | ~350 глав |

Плюс растут реестры: `menus.gen.rpy` уже 6 941 Б (95 UI-строк + подписи пунктов меню), `gallery.gen.rpy` 3 261 Б.

**Модель проверена измерением, и она не завышена.** `vn test corpus` на 100 → 20 000 сцен (по 8 реплик в каждой) даёт стабильные **3,1–3,6 КБ `.rpy` на сцену** на всех масштабах (§7.5). Каталог корпуса `.rpyc` не содержит — движок по `game/` корпуса не запускается, — а в боевом дереве `.rpyc` весит ×1,5 к `.rpy` (замер по четырём сценам репозитория, выше), то есть пара — ×2,5 к измеренному. Итог: бюджет `generated_total_kb` при сценах на 8 реплик упирается около **7,5 тыс. сцен**, при боевых 30 репликах — около **7 тыс. сцен**. То есть **сотни глав, и бюджет генерата не является связывающим ограничением** — раньше упрутся прогон smoke (§7.3) и человеко-часы, а не число в `project.yaml`.

Что делать, если всё-таки упрётся (по возрастанию цены):
1. Поднять число в `project.yaml:8` — это осознанное решение, а не обход: бюджет существует ради cold start, и вместе с ним надо завести замер `Loading script` (сейчас его нет).
2. Перестать копировать авторский источник в генерат (`scenes.py:270-271`) — минус ~40 % объёма, ценой того, что генерат перестанет быть самодостаточным для чтения в отладке.
3. Ввести бюджет на суммарный `.rpyc` отдельно от каталога (`ARCHITECTURE.md:89`) — правильное решение, потому что мерить надо именно то, что грузится на старте.

### 7.3 Когда сломается smoke

`vn test smoke` играет игру **целиком**: от `label start` (`030_flow.rpy:217`) по цепочке `exits` до `vn_end_of_content`. Продвижение — `renpy.queue_event("dismiss")` раз в 0,6 с (`030_flow.rpy:128`, таймер `cli.py:1281`), выбор в меню — раз в 1,0 с (`20_ui/screens/choice.rpy:54`). Каждый тик — скриншот PNG.

```
длительность прогона ≈ (число реплик + число меню) × 0,6 с
```

Замер демо: 19 тиков, 19 PNG на 1,0 МБ (в среднем 54,6 КБ на плейсхолдерной графике).

| Объём | Длительность прогона | Скриншотов | Вердикт |
|---|---|---|---|
| Сейчас (15 реплик, 2 меню) | ~15 с | 19 / 1 МБ | норма |
| 1 реальная глава (300 реплик) | **~3 мин** | ~300 | **пробивает `--timeout 180` по умолчанию** (`cli.py:1574`) |
| 5 глав | ~15 мин | ~1500 / сотни МБ артефакта | nightly ещё терпит |
| 10 глав | ~30 мин × 4 прогона матрицы (`nightly.yml:55-60`) = 2 часа | ~3000 | не терпит |
| 50 глав | ~2,5 часа на **один** прогон | ~15 000 | невозможно |

Дополнительно ломается `--picks`: это плоский список индексов «по одному на меню в порядке появления» (`030_flow.rpy:137-140`), при сотнях меню он нечитаем и неподдерживаем.

**Решения и когда их принимать:**
- **На первой реальной главе:** передавать `--timeout` явно везде, где есть smoke; в `nightly.yml:55-60` таймаут не передаётся вообще.
- **На 3–5 главах:** шардировать прогон. Механизм уже есть в коде — `VN_AUTOPILOT_LOAD` грузит сейв на старте (`030_flow.rpy:162-164`), а `vn save corpus --add` умеет делать фикстуры (`cli.py:1185-1213`). То есть «фикстура на вход каждой главы + прогон от неё» реализуем без нового рантайма, нужна только CLI-обвязка.
- **На 10+ главах:** `vn test smoke --affected --shard N/M --seed` из `ARCHITECTURE.md:3530,3587` — NOT IMPLEMENTED; реальный `test smoke` принимает только `--picks`, `--lang`, `--timeout`.
- **Всегда:** артефакт `.vncache/smoke/` уходит в GitHub с retention 7 дней (`nightly.yml`) — при тысячах PNG это гигабайты; понадобится отбор (первый/последний кадр сцены), а не «всё подряд».

### 7.5 Корпус масштаба (`vn test corpus`): измеренные числа вместо модели

Всё выше в этой части до 2026-08-18 было арифметикой по замерам на четырёх сценах. Теперь у утверждений о масштабе есть прогон: `vn test corpus` (`tools/vn/src/vn/corpus.py`) строит **настоящий проект** заданного размера **вне репозитория**, гоняет по нему конвейер и печатает числа. Тесты корпуса — `tools/vn/tests/test_corpus.py` (14), ночная джоба — `nightly.yml: corpus`.

```bash
export RENPY_SDK=...                # прогон поднимает движок: build-bridge разбирает сцены корпуса
vn test corpus --scenes 2000 --images 2000 --lines 8 --vars 201 --dest /tmp/corp
```

Что делает прогон: `generate` → `assets build` → `content lint` → `content compile` → **повторный** `content compile` → `assets memory`, с замером времени, cpu (своего и детей — Ren'Py-моста и ffmpeg), пиков RSS, объёма каждой зоны и долей бюджетов G19. Прогон **красный**, если упала стадия, если повторная компиляция что-то перезаписала (идемпотентность генерата — не наблюдение, а проверка внутри `measure()`) или если превышен бюджет G19. Дерево сносится и после аварии; генерация отказывается писать в каталог без маркера `.vncorpus.json`.

**Грабля с каталогом по умолчанию.** `default_dest` — `.vncache/corpus`, а `vn save corpus --add` кладёт туда же скриншоты автопилота (`cli.py`: `shots = root / ".vncache" / "corpus"`). После сейв-корпуса `vn test corpus` откажется работать («не пуст и не является корпусом») — до разведения имён указывайте `--dest`.

#### Что из этого следует

1. **Стадии линейны каждая по своему фактору.** `assets build` — по числу выходов (~0,7 мс на выход), `generate`/`lint`/`compile` — по числу сцен. Полная стоимость **на сцену** при росте падает: 17,8 мс (100 сцен) → 3,1 мс (20 000), потому что фиксированный старт Ren'Py-моста амортизируется.
2. **Единственная сверхлинейная стадия — модель памяти.** `vn assets memory` зависит от **произведения** «сцены × выходы»: при фиксированных 2 000 сценах рост выходов в 16 раз даёт ×2,9 времени, при фиксированных 5 300 выходах рост сцен в 10 раз — ×8,8 (0,94 → 8,30 с). Причина в коде: `_character_cost` (`tools/vn/src/vn/assets/memory.py:102`) сканирует **все** ключи манифеста сборки на каждого участника каждой сцены, хотя результат зависит только от пары (персонаж, масштаб). На 5 000 сцен это 3,5 с, на боевом корпусе с десятками тысяч 4K-выходов — десятки секунд на **каждый** `vn build`. Лечится мемоизацией по `(char_id, scale)` — **открытый P2**, в коде не сделано.
3. **Генерат линеен и предсказуем:** 3,1–3,6 КБ `.rpy` на сцену на всех масштабах, пересчёт бюджета — §7.2. Идемпотентность подтверждена на масштабе: повторная компиляция 20 000 сцен переписывает **ноль** файлов.
4. **Память тулинга линейна, но не бесплатна:** пик RSS `vn` 50 МБ (100 сцен) → 747 МБ (20 000). На 20 тыс. сцен компилятор держит в памяти все выходы разом (`compile.py` считает всё в память, а на диск пишет только изменившееся) — на слабом раннере это станет вопросом раньше, чем бюджет генерата.
5. **Модель памяти образов масштабно-инвариантна — и это правильно:** худшая сцена — свойство композиции кадра, а не размера проекта. Но **доли бюджета на корпусе с боевыми несопоставимы**: схема `project@1` держит пол `image_cache_mb ≥ 16 МБ`, а пропорционально экрану 64×48 нужно было бы 1,5 МБ. Сопоставима величина «сцена в экранах»: корпус — 50,2 экрана, боевая худшая сцена — ≈28 экранов при бюджете ≈43 (`project.yaml`).
6. **Бюджет `assets_total_mb` корпусом не проверяется** и на нём бессмыслен: 8 000 мастеров профиля 64×48 = 3,0 МБ = 0,01 % бюджета. Это осознанное свойство метода — иначе прогон мерил бы производительность libwebp, а не конвейера.

#### Найденный потолок — и он устранён

Первый же прогон на 7 000–8 000 сцен уронил `content compile` **сырым** `OSError: [Errno 7] Argument list too long`: `analyze.py` передавал каждый путь сцены **отдельным argv** в `renpy.sh … vn_analyze`, поэтому предел зависел от суммарной длины argv, а не от числа сцен. Замеры прямой пробой `execve` на этой машине (`ARG_MAX = 1 048 576` Б): путь 101 Б (боевое дерево) — 9 468 аргументов, путь 177 Б (корпус в `/private/tmp`) — 5 599. То есть потолок был **5,6–9,5 тыс. сцен** при заявленных десятках тысяч, без диагностики и без обхода: кэш анализа заполняется только после успешного прогона, поэтому падал и повторный запуск.

**Исправлено:** список сцен уезжает в мост файлом — `renpy.sh <root> vn_analyze <out.json> --files-from <список>` (`analyze.py: write_files_listing`, файл `.vncache/analyze-files.txt`; приёмник — `_vn_analyze_inputs` в `game/framework/00_core/050_build_bridge.rpy`, прямые аргументы мост понимает по-прежнему — ими его зовут руками при отладке одной сцены). Батчинг (чанки под `ARG_MAX`) отвергнут осознанно и со счётом: каждый запуск моста — это init **всего** проекта, а он растёт вместе с контентом, поэтому четыре чанка по 5 000 сцен на 20 тыс. стоили бы ~60 с против 23 с одним запуском (цифры — в докстринге `analyze.py:6-24`). Голый `OSError` от `execve` теперь превращается в `AnalyzeError` с числом сцен и путём списка.

**Проверено после починки:** 10 000 сцен — `content compile` 13,3 с, 20 000 сцен — 22,2 с, ноль ошибок (таблица выше). Связывающим ограничением стал бюджет `generated_total_kb`, а не argv.

## 8. Персонажи: 1 → 20 → 50+

### 8.1 Комбинаторика на реальном примере

`content/characters/mira/character.yaml:7-12` объявляет матрицу `poses: [a]`, `outfits: [school, casual]`, `emotions: [neutral, smile, angry]` — то есть **1 × 2 × 3**.

Ключевое различие, которое надо держать в голове: **файлы аддитивны, комбинации мультипликативны.**

```
файлов на персонажа   = poses × (1 base + outfits + emotions)
комбинаций на экране  = poses × outfits × emotions
```

Для `mira`: файлов `1 × (1+2+3) = 6` (проверено: `game/assets/spr/mira/a/` — `base@2.webp`, 2 наряда, 3 лица); комбинаций `1×2×3 = 6`.

| Персонаж | Матрица | Файлов | Комбинаций | Вес в `game/assets/spr` (при 1,5 МБ на слой) |
|---|---|---|---|---|
| `mira` сейчас | 1×2×3 | 6 | 6 | 47 КБ (плейсхолдеры) |
| Реалистичный второстепенный | 2×2×4 | 2×(1+2+4) = 14 | 16 | ~21 МБ |

| **50 персонажей** | — | **~1000+ файлов** | — | **1,5 ГБ+** |

Вес слоя 1,5 МБ здесь — допущение (WebP q95 с 1200×2200 RGBA); измерьте его на первой партии реальных рендеров и подставьте. Что **не допущение**: бюджет `assets_total_mb: 20000` считается по `_dir_size(game/assets)` и краснит `vn build`.

| Механизм | Поведение при росте | Код |

| Холодная сборка | O(N) однопоточно, полное чтение всех сырцов (§4.1) | `pipeline.py:288-357` |
| Порог ADR-0004 | суммарный вес бинарей в `assets_src/` (из подсчёта исключены `.json/.yaml/.yml/.md/.txt/.gitkeep`): warn > 30 МБ, error > 50 МБ | `tools/vn/src/vn/content/lint.py:47`, `:371-400` |

**Самый близкий порог — именно ADR-0004.** Сейчас в `assets_src/` 11 бинарей на 129,3 КБ (плейсхолдеры). Реальный PNG-рендер 1200×2200 RGBA весит порядка 3–8 МБ. То есть:

```
warn (30 МБ)  ≈ после 4–10 реальных файлов
error (50 МБ) ≈ после 6–16 реальных файлов
```

Это буквально **один-два персонажа**. Значит переезд сырцов в хранилище — не «когда-нибудь», а часть подготовки к первой реальной партии рендеров. Механика хранилища (`vn assets lock` / `push` / `pull` / `status`, манифесты `asset_src@1`) — IMPLEMENTED, но **ни разу не запускалась**: `~/vn-assets-store` на машине не существует, `*.manifest.json` в репозитории ноль. S3-бэкенд — честная заглушка с внятным сообщением (`tools/vn/src/vn/assets/storage.py:129-133`). Детали — [Хранилище и бэкап](31-storage-and-backup.md).

**Локи при команде из нескольких человек** (`tools/vn/src/vn/assets/storage.py:99-134,178-209`):

| Свойство | Как есть | Риск |
|---|---|---|
| Где включается | **только** внутри `vn assets push` | `pull` без `--edit` лок не берёт и не проверяет; локальную правку ничто не останавливает |
| Атомарность | read-then-write, без `If-None-Match` (`ARCHITECTURE.md:293` требует условной записи) | два клиента в гонке оба «выигрывают» |

Точный текущий срез (посчитано по файлам): `loc/po/en/common.po` — **115** записей (114 UI-строк + имя персонажа `char:mira`), `ch01.po` — **18** (14 реплик + 4 пункта меню), `ch90.po` — **3**; итого **136**, что совпадает с `vn loc report` (de/en/pseudo — 136/136, fuzzy 0). Удельные веса взяты из замеров: диалоговая запись PO ≈ 193 Б (`ch01.po` 3 478 Б / 18), UI-запись ≈ 138 Б (`common.po` 15 906 Б / 115), строка перевода в `game/tl` ≈ 90 Б плюс `.rpyc` ×1,5.

| Объём | Записей на язык | PO на язык | `game/tl/<lang>` (`.rpy`+`.rpyc`) |
|---|---|---|---|
| Сейчас | 136 | **19,9 КБ (замер)** | **14,6 КБ (замер)** |
| 1 реальная глава (300 реплик + 20 пунктов) | ~430 | ~77 КБ | ~70 КБ |
| 10 глав | ~3 300 | ~630 КБ | ~690 КБ |
| 50 глав | ~16 100 | ~3,1 МБ | ~3,4 МБ |
| **50 глав × 10 языков** | 161 000 единиц перевода | **~31 МБ PO в git** (текст, диффится нормально) | **~34 МБ в `game/tl`** |

Три следствия:

1. **`game/tl` не покрыт ни одним бюджетом**, а именно он растёт быстрее всего и **весь грузится движком на старте** (все языки, а не выбранный). Это и есть будущая деградация `Loading script`. Шардирование по главам уже правильное: `game/tl/<lang>/dialogue_<ch>.rpy` (`tools/vn/src/vn/loc/po.py:378-398`), так что перекомпилируются только изменившиеся файлы.
2. **Стоимость перевода линейна по новым и fuzzy-записям**, и это ровно то, что печатает `vn loc report`. Умножитель — число языков: `release_coverage_min: 0.98` (`loc/loc.yaml:7`) проверяется гейтом по **каждому** несинтетическому языку (`release.py:478-501`). Десятый язык — это не «ещё немного файлов», это десятый блокер релиза каждой главы.
3. **Риск переиспользования say-id — реальный и растёт с объёмом правок.** `used_nums` собирается из id, присутствующих **в текущем файле** (`tools/vn/src/vn/loc/keys.py:87-106`); удалили реплику — её номер освободился и достанется следующей новой реплике, которая унаследует чужой перевод из PO. High-watermark и ретайрмент из `ARCHITECTURE.md` — NOT IMPLEMENTED. Дешёвое лечение сейчас: не переиспользовать номера вручную и держать `loc/ledger/chNN.json` в ревью; правильное — реализовать high-watermark до того, как переводов станет много.

Ещё не реализовано и понадобится с ростом языков: RTL, цепочки фолбэка шрифтов, плюральные формы, локализуемые изображения, POT/msgmerge, push/pull в CAT-систему (все — NOT IMPLEMENTED).

## 11. Команда: 1 → 5 человек

### 11.1 Почему архитектура уже шардирована

Конфликты в git возникают там, где два человека правят один файл. Дерево спроектировано так, чтобы этого не случалось:

| Единица работы | Свой файл/каталог | Кто с кем не пересечётся |
|---|---|---|
| Глава | `content/chapters/ch<NN>_<slug>/` целиком | два сценариста на разных главах |
| Сцена | пара `sNNN_<slug>.scene.{yaml,rpy}` | два сценариста внутри одной главы |
| Переменные главы | `content/chapters/<ch>/vars.yaml` (store = `ch<NN>`) | без конфликтов в общем файле переменных |
| Реплики для перевода | `loc/ledger/ch<NN>.json` | переводчики по главам |
| Перевод | `loc/po/<lang>/ch<NN>.po` | язык × глава |
| Выход перевода | `game/tl/<lang>/dialogue_<ch>.rpy` | не в git вообще |
| Персонаж | `content/characters/<id>/character.yaml` | арт-директор vs сценарист |
| Пак/DLC | `packs/<id>/` — зеркало `content/` | команда DLC vs основная |

**И главное: весь генерат не в git** (`.gitignore` исключает `game/generated/`, `game/assets/`, `game/tl/`). Если бы 19 `.gen.rpy` + 19 `.rpyc` коммитились, каждый merge двух веток давал бы конфликт в бинарном `.rpyc` и в `manifest.json` — то есть конфликт при **любой** параллельной работе. Это, а не экономия места, — главная причина решения.

### 11.2 Что остаётся узким местом

| Файл | Почему конфликтует | Смягчение |
|---|---|---|
| `content/ui/strings.yaml` | один файл на все 95 UI-строк | правки редки; при росте — шардировать по доменам |
| `chapter.yaml: scene_order` | правится при каждой новой сцене главы | одна глава = один владелец (заготовка в `CODEOWNERS:25-26`) |
| `content/renames.yaml`, `content/registry/id_registry.json` | кросс-главные, правятся релизом | владельцы `@tech-lead` (`CODEOWNERS:15-16`) |
| `content/gallery/*.yaml`, `content/achievements/*.yaml` | один файл на всю игру | **в `CODEOWNERS` их нет вообще** |
| `project.yaml` | версия, бюджеты, флейворы | `@tech-lead @engine-dev-1` |
| `assets_src/` бинари | git не умеет мержить PNG | лок хранилища (§9) — но он не атомарен |

**Состояние `CODEOWNERS` — PARTIALLY IMPLEMENTED:** 19 правил (`CODEOWNERS:5-23`), но **все хэндлы — плейсхолдеры** (`@tech-lead`, `@engine-dev-1`, …; TODO прямо в шапке файла, `CODEOWNERS:3`). Не покрыты: `/content/gallery/`, `/content/achievements/`, `/content/ui/`, `/packs/`, `/assets_src/` и — важнее всего — **`/.github/`**, где живёт настоящий CI: 5 workflow, 9 определений джоб (на теге релизная `build` разворачивается матрицей флейворов в 2 прогона, итого до 8).

### 11.3 Порядок действий при найме второго человека

1. Заменить плейсхолдеры в `CODEOWNERS` на реальные хэндлы; добавить строки на непокрытые зоны и на конкретные главы по образцу `CODEOWNERS:26`.
2. Поднять хранилище сырцов на общем диске/NAS: `.vnstorage.yaml` сейчас указывает на `~/vn-assets-store` — **локальный путь**, для команды бессмысленный. Прогнать `vn assets lock` + `push` + `pull` хотя бы раз — механизм ни разу не исполнялся вживую.
3. Ввести правило «глава = ветка = один владелец» и держать `vn build --check` зелёным в PR (это уже делает `ci.yml`).
4. Проверить, что у каждого есть работающий `RENPY_SDK` — без него `vn build` падает чистой ошибкой компилятора (`tools/vn/src/vn/content/analyze.py:26-29`), а `vn bootstrap` собирает всё локально: удалённого кэша артефактов (G4) **нет**.

## Чего НЕ делать

- **Не считать, что «cold start 1,13 с» что-то доказывает.** Метрика снята на RTX с аппаратным GL, а бюджет калиброван по llvmpipe (`project.yaml:9`). Регрессию старта увидит nightly, не вы.
- **Не оптимизировать размер `game/assets`, пока он единицы мегабайт.** 97 % дистрибутива — движок и python (§6).
- **Не переключаться на `--profile draft` перед пушем.** Профиль входит в сравнение свежести — `vn build --check` покраснеет на всех выходах (`pipeline.py:309-311`).
- **Не полагаться на релизный гейт в вопросе качества энкода.** В `release.py` **нет ни одной ссылки на `profile`** — черновые q50/CRF42 ассеты пройдут все 21 проверку.
- **Не удалять `.vncache/assets-manifest.json` ради «чистой пересборки».** Он не в git и ниоткуда не восстанавливается; без него удаление осиротевших **навсегда** отключается, а сборка остаётся зелёной (`pipeline.py:394-399`).
- **Не оставлять `vn assets cache --gc` на потом.** Кэш растёт неограниченно и не подметается ни одной джобой CI.
- **Не рисовать оверлеи персонажей «на будущее»** — эмиссии `overlays`-группы нет (`images.py:178-182`), файлы соберутся и уедут в дистрибутив мёртвым грузом.
- **Не добавлять реальную главу, не подняв `--timeout` у smoke.** 300 реплик × 0,6 с ≈ 180 с — ровно дефолт (`cli.py:1574`), прогон снимут по таймауту и назовут это падением.
- **Не заливать в `assets_src/` реальные рендеры «на пробу».** Порог ADR-0004 в 50 МБ — это единицы файлов, а git append-only: убрать их потом = переписывание истории.
- **Не ставить `game/generated/`, `game/assets/`, `game/tl/` под git «чтобы у всех было одинаково».** Это гарантированный конфликт в `.rpyc` и `manifest.json` при любой параллельной работе (§11.1).
- **Не искать `vn test perf`, `vn validate --budgets`, `vn build --jobs/--use-artifact`** — ни одной из этих команд не существует, они есть только в `ARCHITECTURE.md`.
